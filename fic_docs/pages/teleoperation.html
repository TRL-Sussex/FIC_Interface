Teleoperation

One station's arm follows another's across the lab network. Built into the Multi-Robot page.

Overview

Pick a leader station and a follower station on the Multi-Robot page and press Start teleop. The follower's arm then copies the leader's joint motion.

  • Any Studio can set up a pair. The Master station, at a lab's control PC, can pair two robots without being either of them.
  • Several pairs can run at once.
  • One leader can drive several followers. A follower has one leader at a time.

This replaces the teleop extension (Studio ≤ 4.3), which ran one session per ROS domain. It is not compatible with that extension, or with the dev console's older teleop tab.

Quick start (simulation)

  1. On two PCs (or stations), start a simulation of the same robot type.
  2. On any Studio, open Multi-Robot. Under Teleoperation, choose the leader, then the follower, then press Start teleop.
  3. The follower accepts at once, because it is in simulation. Its card reads follows Robot N.
  4. Move the leader, for example with its control bar. The follower copies the motion.
  5. To end the pairing, press Stop on the session row, on any Studio. The follower holds where it is.

On hardware

  • The follower's operator must agree. When the follower is on hardware, its Studio shows the request and who sent it. Nothing moves until someone at that robot presses Accept. An unanswered request is refused after 30 s.
  • The leader's mode is not changed. Set the leader to a mode its operator can move it in, such as Joint Admittance.
  • The follower is put in Joint Impedance, with the admittance planner off. When the session ends, the follower holds its position and the planner goes back to how it was.
  • Try it in simulation first, with a low Max speed.

How the follower moves

The follower copies the leader's motion relative to where each arm stood at the start:

  • At the start, the follower stays exactly where it is. The two arms never need to be lined up first, and starting never makes the follower jump.
  • From then on, each follower joint moves by scale × the leader joint's motion, subject to these limits in order:
StepDetail
Continuous jointsMotion is summed from small increments, so a joint crossing ±180° does not look like a full turn.
Joint limitsTargets are clamped to the follower's joint_limits_deg in robots_config.yaml. The controller's own limits and workspace zone still apply.
SmoothingAn exponential filter.
Speed capNo joint target moves faster than Max speed (default 35 °/s).
DeadbandNothing is sent while every joint is within 0.002 rad (0.1°) of where it should be. A still leader therefore costs no traffic.

This first version supports joint-space teleop between robots of the same type and joint count. The follower's Studio refuses other pairs, and gives the reason. Cartesian teleop, mapping between different robots, and force feedback are not built yet.

Safety

EventWhat happens
E-stop at the leader or the followerThe session ends, and the partner arm is E-stopped as well.
E-STOP ALLEvery Studio E-stops, which also ends every session.
Leader data pauses for more than 0.3 sThe follower stops receiving targets and holds its last one. Its card shows holding.
No first data from the leader within 10 sThe follower ends the session (no data from leader).
Leader silent for 5 sThe follower ends the session and holds its position. It was 2 s, which sat below this lab's own discovery stall: a process joining the ROS domain pauses an existing leader's stream for about 1.9 s, so starting anything new during a session could end it with “lost leader”.
Follower silent for 3 sThe leader stops streaming.
A Studio closesIts sessions end.
Over the network

Teleop, and the E-stop that reaches the partner arm, travel over the lab network. Wifi adds a few milliseconds of latency, with occasional spikes. Each robot's own E-stop remains the primary stop.

ROS 2 topics

TopicTypeCarries
/fic/teleop/sessionstd_msgs/String (JSON)These messages:
  • request, accept and reject, which set up a pair;
  • stop, which ends one;
  • alive, sent every 0.5 s by the leader and the follower.
Each Studio acts only on messages for its own station.
/fic/teleop/leader_jointsstd_msgs/Float64MultiArray, sensor QoS[leader station, q1, q2, …] at 100 Hz from every station that is leading (one stream however many followers). Every Studio opens this topic when it starts, so no new ROS endpoint has to be discovered when a pair starts — over wifi that took several seconds.
robotF_desired_joint_anglesstd_msgs/Float32MultiArrayThe follower's targets. Its Studio publishes them for its own arm only.
/fic/fleet/commandstd_msgs/String (JSON)Carries the E-stop sent to the partner arm. See Multi-Robot.

Troubleshooting

SymptomCheck
The other Studio is not in the pickersBoth Studios must be on the same ROS domain and able to discover each other. See Multi-PC Lab Setup.
Refused: no joint dataThe follower's simulation or robot is not running.
Refused: different robots or joint counts differBoth stations must use the same robot type.
Ended: no data from leaderThe leader's simulation or robot is not running, so it has no joints to stream.
Follower card shows holdingThe leader's data has paused. Check the network between the two PCs.
“Lost leader” the moment you start something elseAny process joining the ROS domain stalls an existing leader's stream for about 1.9 s — launching a trajectory player, a recorder or another Studio is enough. The liveness window was raised to 5 s to absorb it. If you still see this, something is taking even longer to discover; start it before the session rather than during it.
A command you published was ignoredDiscovery here takes up to about 12 s, and publishing into a topic nobody has subscribed to yet succeeds silently and delivers nothing. Wait for a subscriber before sending. Publishing a request repeatedly to “make sure” is worse: each copy is a separate request.

For developers

  • fic_studio.teleop.session: the protocol and each Studio's part in it (TeleopManager).
  • fic_studio.teleop.tracker: the follower's maths (JointFollower).

Both modules are Qt-free and are tested without a network (test/test_teleop_core.py).
