Contact Localization — Adding a Robot

What a robot must actually provide before contact localization can work on it, in the order you should check. Every gate below has a command that answers it in seconds, so you can find out in ten minutes whether an arm is a candidate rather than discovering it three days into a port.

Work through the gates in order

They are ordered by how expensive they are to discover late. Gate 0 is a property of the mechanism and cannot be fixed by any amount of work; Gate 1 is a missing file you can author. Do not start writing config for an arm that fails Gate 0.

Gate 0 — Does the method apply at all?

Three properties are load-bearing. If the arm lacks any of them, stop here.

RequirementWhyIf it fails
A serial kinematic chain The whole method rests on “a contact on link k loads only joints 1…k”. That is a property of a serial chain. In a closed-loop or parallel mechanism, force paths close through the structure and the triangular pattern simply does not exist. Fatal. No estimator fixes it. CSPM in this repo is exactly this case.
Genuine per-joint torque sensing You need what the joint measured, not what the controller commanded, and not a motor-current estimate. Commanded torque contains no contact information at all; current-based estimates are dominated by friction. Fatal. CSPM's bridge writes the firmware's commanded t_in, which is useless here.
A URDF with real inertial data The residual is tau_meas − g(q). Without inertias, Pinocchio returns g(q) ≈ 0 and the “residual” is just the raw torque, gravity and all. Fixable — but you must author or obtain a proper URDF. Franka_FR3 fails here today.

Check it

# 1. Inertial blocks present? Anything less than one per moving link is a fail.
grep -c '<inertial>' fic_ws/src/menagerie/model/<ROBOT>/URDF/<ROBOT>.urdf

# 2. Is gravity actually non-degenerate? Should be several N.m at a bent pose, not ~0.
source /opt/homebrew/Caskroom/miniforge/base/etc/profile.d/conda.sh && conda activate fic_ros
python3 -c "
import pinocchio as pin, numpy as np
m = pin.buildModelFromUrdf('<path to urdf>'); d = m.createData()
q = pin.neutral(m); q[:] = 0.5
print('total mass', round(sum(i.mass for i in m.inertias), 3), 'kg')
print('||g(q)||  ', round(np.linalg.norm(pin.computeGeneralizedGravity(m, d, q)), 3), 'N.m')
"

A total mass near zero, or ‖g(q)‖ under about 1 N·m on a metre-scale arm, means the URDF has no usable inertias.

Gate 1 — Files that must exist

FileRequirement
menagerie/model/<ROBOT>/URDF/<ROBOT>.urdfReal inertials. Joint names must match the config's joint_names exactly.
menagerie/model/<ROBOT>/xml/scene.xmlAn MJCF whose body names match the URDF link names. This is what lets a link index map to a MuJoCo body with one lookup and no translation table.
Mesh assetsEach link body needs at least one mesh geom with vertices and normals, for surface contact candidates. Primitive-only bodies give no surface to sample.
The name-matching requirement is the one people miss

The URDF and the MJCF are separate files maintained by different upstreams, and nothing enforces that their names agree. On the Kinova they happen to match exactly (Shoulder_Link, ForeArm_Link, …), which is why the port was cheap. Check before you assume:

python3 -c "
import mujoco, pinocchio as pin
mj = mujoco.MjModel.from_xml_path('<scene.xml>')
mjnames = {mujoco.mj_id2name(mj, mujoco.mjtObj.mjOBJ_BODY, i) for i in range(mj.nbody)}
m = pin.buildModelFromUrdf('<urdf>')
urdf = {f.name for f in m.frames if f.type == pin.FrameType.BODY}
print('in URDF but not MJCF:', sorted(urdf - mjnames))
"
Also check that mesh normals are indexed the same way as vertices

The estimator pairs mesh_normal[i] with mesh_vert[i] to get the outward normal at each candidate surface point, and that normal decides which push directions are physically possible (F·n ≤ 0). MuJoCo indexes normals separately from vertices in general — mesh_facenormal need not equal mesh_face. On the Kinova meshes the two arrays happen to be elementwise identical, so the pairing is valid; on a different robot it may not be, and the failure is silent: the push constraint quietly starts rejecting the right contacts and accepting the wrong ones.

python3 -c "
import numpy as np, mujoco
m = mujoco.MjModel.from_xml_path('<scene.xml>')
b = mujoco.mj_name2id(m, mujoco.mjtObj.mjOBJ_BODY, '<a link body name>')
g = m.body_geomadr[b]; d = m.geom_dataid[g]
fa, fn = m.mesh_faceadr[d], m.mesh_facenum[d]
same = np.array_equal(m.mesh_facenormal[fa:fa+fn], m.mesh_face[fa:fa+fn])
print('normal indexing matches vertex indexing:', same)
print('vertnum', m.mesh_vertnum[d], 'normalnum', m.mesh_normalnum[d])
"

If that prints False, geometry.py must look normals up through mesh_facenormal rather than by vertex index. Verify the result either way: compute each face's geometric normal from its winding and check it agrees with the stored normals — the Kinova's ForeArm_Link gives a mean dot product of +0.92 with about 92% agreement, the rest being ordinary smooth shading at sharp edges. A mean dot near zero means the pairing is wrong.

Gate 2 — Config keys

In fic_studio/fic_studio_robots.yaml (authoritative — Deploy regenerates fic_library/config/robots_config.yaml from it). See Robot Config & Models.

KeyWhy it matters here
num_joints, joint_namesJoint order is load-bearing and must match the URDF. The estimator maps by name, never by position — but a mismatch still means it cannot find the joint at all.
urdf_path, mujoco_xml_pathBoth must point at files that exist. IIWA_14 declares a .urdf that is not on disk.
torque_signApplied by fic_control before publishing. Never apply it a second time in Python — that silently inverts every residual.
gravity_compensatedIf the driver already removes gravity (as libfranka's tau_ext_hat_filtered does), g(q) must not be subtracted again. Get this wrong and a full gravity vector appears as phantom contact.
joint_torque_limits.maxUsed for safety clamping and to interpret per-link thresholds. Kinova's are [39, 39, 39, 39, 9, 9, 9] N·m — note the distal joints are far weaker.

Gate 3 — The driver must publish measured torque

The vendor driver writes into the shared-memory segment; fic_control reads it, applies torque_sign, filters it, and republishes on {rid}_joint_torques. Confirm the driver is writing a measurement:

# With the arm running and stationary, then again while you push a link:
ros2 topic hz   /robot1_joint_torques
ros2 topic echo /robot1_joint_torques --once

Values must change when you push the arm and settle when you let go. If they track your commands instead of your hands, the driver is publishing commanded torque and this arm fails Gate 0.

Do not use host.joint_effort_for()

It is documented as “measured joint efforts” but returns block 4 of trajectory_data, which is the FIC controller's commanded control effort. Use joint_torque_for(), which reads the real topic.

Gate 4 — Characterise before you trust it

Two measurements are mandatory for a new arm. Neither is optional, and both belong in the run's meta.json.

  1. The noise floor, per joint. Hold a pose in Mode 1 with nobody touching the arm, calibrate, and record σ per joint. Repeat across about ten poses spanning the workspace. Thresholds are 6σ; if that lands above the controller's own admittance_deadbands.joint_tau, the per-pose bias is not buying you anything and you should say so rather than tuning until the demo looks good.
  2. The per-link detectability table. Different arms have wildly different moment arms. On the Kinova, the shoulder needs 69 N to be detected half the time — effectively never, by hand — while the wrist needs 3 N. You must know which links are usable on your arm before demonstrating it, or a correct “nothing detected” will look like a bug.

Generate the detectability table

python3 - <<'PY'
import numpy as np, mujoco, pinocchio as pin, sys
sys.path.insert(0, 'fic_ws/src/fic_contact')
from fic_contact.residual import ArmModel
URDF, MJCF = '<urdf>', '<scene.xml>'
JOINTS = ['<joint names in order>']
FLOOR  = 1.2          # N.m, your measured 6-sigma threshold
m  = ArmModel(URDF, JOINTS)
mj = mujoco.MjModel.from_xml_path(MJCF)
def surface(name, n=60):
    b = mujoco.mj_name2id(mj, mujoco.mjtObj.mjOBJ_BODY, name)
    g = mj.body_geomadr[b]; d = mj.geom_dataid[g]
    v = mj.mesh_vert[mj.mesh_vertadr[d]:mj.mesh_vertadr[d] + mj.mesh_vertnum[d]]
    R = np.zeros(9); mujoco.mju_quat2Mat(R, mj.geom_quat[g])
    return (mj.geom_pos[g] + v @ R.reshape(3, 3).T)[::max(1, len(v) // n)][:n]
def skew(r): return np.array([[0,-r[2],r[1]],[r[2],0,-r[0]],[-r[1],r[0],0]])
rng = np.random.default_rng(0)
for k, name in enumerate(m.link_names, 1):
    pts, need = surface(name), []
    for _ in range(150):
        q = rng.uniform(-2, 2, m.n); J = m.link_jacobians(q)[k]
        for r in pts[rng.integers(0, len(pts), 10)]:
            Jp = J[:3] - skew(r) @ J[3:]
            d = rng.normal(size=(10, 3)); d /= np.linalg.norm(d, axis=1, keepdims=True)
            need.extend(FLOOR / np.maximum(np.abs((Jp.T @ d.T).T).max(axis=1), 1e-9))
    need = np.array(need)
    print(f'{name:<24}{np.percentile(need,50):6.1f} N (50%)  {np.percentile(need,90):7.1f} N (90%)')
PY

Anything needing more than about 30 N at the 50% mark is not usable by hand. Put the resulting table in the docs for that robot, the way the Kinova's is on the Contact Localization page.

Gate 5 — Verification ladder

In this order. Do not skip upward.

  1. {rid}_joint_torques appears, updates at rate, and moves when you push the arm.
  2. Sign and gravity conventions confirmed at three poses: stationary and untouched, tau_meas − g(q) is small on every joint. If a joint shows a residual the size of its own gravity term, gravity_compensated or torque_sign is wrong.
  3. Noise floor measured per joint, across the workspace.
  4. Detectability table generated; usable links identified.
  5. Twin mirrors the arm's pose with the estimator disabled.
  6. Push each usable link in turn; the right body lights up.
  7. Full recorded run against a written contact-safety procedure.
A human deliberately touching a live arm needs its own procedure

The existing hardware verification protocol requires the workspace to be clear of people and treats unexpected motion toward a person as an abort criterion. Deliberate contact is outside it. Write a procedure for the new arm before Gate 5 step 6, covering Mode 1 enforcement, enabled safety zones, reduced torque limits, and a two-person rule with a second person at the E-stop.
