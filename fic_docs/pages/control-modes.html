Control Modes & FIC Algorithm

Control modes 0–8 powered by the Fractal Impedance Control library (0 = stop). Available in both simulation and hardware.

Gravity handling: in both controller nodes (fic_simulation and fic_hardware; on hardware not when the robot's gravity_compensated is set), Modes 1 and 2 add the model gravity torque g(q) on top of the FIC output (the impedance law itself has no gravity term); Modes 3/4 and Hapfic add it too, and Modes 3/4 also use it as the commanded effort against which the interaction torque is measured; Cartesian modes fold it in as τ = JTw + g(q). Mode 9 (Cartesian IK + joint impedance) was removed in v3.9.0 — a legacy enum entry remains in the code but the mode is no longer exposed in the GUI.

Hapfic overlay (Modes 6–8)

The Hapfic checkbox (in the Null-space row) activates a hybrid control path within Cartesian modes 6–8 (on 7 and 8 the host's task-space admittance first shifts the goal). When enabled, the Cartesian planner generates an EE trajectory, Cartesian impedance computes a task-space wrench, and the resulting joint torques (via JT) feed as desired effort into per-joint haptic admittance controllers. The admittance output modifies q_target and a joint impedance inner loop produces the final torques. Internally this calls RC.hapfic() instead of RC.admittance(). The Cartesian planner+impedance channels live at a dedicated offset (16–19) to avoid channel conflicts with the joint controllers at 0..nj−1. Both layers are tuned in Hapfic's own config.xml block, <mode id="100" name="HAP-FIC"> (a joint layer and a Cartesian layer); a robot without one runs on Mode 4's joints and Mode 6's Cartesian block. See the Hapfic page for the full architecture.

6-DOF compliance (v2.5.8+)

Modes 7 / 8 respond to both forces and torques. Translational pushes yield via the position pass on axes 0–2 (m, with a 4 N default deadband; the internal admittance offset is clamped to ±30 cm in Mode 7 / ±5 cm in Mode 8, and the resulting target to a ±10 m workspace box). Rotational torques yield via a second pass on axes 3–5 (rad, with a 0.2 Nm default deadband and ±30° / ±5° clamp). The orientation pass composes its axis-angle delta into the desired quaternion as a base-frame left-multiply, so torquing the EE the same way the user pushes rotates the target the same way. Pre-v2.5.8, only the translation pass ran and the orientation target passed straight through unchanged. Deadbands are per-robot: admittance_deadbands (joint_tau, cart_force, cart_torque) in fic_library/config/robots_config.yaml, defaults 1.5 Nm / 4.0 N / 0.2 Nm.

Postural null-space now runs in Modes 7 & 8

Earlier releases gated the Null-space → Postural toggle out of the Cartesian admittance modes because the admittance offset fought the postural correction. That gate has been removed: applyJointPosturalCorrection now ignores CartAdmMode and postural runs in all Cartesian modes (5–8). If you see stale “gated out” hints elsewhere, trust the code — see the changelog for the history.

{N} is the station ID (1–4; 100–999 for a Master station) set by the station_id node parameter — see Topics. The hardware hub accepts these exact strings: "Joint Impedance", "Joint Impedance With Planner", "Joint Admittance", "Joint Admittance Haptic", "Cartesian Impedance", "Cartesian Planner", "Cartesian Admittance", "Cartesian Admittance Haptic". "Stop Controller" or "Pause Controller" switch to Mode 0 with a graceful torque ramp-down (see Safety). Unknown strings are rejected with an error log. Hardware also accepts "Start", which launches the vendor robot driver from driver_command in the robot config.

Legged robots run Mode 1 only

A robot configured robot_category: legged also configures kinematics_solver: none, so the C++ node rejects the Cartesian modes outright and the GUI disables the four Cartesian mode buttons; a stale Cartesian selection falls back to Joint Impedance on the robot switch. Its joint targets are published by the fic_locomotion gait node, which also announces Mode 1 once at startup so a headless run works without the GUI. See Legged Locomotion.

What happens on a mode switch

Every mode change re-initialises the FIC controllers with that mode's parameters (read from config.xml in the background the first time the node needs them for this robot and mode; the loop sends no new command until they are in memory) and snaps the targets to the robot's current state: joint targets to q_current, and (for Modes 5–8) the EE target to the current EE pose. The robot therefore holds position after a switch instead of jumping to a stale target. Both controller nodes boot in Mode 1 until a mode message arrives.

FIC Algorithm Internals

The FIC<T> template class (in fic_library/include/fic/FIC.cpp) implements three nested component types per degree of freedom:

Controller

Pure position-error feedback using a nonlinear saturation mapping. Maps position error through configurable breakpoints (x_b) and force limits (E_max) with multiple saturation stages, producing a stiffness-scaled torque output.

ParameterDescription
K0Linear stiffness gain (separate values for negative / positive error)
x_bError breakpoints for saturation stages (error_max in XML)
E_maxForce limit per saturation stage (force_max in XML)
S_StartSaturation ratios — fraction of each breakpoint where the tanh blend begins (clamped to 0.4–0.9)
n_Number of saturation stages

Within each stage the profile is a linear region (K0 × error up to S_Start × x_b) followed by a smooth tanh blend up to the stage's force limit at x_b; beyond the outermost breakpoint the output is flat at the last E_max entry.

Divergence / convergence — the fractal attractor

The controller is state-dependent: it behaves differently depending on whether the error is growing or shrinking (compared per time step):

  • Divergence (|error| increasing): output follows the nonlinear profile above; the controller records the largest error and its effort as (error_max, effort_max).
  • Convergence (|error| decreasing): output switches to a linear spring anchored at the midpoint of the excursion: effort = K_conv × (error − error_max/2) with K_conv = |effort_max| / max(|error_max/2|, 1e-5). The force crosses zero at half the peak error, releasing the stored energy symmetrically. If the error crosses zero or starts growing again, error_max re-anchors.

This hysteresis is what makes FIC stable without velocity feedback: each divergence/convergence cycle returns the energy injected on the way out, so the closed loop is passive by construction.

No velocity damping in the Controller

The Controller class is purely position-based. damping_ratio only exists in the Planner (Modes 2, 6). Kv_ only exists in AdmittanceController (Modes 3, 4, 7, 8). If Mode 1 oscillates, the only lever is to reduce K0 (the convergence phase dissipates energy, but K0 sets how much gets injected).

Separately — and outside the FIC library — the simulation node subtracts an output damping term kd × qdot from the final torque, with kd = per-joint torque limit / max_joint_vel from the robot's safety_zones. It is fed from the raw feedback velocity through a dedicated first-order 20 Hz lag: a first-order lag can never exceed 90° of phase, so it can attenuate a damper but never invert it, whereas the 10 Hz second-order state filter reaches 159° at a lightly-loaded joint's resonance and would pump energy in instead of removing it.

Planner

Trajectory generator producing smooth position references via an acceleration-limited second-order model. Each step it computes an acceleration from the position error (with the same divergence/convergence hysteresis as the Controller), subtracts a velocity damping term 2·ζ·ωn·v, then Euler-integrates acceleration → velocity → position. The natural frequency ωn and the velocity/acceleration caps are re-derived from velDesired and the distance to the goal whenever the target moves, so short moves stay gentle and long moves reach full speed. Wrapping behaviour and joint limits are sourced from the robot config, not from per-mode tuning.

ParameterDescription
stiffnessInitial internal stiffness; recomputed as ωn² whenever the target moves
velDesiredTarget velocity (rad/s or m/s) — the main speed knob
accMaxMaximum acceleration ceiling
dampingRatioζ in the damping term 2·ζ·ωn·v; typical config value 0.005 — larger = more overshoot suppression
frequencyLoaded from XML but not used by the planning math — ωn is derived dynamically from velDesired / distance-to-goal
Planner degrades to pass-through at low rates

If the step time exceeds 5 ms (dt > 0.005), plan() skips the smooth integration and snaps the planned position straight to the desired target. The controller loop runs at 1 kHz, so this only bites if you call the library yourself at a lower rate — expect no trajectory shaping there.

Continuity & limits come from the URDF, not the mode

Whether a joint is treated as continuous (shortest-arc wrap across ±π) is derived at robot-load time by parsing the URDF directly with tinyxml2 (fic::deriveJointContinuityFromUrdf). A joint is continuous iff its <limit> element omits both lower and upper attributes, or if type="continuous". Clamp limits for bounded joints come from Pinocchio's lowerPositionLimit/upperPositionLimit; continuous joints use ±π as a placeholder (irrelevant, since they're never clamped). This correctly handles multi-turn bounded joints (e.g. ±720°) as non-continuous. ficControl::setJointContinuous() and setJointLimits() install these once per robot in loadRobotModel(), so all control modes — including Cartesian modes that skip initJointPlanner — see the correct values.

AdmittanceController

Integrates applied force over time for compliant motion:

acceleration = invM × (effort − Kv × velocity)

Euler integration of acceleration → velocity → position, all clamped to limits. When the integrated pose saturates against a bound, the velocity component driving into that bound is zeroed (anti-windup), so the offset settles at the wall and releases without snap-back.

ParameterDescription
InvMInverse virtual mass (higher = more responsive to forces)
KvVelocity damping (prevents runaway)
dFlowAcceleration limits [min, max]
FlowVelocity limits [min, max]
PosePosition offset limits [min, max] — at init these are overridden to the Controller's x_b breakpoints; the Cartesian admittance modes then re-clamp them per mode (±30 cm / ±5 cm, ±30° / ±5°)

M1 vs M2: both are driven by the interaction effort alone (commanded minus measured, outside the deadband): with nothing pushing, the offset does not move. In push-and-stay (m=1) the offset accumulates up to the joint limits (±30 cm / ±30° in task space), so the robot stays where you push it. In haptic mode (m=2) the offset is bounded to the joint law's outer breakpoint (±5 cm / ±5° in task space): within it the robot yields and stays, and pushed beyond it the FIC law resists and returns it to the bound on release.

Desired wrench (modes 7/8, and Hapfic on them): the task-space admittance is driven by the desired minus the measured wrench, outside the deadbands, so it moves the goal until the measured wrench equals the desired one, within the mode's bound. The desired wrench is zero when the controller starts, which is the plain compliant behaviour above. Set it with the Wrench… button in the Cart options, the Desired wrench row of the web interface's Cart panel, robot.mode.desired_wrench(force, torque) in the Script Editor, or the robot{N}_desired_wrench topic (geometry_msgs/Wrench, [N, N·m], in the frame and sign of the measured wrench). The topic is not latched, so a controller that restarts begins at zero again. In free space a non-zero desired wrench moves the goal to the bound, since nothing pushes back.

Control Wrapper — fic_control.h

The ficControl<T> class wraps FIC<T> and exposes two sub-modules:

JC — Joint Controller (Modes 1–4)

MethodModeDescription
JC.impedance(i, ...)1Pure FIC stiffness
JC.impedanceWithPlanner(i, ...)2FIC + trajectory planner
JC.admittance(i, ..., m)3/4Admittance (m=1 push-and-stay up to the joint limits, m=2 haptic: stays where released within ±xb,n)

The admittance target normally routes through the joint planner before the impedance inner loop. On hardware this is switchable at runtime via the Admittance Planner checkbox (Bool on robot{N}_admittance_planner_enable, default on); the simulation node currently always uses the planner path.

RC — Robot/Cartesian Controller (Modes 5–8)

MethodModeDescription
RC.impedance(...)5Task-space impedance via Jacobian transpose; orientation error is controlled as a scalar angle θ on channel 3 and projected back along the quaternion error axis
RC.planner(...)6Task-space with trajectory planning (plans XYZ; orientation target passes through to the impedance stage)
RC.admittance(..., m)7/8Task-space admittance — 6-DOF since v2.5.8 (translation + orientation; torques about EE x/y/z compose into the desired quaternion as a base-frame rotation delta). Driven by setDesiredWrench() minus the measured wrench; the desired wrench is zero by default.
RC.hapfic(...)6/7/8 + HapficHybrid: Cartesian planner → impedance wrench → JT joint torques → per-joint haptic admittance inner loop. Activated by the Hapfic checkbox.

FIC Channel Map

Every FIC component (controller / planner / admittance) is indexed by a channel. Joint modes use one channel per joint; Cartesian modes repurpose the low channels for EE axes and stack the helpers above them:

Null-Space Helpers (Cartesian modes only)

A 7-DOF arm running a 6-DOF Cartesian task has one redundant degree of freedom. The EE controller leaves that redundancy unconstrained — the arm can “swim” around a fixed EE pose. Two optional helpers on ficControl add secondary tasks in the null-space of the primary EE Jacobian, so the redundant motion is shaped without disturbing the EE.

Postural (ficControl::postural.apply())

Per-joint position controllers pushing each q_current[i] toward q_target_ik_[i] (the joint configuration the iterative IK solver produced for the current EE target). Uses its own FIC channels (offset 9 onward, past the Cartesian [0..5] and elbow [6..8] channels) so it doesn't fight the primary task.

  • Why you'd use it: on a 7-DOF arm, Cartesian Impedance/Planner (Modes 5/6) leaves the elbow swingable — gravity or contact can drift it to an awkward configuration. Postural pulls the whole arm toward the IK-preferred pose, so the elbow stays where IK put it.
  • When it runs: all Cartesian modes, 5–8. (Earlier releases gated it out of 7/8; applyJointPosturalCorrection now ignores CartAdmMode.) Joint modes (1–4) have no redundancy.
  • How to enable: tick Null-space → Postural in the Control panel. Publishes Bool on robot{N}_postural_enable.
  • Tuning: each robot has one <postural> block in config.xml (a sibling of the <mode> blocks, with its own <controller> stiffness / error_max / force_max and <planner> sub-blocks). Keep stiffness well below the primary Cartesian task so the secondary stays secondary.

Elbow (ficControl::applyElbowControl())

Holds the elbow link at a snapshot of its current Cartesian position. Computes a 3D position error on the elbow frame, maps to force via three FIC channels (offset 6..8), converts to torque with J_elbow.topRows(3).transpose(), then projects into the null-space of the primary EE Jacobian via N = I − J_EE+ J_EE (damped pseudo-inverse, λ = 0.01) so the resulting torque cannot disturb the EE pose.

  • Why you'd use it: precise elbow placement matters around obstacles, cables, or an operator's head. Postural anchors the whole arm; Elbow anchors just the elbow link and leaves the rest of the null-space free to flow.
  • When it runs: Modes 5–8 (all Cartesian modes). Independent of CartAdmMode.
  • How to enable: tick Null-space → Elbow in the Control panel. Publishes Bool on robot{N}_elbow_enable. On enable, elbowEnableCallback captures the current elbow pose as the target — pose the arm how you want the elbow before ticking the box. The target stays frozen while the toggle is on, even across new EE commands; IK refreshes the stored target only while the toggle is off.
  • Tuning: the elbow helper reuses the Cartesian translational (pos_axes) parameters from the mode's <cartesian> block. Some robots have an <elbow> block in config.xml — it is currently not read by the C++ parameter loader, so editing it has no effect.
  • Which link is the elbow: the elbow_frame_name key in robots_config.yaml (see Robot Config).

Hapfic (ficControl::RC.hapfic())

A hybrid overlay for Cartesian modes (6–8) that routes the Cartesian control output through per-joint haptic admittance before producing final torques. Instead of the normal Cartesian planner/admittance path, Hapfic uses its own Cartesian planner to generate a smooth EE trajectory, computes a Cartesian impedance wrench, converts it to joint torques via JT × wrench + gravity, then feeds those torques as τdes into handleJointAdmitanceControl(i, ..., τdes[i], τmeas[i], 2) per joint. Its deadband has hysteresis: a joint starts yielding when its gap τdes − τmeas reaches the deadband b (joint_tau) and keeps yielding until the gap is below b/4, so a held contact ends within b/4 of the desired torque. Each joint's IK set-point is first limited to within max(xb,n, 0.1 rad) of the measured joint, and the admittance offset is added to it (q_adm = sat(limit(q_ik) + δ)); a joint impedance inner loop produces the final torques.

  • Why you'd use it: compliant teleop with Cartesian trajectory planning. The EE follows a planned Cartesian path while the joints remain force-responsive through the haptic admittance layer — combining the precision of Cartesian planning with the compliance of joint-space haptic admittance.
  • When it runs: Modes 6, 7, and 8 (Cartesian Planner & Cartesian Admittance), when the Hapfic checkbox is ticked. When disabled, the normal RC.planner() (mode 6) or RC.admittance() (modes 7/8) path runs as before.
  • Host mode: the dispatcher forwards the outer CartAdmMode (0 for Mode 6, 1/2 for Modes 7/8). On Modes 7 and 8 the host's task-space admittance (M1 push-and-stay within ±30 cm / ±30°, M2 within ±5 cm / ±5°), driven by the estimated external wrench, shifts Hapfic's Cartesian goal and, to first order (J#Δx), its IK set-point; on Mode 6 the goal is used as commanded. The per-joint inner loop always runs in haptic mode (m=2).
  • How to enable: tick Null-space → Hapfic in the Control panel. Publishes Bool on robot{N}_hapfic_enable. Toggling re-initialises the controllers (both layers from the HAP-FIC block, see Tuning below); a repeated message with the value already set is ignored.
  • Channel allocation: joint controllers occupy channels 0..nj−1 (same as Modes 1–4). The Cartesian planner + impedance for the hapfic path lives at a dedicated offset (channels 16–18 for translation, 19 for orientation θ) to avoid collisions with the joint channels.
  • Tuning: Hapfic has its own XML block, <mode id="100" name="HAP-FIC">: its <joint> elements tune the joint layer and its <cartesian> element the Cartesian layer (fic::tuningKeyFor). A robot without the block falls back to the Mode 4 joints and the Mode 6 Cartesian block. Full details on the Hapfic page.
Postural vs. Elbow — which to use

Postural = “arm follows IK-preferred config”. Most users want this on by default in Cartesian modes.

Elbow = “elbow stays here, rest of the arm is free”. Use on top of a Cartesian task when you need deterministic elbow placement without over-constraining the joints.

They compose — you can enable both. Postural's softer whole-arm pull plus Elbow's sharper link-level hold tends to feel stable without locking up the null-space.

Parameter Loading

FIC parameters are loaded from fic_library/config/config.xml via fic_param_loader.hpp (C++) or xml_manager.py (Python/GUI). Parameters are per robot, per mode, per profile (the profile attribute on each <mode> block; the active profile is selected on robot{N}_active_profile — see Tuning).

All loading is fail-safe: missing XML tags retain defaults. No exceptions on missing tags.

Controllers read the installed copy

At runtime the C++ nodes read config.xml from the package share directory (e.g. <install>/fic_simulation/share/fic_simulation/config/config.xml), which CMake installs from fic_library/config/ at build time. If you hand-edit the source file, rebuild (or use a symlink install) so the controller sees the change — or edit through the GUI's config editor, which manages this for you.

When the nodes read config.xml (v4.4.0)

Both nodes read the whole tuning for the current robot and mode (every joint, the Cartesian axes and, in Modes 5–8, the postural block) into one in-memory set (fic::TuningSet), on a background thread. They read it again only when what the set is for changes — robot, joint count, mode, or a Hapfic toggle that changes the mode the parameters come from — or when the tuning on disk changes (robot{N}_param_update, sent on every SAVE TO XML, or a new robot{N}_active_profile). On a save or profile change the controllers keep the old set until the new one is ready and switch on the next tick. A new target only re-seeds the controllers from the set in memory; it never reads the file. The Postural/Elbow toggles trigger neither. See config.xml.

Signal Filtering

Joint feedback passes through second-order Butterworth low-pass filters (butterworth_filter.hpp, bilinear-transform coefficients, Direct Form II Transposed):

ButterworthFilter filter(cutoff_hz, sample_rate_hz, initial_value);
double filtered = filter.filter(raw_value);

The simulation node filters joint position, velocity, and effort at a 10 Hz cutoff before they reach the control law. The initial_value seeds the filter history to avoid startup transients.

The sample rate is measured, not assumed. These filters are stepped once per joint_states message, not by the 1 kHz control timer, and the bilinear transform derives its coefficients from the declared rate — so the previous hard-coded 1 kHz was realising the 10 Hz design cutoff at 1.4–1.7 Hz. The node now measures the feedback interval over a 50-sample warm-up window, takes the median, guards it (plausible range plus a periodicity test), and rebuilds the filter banks once, seeded for a bumpless transfer. If a rate cannot be established it falls back to 1000 Hz — the historical behaviour — with a WARN naming the reason.
