config.xml Reference

Location: fic_library/config/config.xml

Overview

This file stores all FIC tuning parameters, organised per robot, per control mode (1–8), per tuning profile, and per joint (or Cartesian axis). It is read by fic_param_loader.hpp (C++ controller) when the robot or mode needs a new tuning set and whenever the tuning on disk changes, and by xml_manager.py (Python GUI) for live editing. The file currently contains an entry for each robot: KinovaGen3_7DOF, Franka_FR3, IIWA_14, Pendulum. The robot-description file robots_config.yaml lives in the same directory (see Robot Config).

Which copy do the nodes read?

The C++ nodes do not read fic_library/config/config.xml directly. Both fic_control.cpp and fic_control.cpp resolve the path via the installed package share directory:

get_package_share_directory("fic_control") + "/config/config.xml"

fic_control's CMakeLists installs fic_library/config/ into share/fic_control/. With colcon build --symlink-install the installed copy is a symlink back to the source file, so edits take effect on the next reload; with a plain colcon build you must rebuild fic_control for edits to be seen by the controller. The Python GUI always edits the source file in fic_library/config/ (resolved by find_config_path()).

Profiles — named tuning sets

Every control-mode block carries a profile="..." attribute. Profiles let you store multiple named tuning variants for the same mode (e.g. default, Stiff, Gentle) and swap between them at runtime. Profiles are robot-scoped: the name Stiff is a robot-wide label that may have concrete per-mode overrides for some modes and fall back to default for others.

Uniform <mode> Schema

Every tuning entry under a robot is a <mode> element with three attributes:

AttributeTypeDescription
idint 1–8Control mode index (see Control Modes page)
namestringHuman-readable mode name (e.g. "Joint Impedance")
profilestringTuning profile name. "default" always exists; others are user-created. A missing attribute is treated as "default"

The name attributes used in the shipped file match the GUI's mode table (CONTROL_MODES in xml_manager.py; see Control Modes):

idname attributeidname attribute
1Joint Impedance5Cartesian Impedance
2Joint Impedance With Planner6Cartesian Impedance with Planner
3Joint Admittance7Cartesian Admittance
4Joint HAP-FIC8Cartesian HAP-FIC

Mode 0 (Idle) has no tuning entry. Joint elements use zero-based ids (<joint id="0"> … id="6" for a 7-DOF arm). Only the id attribute is used for matching — the loader ignores name.

    <elbow>
      <controller>...</controller>
    </elbow>

  </robot>
</robots>
What the planner reads

The planner's motion is set by vel_desired (how fast it moves toward the goal) and damping_ratio, and since v5.11.0 acc_max caps its acceleration (0: no cap; the shipped 5000 is never reached, so the shipped profiles move as before). Its stiffness and frequency are read but have no effect: the planner derives its stiffness from the desired speed and the distance left each time the goal moves. The cap on that natural frequency (8.75 Hz) and the speed margin (1.5708) are per robot, in robots_config.yaml fic_law. A mode with no <planner> block gets vel_desired = 0: in the admittance modes (3 and 4, with the planner on) the target then cannot move and the joint does not yield to a push.

The <postural> and <elbow> blocks configure the null-space helper toggles available in Cartesian modes (see Control Modes and H-PMP). They sit directly under <robot> — they are not per-mode and not per-profile; a single block is shared by every Cartesian mode that invokes the task.

Profile Resolution & Fallback

At runtime, the controller resolves (robot, mode, profile) as follows:

  1. Search for a <mode> with exactly matching id and profile. If found, use it.
  2. Otherwise fall back to the <mode> with the same id and profile="default" (implemented by findModeElement() in fic_param_loader.hpp).
  3. If even the default is missing, use the loader's built-in safe defaults (no segfault).

H-PMP has a block of its own, <mode id="100" name="H-PMP">: its joint layer in <joint> and its Cartesian layer in <cartesian>. Id 100 is not a control mode; both nodes read it whenever H-PMP is on in modes 5–8 (fic::tuningKeyFor), resolving the profile as above. A robot with no H-PMP block at all runs H-PMP on mode 4’s joints and mode 6’s Cartesian block, as before the block existed.

This means a profile like Gentle only needs concrete blocks for the modes you want to customise; other modes transparently inherit the default tuning. The GUI shows a (fallback → default) indicator next to any profile that falls back for the currently selected mode.

The loader injects its safe memory defaults before parsing the XML, then overwrites whatever it finds, so a partially-populated block is fine — missing elements silently keep the defaults. When a mode block or the whole file is missing entirely, the loader logs to stderr and keeps the memory defaults:

[fic] config.xml load FAILED at <path> — planner will use defaults (vel_desired=0)
[fic] no <mode id="N" profile="P"> for robot <name> — planner defaults (vel_desired=0)
Symptom: joints sag under gravity

A failed config load leaves vel_desired = 0 in the planner, which historically manifested as joints slowly sagging under gravity in planner modes. If you see that, check the node's console output (Logs) for the [fic] error lines above.

Data Flow

The GUI edits the source file; the controller nodes read the installed copy. Since v4.4.0 they read the whole tuning for the current robot and mode once and keep it in memory; they read it again only when the robot, joint count or mode changes, or when the tuning on disk changes (a robot<N>_param_update message, sent on every SAVE TO XML, or a profile change). See When the Nodes Read the File below.

When the Nodes Read the File

Reading config.xml parses the file once per joint plus a Cartesian pass; one read measured about 29 ms on the lab PC, against a 1 ms control tick. Both nodes therefore read the tuning into one in-memory set (fic::TuningSet, built by fic::loadTuningSet() in fic_param_loader.hpp) holding every joint, the Cartesian axes and, where needed, the <postural> block. The set is labelled with what it was read for (fic::TuningKey): robot, joint count, the mode the joint parameters come from, the mode the Cartesian parameters come from, and whether the postural block is included.

EventWhat the node does
Mode change, robot selection, joint-count change, H-PMP on/off where it changes the mode the parameters come fromThe key changes, so a new set is read. Until it is in memory the control loop returns early and sends no new command; then the controllers start on it.
robot<N>_param_update (any payload)The set is read again with the same key. The controllers keep running on the old set until the new one is ready, then switch to it on the next tick.
robot<N>_active_profile with a different nameAs param_update, with the new profile.
A new joint or Cartesian targetNo read. Where a joint target re-seeds the controllers (robot<N>_target_joint_angles in fic_control outside mode 1; robot<N>_desired_joint_angles in mode 2, or in the other modes except 1 while the admittance planner is on) they re-seed from the set already in memory, which takes microseconds. A Cartesian target does not re-seed them.
A robot<N>_hpmp_enable repeating the current valueIgnored.

The read runs on a background thread (std::async), so the 1 ms loop never waits on the file. A finished read that no longer matches what the loop wants (the mode or robot changed while it ran) is dropped and the read is started again for the new key. A read that fails (an exception from the loader, logged as Init Failed) is not retried every tick: the node tries again on the next change of key, param_update or profile. Each installed set is logged as Controllers Initialized … (tuning read from config.xml).

Before v4.4.0

The nodes re-read the file inside the control loop whenever initControllerPLanner was cleared, and outside Joint Impedance (mode 1) a streamed joint target cleared it (on robot<N>_target_joint_angles, which only the simulation target takes, in every such mode; on robot<N>_desired_joint_angles, in both nodes, in mode 2 and in the other modes while the admittance planner is on), as did every hpmp_enable message even with an unchanged value. In MuJoCo, with targets streamed at 100 Hz, the FIC loop fell from 1000 Hz to 74 Hz in mode 2 and 65 Hz in mode 3; hpmp_enable re-sent at 20 Hz brought it to 405 Hz. With the tuning set all of these run at 1000 Hz, including a tuning save while targets stream.

Parameter Reference

Three Sub-Blocks per Joint / Per-Axis

Each <joint> and each Cartesian axis (<x>/<y>/<z>/<q>) — and the robot-scoped <postural> — groups its parameters into up to three sibling sub-blocks, each owned by a runtime sub-system:

Sub-blockPresent inConsumed by
<controller>every mode, postural, elbowFIC inner loop (saturation mapping, force limits)
<planner>Modes 2, 6, 7, 8 (edited by the GUI); postural (round-trip only)Trajectory planner (smooths target before the inner loop)
<admittance>Modes 3, 4, 7, 8Virtual admittance (converts force to motion)

The GUI's CONTROL_MODES table drives which sub-blocks are shown per mode (planner for 2/6/7/8, admittance for 3/4/7/8). The shipped file also carries <planner> blocks under joint-admittance modes 3/4 for some robots; the C++ loader reads any sub-block it finds regardless of mode, so those values are loaded if present. The postural <planner> block is written so existing configs round-trip, but the runtime postural path only consumes the controller parameters.

Prior to v2.5.3 the <controller> fields were direct children of the parent block. Loaders retain a legacy fallback so un-migrated files still load, but all new tooling writes the nested form.

<controller> Sub-Element

XML ElementTypeDescription
<stiffness>floatLinear spring constant K0 (N/m or Nm/rad)
<diff_effort_max>floatRead by the loader, but no controller uses it. Kept so existing files and tools load; not on the Tuning pages, and a save keeps the stored value.
<error_max>float,float,…Saturation breakpoints xb1,xb2,… (rad or m)
<force_max>float,float,…Force values f1,f2,… at breakpoints (N or Nm)
<saturation_ratios>float[]Blend factors per segment (higher = more linear)
<velocity>floatNominal velocity (joint blocks; present in planner modes and postural)
<n_saturations>intNumber of saturation stages the FIC mapping uses (loader default 4; GUI range 2–8)
<asymmetric>boolIf true, separate positive/negative saturation layouts (default false; accepts true/1/yes)
<n_neg_sat>intNegative-side stage count when asymmetric=true (loader default 2; GUI range 1–4; ignored otherwise)

XMLManager API (Python)

The GUI uses xml_manager.py to read and write config.xml. Every load/save method accepts an optional profile="default" argument:

save_joint_params(robot, joint, mode, params, profile="default")Save parameters into a specific profile — creates the <mode> block if it doesn't exist yet
load_cartesian_params(robot, mode, profile="default")Load all four Cartesian axes
save_cartesian_axis(robot, mode, axis, params, profile="default")Save one Cartesian axis
get_all_profiles(robot)Union of profile names across every mode for the robot. Use this for UI selectors.
get_available_profiles(robot, mode)Profiles that have a concrete block for this mode (used to compute the fallback indicator)
clone_profile(robot, mode, src, dst)Create a new <mode id=N profile=dst> by cloning from (mode, src)

XMLManager() locates the file via find_config_path(), which prefers fic_library/config/config.xml relative to the source tree; pass config_path= to override.

C++ Loader API

fic_param_loader.hpp exposes two functions that both accept a profile_name argument (default "default"):

fic::ParameterLoader::loadJointParams(
    xml_file, robot_name, joint_id,
    scalars, lists, planner, admittance,
    control_mode = 1, is_postural = false,
    profile_name = "default");

fic::ParameterLoader::loadCartesianParams(
    xml_file, robot_name,
    cart_params,
    control_mode = 5,
    profile_name = "default");

Internally, findModeElement(robot, mode, profile) iterates <mode> children and falls back to default automatically if the requested profile isn't present. For is_postural = true the mode/profile arguments are ignored and the loader reads the robot-scoped <postural> block directly (it also accepts a legacy capitalised <Postural> tag). Both loaders retain a pre-v2.5.3 fallback: if a joint or axis block has no <controller> child, controller fields are read as direct children of the block itself.

Runtime Profile Switching

fic_control subscribe to a station-scoped String topic:

robot<N>_active_profile   (std_msgs/String)

where <N> is the station id (see Topics). An empty string is treated as "default"; a message that matches the current profile is ignored. When the profile actually changes, the node updates its internal active_profile_:

  • Both nodes then read the tuning again with the new profile, in the background, and switch the controllers to it when it is ready (see When the Nodes Read the File). The controllers run on the old profile until then.
  • fic_control subscribes reliable and transient-local (as the GUI and the experiment runner publish it), on both targets, so a profile chosen before the node started is still received.

Both nodes log Active tuning profile: <name> on change. The GUI publishes to this topic whenever the user changes the Config dropdown in the Tuning panel or a Control Panel robot card (extra cards publish to their own robot<N>_active_profile), and after adding or deleting a profile.

H-PMP loads its own tuning

When the H-PMP helper is active (modes 5–8), both nodes load its joint and Cartesian parameters from the H-PMP block, <mode id="100">, of the active profile, whichever Cartesian mode is selected (fic::tuningKeyFor keys both layers to 100). A robot without a H-PMP block falls back to the mode 4 joints and the mode 6 Cartesian block. Tune the H-PMP block (H-PMP at the end of the Tuning panel's Mode list) to affect H-PMP behaviour.

Manual Editing

# Edit the source file (path relative to the repository root)
nano fic_library/config/config.xml

# Tell the running node the file changed (sim and hardware; the payload is only logged)
ros2 topic pub --once /robot1_param_update std_msgs/String "data: robot1:manual:0"

# Or switch profile: a DIFFERENT name forces a read (a message equal to the
# current profile is ignored)
ros2 topic pub --once /robot1_active_profile std_msgs/String "data: Gentle"
ros2 topic pub --once /robot1_active_profile std_msgs/String "data: default"

Both nodes read the file again on either message. If your workspace was not built with --symlink-install, rebuild fic_control so the installed copy under share/fic_control/config/ picks up your edits (see Build Tools).

Validation

The GUI validates parameter ranges before saving. If you edit the XML manually, ensure values stay within the ranges documented in the Manual Tuning page. Invalid values may cause the controller to behave unpredictably. Malformed numeric list entries (e.g. a stray letter in error_max) are silently skipped by the C++ loader, which can shorten the breakpoint list without warning — keep lists comma-separated numbers only, with error_max and force_max the same length.
