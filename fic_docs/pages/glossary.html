Glossary

Plain-English definitions for the terms you'll see across the FIC Control Studio docs, XML configs, and code.

New to impedance control?

Read the Control Modes & FIC Algorithm page alongside this glossary — the terms here are cross-referenced throughout it.

Core concepts

FIC — Fractal Impedance Control

The nonlinear impedance control algorithm at the heart of this project. Instead of a single linear spring τ = K·e, FIC maps position error through several saturation stages with progressively capped force, so a small error feels stiff while a large error is force-limited — robust against contact and without the overshoot of a high-gain PD controller. The controller also distinguishes a divergence phase (error growing — force follows the nonlinear profile) from a convergence phase (error shrinking — force is released along a virtual spring anchored at half the peak error), which keeps it stable without an explicit damping term. Implemented in fic_library/include/fic/FIC.cpp.

Impedance vs. Admittance

  • Impedance control — you set a position target, the controller outputs torque. The robot behaves like a spring anchored at your target. This is Modes 1, 2, 5, 6.
  • Admittance control — the controller isolates the external force (measured minus expected), integrates it through a virtual mass/damper, and shifts the position target accordingly. The robot "yields" to pushes. This is Modes 3, 4, 7, 8.

Push-and-stay vs. haptic admittance (M1 / M2)

Each admittance mode comes in two variants, selected by the mode number:

  • M1 — push-and-stay (Modes 3 & 7). No virtual spring: each push is accumulated into a persistent offset on the target, so the arm stays where you left it. Used for hand-guiding, e.g. by Teach Mode.
  • M2 — haptic (Modes 4 & 8). Also driven by the push alone, with no virtual spring, but the offset is bounded: the arm follows a push and stays where you release it within the bound (Mode 4: the joint law's outer breakpoint ±xb,n, ±0.2 rad by default; Mode 8: ±5 cm / ±5°). Pushed beyond it, the FIC law (the joint's own in Mode 4, the Cartesian law in Mode 8) resists and returns it to the bound on release. This is the variant used for bilateral teleoperation force feedback.

Both variants read the same estimated external wrench (or external joint torque); only the target-update rule differs. In the code this is AdmMode_ / CartAdmMode = 1 or 2 in fic_control.h.

Joint space vs. Cartesian / Task space

  • Joint space — commands and errors in joint angles [q₁, q₂, …, qₙ]. Modes 1–4.
  • Cartesian / task space — commands and errors on the end-effector pose [x, y, z] + quaternion orientation. Modes 5–8 (torque is produced from a Cartesian wrench via Jᵀ).

Jacobian (J) & Jᵀ

Linear map between joint velocities and end-effector velocity. FIC's Cartesian modes compute a desired wrench in task space and project it back into joint torques through the Jacobian transpose: τ = Jᵀ · F_desired. The model is built from the robot's URDF by Pinocchio (pinocchio::computeFrameJacobian), which also supplies joint limits and gravity torques.

Wrench

A 6-vector of force + torque [Fx, Fy, Fz, Tx, Ty, Tz] (geometry_msgs/Wrench). The Cartesian admittance modes consume the measured external wrench alone (no gravity reference). Both controller nodes estimate it from the joint torques, pinv(Jᵀ)(τ_meas − g(q)), unless the robot's wrench_from_api is true; then it comes from the vendor driver on hardware and from the robot{sid}_simulation/force_torque sensor topic in simulation. If the message carries no torque components, orientation admittance is silently skipped.

Null-space

On a 7-DOF arm with a 6-DOF end-effector task there is one redundant direction of joint motion that does not move the EE — the arm can "swim" around a fixed EE pose. Secondary tasks (postural, elbow) act in this null space: their torque is projected through N = I − J⁺J (damped pseudo-inverse) so they never disturb the primary EE task. The toggles live in the Null-space: row of the Control panel.

Gravity compensation

The controller adds the model's gravity torques (gravity_torques, computed by Pinocchio from the URDF) to its output, so the FIC springs act around a weightless equilibrium. In admittance modes the same term is used as the expected effort when isolating what the human is applying.

FIC algorithm terms

Saturation stage

FIC's error-to-force curve is piecewise: linear up to a fraction (saturation_ratios) of the first breakpoint, then a smooth tanh blend up to the first force ceiling at x_b[1], then another blend up to the next ceiling at x_b[2], and so on. Each piece is a "saturation stage". n_saturations counts the total number of stages (negative + positive sides).

x_b — error breakpoints

Position-error values (rad for joints, m for translation, rad for the orientation channel) at which FIC reaches the next force ceiling. Set directly from the <error_max> list in config.xml — one value per stage. For symmetric configurations you list only the positive side; the negative side is mirrored automatically.

E_max — force limit per stage

The maximum torque / force each saturation stage can command (called E_s in FIC.cpp). Set directly from the <force_max> list — one value per stage, matched index-for-index with error_max. Beyond the last breakpoint the output is clamped at the last E_max, which is what makes FIC intrinsically force-bounded.

saturation_ratios (S_Start)

Per-stage fraction (clamped to 0.4–0.9 in code) of the breakpoint distance at which the smooth tanh blend begins. Higher values keep the response linear longer before saturating; lower values start the roll-off earlier. Edited as sr handles on the Tuning canvas.

K0 — base stiffness

Slope of the linear region — the gain you feel for small errors. Larger K0 → "stiffer" robot. Loaded from the single <stiffness> value inside each <controller> block of config.xml (per robot, per mode, per profile, per joint or Cartesian axis) and applied to both error directions. See config.xml reference.

Asymmetric saturation / n_neg_sat

By default FIC saturates symmetrically (same curve left and right of zero). Setting <asymmetric>true</asymmetric> splits the curve so the negative side has n_neg_sat stages and the positive side gets the rest; the error_max/force_max lists must then cover all n_saturations stages explicitly. Useful for joints with uneven physical travel.

Wrapping (wrapToPi)

Folding a joint angle into [-π, π]. Harmless on continuous joints but destructive on bounded joints whose legal range extends past π (e.g. Franka fr3_joint6). FIC only wraps joints flagged continuous — derived at robot-load time by parsing the URDF (type="continuous", or no position limits) — see the v2.5.1 changelog entry. Bounded joints are clamped to their URDF limits instead.

Planner

Smooth trajectory generator that sits between your command target and the FIC controller in Modes 2 & 6, producing a time-parametrised ramp so you never command a step. Tuned via <planner><vel_desired>, <acc_max> and <damping_ratio>. The same planner also smooths the shifted target inside the admittance modes: always in Cartesian admittance (7/8), and optionally in joint admittance (3/4) via the Admittance Planner checkbox in the Control panel (disable it for teleop / streaming targets to avoid planner resets).

Damping ratio (ζ) vs. Kv

  • damping_ratio — planner parameter (<planner><damping_ratio>), a velocity-damping term tied to the ramp the planner is producing.
  • Kv (admittance modes 3, 4, 7, 8) — explicit virtual-damper coefficient on the admittance state, loaded from <admittance><Damping>. Its sibling <InvM> is the inverse virtual mass — larger InvM means a lighter-feeling arm.

Deadband

Threshold below which the estimated external effort is treated as zero, so sensor noise and residual gravity-model bias don't make the admittance integrator drift. Three per-robot values, configured under admittance_deadbands in robots_config.yaml (editable in Robot Config): joint_tau (default 1.5 Nm), cart_force (4.0 N), cart_torque (0.2 Nm). If your robot drifts in admittance with an unregistered tool on the flange, widen these (or register the tool's mass with the driver).

Workspace clamp

Bounds on how far admittance can shift the Cartesian target: push-and-stay (Mode 7) accumulates at most ±30 cm translation and ±30° rotation; haptic (Mode 8) allows a ±5 cm / ±5° live spring deflection. An anti-windup rule refuses steps that would push past a bound, so the target settles at the wall instead of winding up behind it. Separate from these, the June 2026 safety remediation added enforced joint and Cartesian safety zones.

Postural null-space

Adds per-joint FIC springs toward the IK-preferred configuration (q_target_ik_) in the redundant direction, stabilising the arm's shape while the EE task runs. Runs in all Cartesian modes, including admittance (7/8). Enabled via the Postural checkbox in the Null-space row of the Control panel; tuned under the robot-level <postural> block in config.xml. Uses its own FIC channels (offset 9+) so it never fights the joint-mode controllers.

Elbow null-space

Same idea as postural but anchors only the elbow link's Cartesian position (3 linear FIC channels, indices 6–8), leaving the rest of the null-space free. The elbow torque is projected through N = I − J⁺J so the EE task is untouched. Enabled via the Elbow checkbox; the current elbow position is snapshotted as the hold target at the moment you tick the box.

H-PMP

Hybrid helper layered on the Cartesian modes: a Cartesian planner + impedance loop computes the desired wrench, projects it to joint torques via Jᵀ, and feeds those as the desired effort into per-joint haptic admittance — Cartesian precision with joint-space compliance. Toggled by the H-PMP checkbox in the Null-space row; the controller engages it on Modes 6/7/8. It uses dedicated FIC channels (offset 16+) and loads its joint and Cartesian layers from its own XML block, <mode id="100" name="H-PMP"> (Mode 4's joints and Mode 6's Cartesian block on a robot without one). Full detail on the H-PMP page.

Workspace / infrastructure terms

Station ID

Which robot a Studio drives when several FIC stations share a DDS domain: Robot 1–35 (station 1–35, topics robot{N}_*), or Master (setting 0; each Master runs on its own station 100–999 taken from the PC name) — the control seat for a PC with no arm of its own, whose simulations can never reach a real arm. Switched from the Robot selector in the main toolbar (persisted as general.station_id in Settings; changing it restarts the GUI so every subscription re-points). Every machine takes its own station; the Multi-Robot page warns when two claim the same one.

Master station

Station 0, shown as Master: the Studio at a lab's control seat. It sees every Studio on the network, can E-STOP ALL and pair any two stations for teleoperation, and runs its own simulations on topics of its own. Several PCs can be Master at once. See Multi-Robot.

Shared memory bridge

On hardware, FIC talks to the vendor driver (libfranka / Kortex) through POSIX shared-memory segments (/dev/shm/robot_feedback_memory) instead of ROS topics, so the control loop runs at 1 kHz without DDS serialisation overhead. Feedback and torque commands are lock-free atomic floats. See Simulation vs. Hardware for the full rationale.

rid / robot ID

String prefix used to namespace per-robot topics, e.g. robot1, robot2 — derived from the station ID (robot{N}). The simulation node additionally prefixes its own topics as robot{sid}_simulation/. See the Topics reference.

Driver / API / vendor driver

The manufacturer-SDK program that exchanges commands and feedback with the physical robot over the shared-memory bridge: a libfranka-based torque bridge for Franka (default driver_command runs robot_library/libfranka/build/examples/cartesian_impedance_control 172.16.0.2) and a Kortex-based bridge for Kinova (robot_library/Kinova/api_cpp/…/01-torque-control_00-Torque_Controller). The exact command is per-robot, editable in Robot Config → Driver command, and started/stopped from the GUI via the ▶ API button; its stdout is streamed into the log panel.

Profile

Named tuning set for a control mode. Every <mode> block in config.xml carries a profile="..." attribute; "default" always exists, and you can save alternates (e.g. a gentler stiffness set) without losing your baseline. Selected per mode from the Config: dropdown in the Control panel; if a requested profile doesn't exist for a mode, the loader falls back to default. See config.xml.

robots_config.yaml

Robot-description file generated by the GUI (fic_library/config/robots_config.yaml) and read by both control nodes at robot load: URDF path, joint count, per-joint torque limits, admittance deadbands, driver/build commands. Distinct from config.xml, which holds the per-mode FIC tuning. Edited via Robot Config.

Teach mode

Guide-and-record: the robot is switched into an admittance mode — Joint Admittance (Mode 3) or Cartesian Admittance (Mode 7) depending on the teaching space — so you can move it by hand while the panel records waypoints and gripper steps; stopping the session switches to the matching planner mode. Started from the Teach Mode panel.

E-STOP

The red E-STOP button in the main toolbar (shortcut: Space). Since the June 2026 safety remediation it triggers a graceful torque ramp-down rather than an instant zero-torque cut, and fans out to every loaded extension so recordings and sequences halt too. Details on the E-STOP and Safety pages.
