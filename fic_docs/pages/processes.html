Process Management

Starting, stopping, and monitoring background processes from the GUI.

Overview

FIC Control Studio manages several background processes — the physics simulator (MuJoCo or Newton backend), the FIC controllers (simulation and hardware variants), the vendor robot driver, the VR relay, bag recorders, and the plotter. All of them are spawned as OS subprocesses by fic_studio/mixins/process_mixin.py; the GUI is the single owner of their lifecycle. Status is shown via LED indicators in the status bar.

Launch Toolbar

The toolbar uses a target selector plus a single Start/Stop button instead of one button per process. Pick a target (Simulation, Hardware, or VR), then press ▶ Start. While a session is running the target segments, the station selector (Robot 1–4), and the robot dropdown are locked, and the button turns into a red ■ Stop.

TargetWhat Start launchesStop behaviour
SimulationSimulator (mujoco_native or mujoco_newton package) + gripper bridge, then the FIC simulation controller 2 s laterStops FIC controller, then force-kills the simulator
HardwareVendor robot driver (from driver_command), then the FIC hardware controller 2 s later. If the driver fails to start, the controller is not launchedStops controller, then driver
VRVR relay node; FIC controllers are spawned automatically per robot once the headset publishes /vr/scene_configKills relay and all VR FIC controllers

Utility buttons sit next to the launch cluster: EXP (quick experiment recording — only visible when the Experiments extension is enabled), BAG (manual rosbag record), PLT (plotter), and VIEW (toggles the contact localization twin viewer — visible only while the control target is Hardware, since mirroring the real arm's measured pose only makes sense while driving it). Running buttons show a red ■; idle buttons show ▶ in their category accent colour. The red ⬛ E-STOP button is always on the right — see E-STOP.

Start order matters for manual toggles

When starting processes individually, launch the data source first: simulator before the FIC simulation controller (the controller reads joint states from the simulation topics), and driver before the FIC hardware controller. The Start button and F7 enforce this automatically with a 2 s stagger. BAG and PLT can start at any time.

Process Launch Commands

These are the exact commands the GUI executes (all wrapped in bash -c "source .../install/setup.bash && exec ..."). Use them in a terminal for manual control or debugging. <sid> is the station id from the toolbar's Robot N selector (topics are prefixed robot<sid>_, simulation topics robot<sid>_simulation/).

Simulator

source ~/FIC_Interface/fic_ws/install/setup.bash
ros2 launch mujoco_native simulation_launch.py robot_name:=Franka_FR3 station_id:=1 model_file:=<scene>

When Settings → Simulation → Backend is set to newton, the GUI launches ros2 launch mujoco_newton simulation_launch.py ... instead. If the mujoco_newton package has not been built (fic_ws/install/mujoco_newton missing), it logs a warning and falls back to the CPU simulator. Alongside the simulator the GUI also spawns Extensions/mujoco_playground/gripper_bridge.py, which translates the robot<sid>_gripper_width topic into robot<sid>_simulation/actuators_cmds for the gripper actuator (harmless on robots without one).

FIC Simulation Controller

ros2 launch fic_simulation fic_launch.py robot_name:=Franka_FR3 num_joints:=7 \
    station_id:=1 source_prefix:=robot1_simulation

source_prefix selects where the controller reads robot state from: robot<sid>_simulation for the simulator, or vr / vr<i> when launched by the VR target (multi-robot VR scenes additionally pass joint_name_prefix:=r<i>_).

FIC Hardware Controller

ros2 launch fic_hardware robot_control_launch.py robot_name:=Franka_FR3 station_id:=1

Robot Driver (API)

Configured per robot in fic_library/config/robots_config.yaml under driver_command (editable in Robot Configuration → Edit → File Paths). The placeholders {robot_lib} (the robot_library/ directory) and {robot_name} are substituted before launch, and FIC_ROOT is set in the driver's environment. The shipped commands:

# Franka FR3:
cd {robot_lib}/libfranka/build && ./examples/cartesian_impedance_control 172.16.0.2

# Kinova Gen3 7DOF:
cd {robot_lib}/Kinova/api_cpp/examples/build-gcc-release && ./01-torque-control_00-Torque_Controller

The driver's stdout is streamed live into the GUI log panel (tag Driver). Lines containing [FAULT] or [SESSION] are flagged as warnings, and consecutive identical lines are collapsed into a single entry plus a repeated ×N summary so a faulted arm spamming at the 1 kHz control rate cannot freeze the UI. If the driver exits on its own, the GUI detects it, logs the exit code, and resets the button so you can restart. Drivers are compiled from Robot Configuration → Compile (see Build Tools).

ROS Bag Recording

ros2 bag record -a -o ~/FIC_Interface/experiments/bags/2026_07_04_session_001

Bags are stored under experiments/bags/ in the repo root (not ~/bags) as YYYY_MM_DD_session_NNN; the session number auto-increments per day. The mixin also implements a bag-replay toggle that plays the most recently recorded bag with ros2 bag play and refuses to start while recording is active. For structured recording with metadata, prefer the Experiments extension (EXP button).

Plotter

ros2 run fic_simulation plotter_node.py --ros-args -p station_id:=1 -p num_joints:=7

Log Files and Health Checks

The simulator, gripper bridge, and VR relay write their output to per-launch files in /tmp (timestamped with the launch epoch), so silent startup failures are diagnosable:

ProcessLog location
Simulator/tmp/fic_sim_mujoco_<epoch>.log or /tmp/fic_sim_mujoco_newton_<epoch>.log
Gripper bridge/tmp/fic_gripper_bridge_<epoch>.log
VR relay/tmp/fic_vr_relay_<epoch>.log
DriverStreamed into the GUI log panel
FIC controllers, bags, plotterDiscarded (/dev/null) — run the launch command in a terminal to see their output

After starting the simulator, the GUI runs a one-shot health check: 2 s after a MuJoCo launch, 8 s after a Newton launch (Newton's first run JIT-compiles CUDA kernels for several seconds). If the simulator process has died by then, the GUI reads the tail of its log file, prints the last lines into the log panel, resets the button, and shows an error dialog pointing at the full log path. The exact log path is also printed in the log panel at start ("simulation started … (log: /tmp/fic_sim_…)").

Process Termination

Every subprocess is started in its own process group (setsid), so stop actions signal the whole tree (ros2 launch plus every node it spawned), not just the shell wrapper. The signals differ per process:

ProcessStop semantics
FIC controllers (sim + hw), plotterSIGTERM to the process group
SimulatorSIGKILL to the group, then to any process still in its session (strays that moved to another process group); the gripper bridge the same way. Nothing outside the Studio's own processes is touched.
Bag recorderSIGINT (so the bag closes cleanly), 5 s grace, then SIGKILL
DriverSIGTERM, 3 s grace, then SIGKILL
VR relay + VR FIC controllersSIGTERM relay / SIGKILL controllers, plus pkill -9 -f vr_relay_node.py
Simulator stop is scoped to this Studio

Before v4.5.0, stopping the simulator also ran pkill -9 -f mujoco, which killed any process on the machine whose command line contained "mujoco", including simulators started by another Studio or another user. It now stops only the processes in its own session, so several simulators can share a PC. The VR relay and the contact twin still use a pkill sweep on their own script names.

Crash-safe cleanup

If the GUI itself dies, its children must not keep running — an orphaned controller would keep sending the last torque command to the robot. Two independent defences cover every exit path:

  1. Python-level hooks — install_crash_cleanup() wires _kill_all_processes() into Qt's aboutToQuit, atexit, and the SIGTERM/SIGHUP/SIGQUIT handlers. It stops the children one at a time — the driver first, so it leaves torque mode while its controller is still running — SIGTERMing each process group, waiting 2 s, then SIGKILLing stragglers.
  2. Kernel-level parent-death signal — every child is spawned with prctl(PR_SET_PDEATHSIG, SIGTERM), so the kernel itself signals the child the moment the GUI dies, covering the cases Python can never catch (SIGKILL, segfault, OOM-kill). The launch commands use exec so this signal lands directly on ros2 launch, not on a bash wrapper that would not forward it.
An exception in the GUI is not a crash (v4.3.0)

sys.excepthook is still replaced, but it only reports. With a custom hook installed, PyQt5 routes exceptions from every Qt slot and timer through it and keeps running, so it fired for harmless UI bugs too. Until v4.3.0 the first such exception tore down the robot stack mid-run; a fatal exception still ends the interpreter, and atexit reaps the children. On its way out fic_hardware also clears the shared-memory alive flag, which makes the Kinova driver and the CSPM bridge leave torque mode rather than keep applying the last torque.

E-STOP and Stop All

The E-STOP (Space) does not simply kill processes. Since the June 2026 safety remediation it runs a graceful sequence: (1) fan out to every loaded extension's emergency-stop hook, (2) publish mode 0 (Stop Controller) to every active robot so the C++ controller ramps its torque down and locks at the last-known joint pose, (3) wait ~250 ms for the ramp, and only then (4) tear down all processes as a backstop. See Safety for the full contract.

Simulation → Stop All Processes (Ctrl+Shift+Q) asks for confirmation and then stops simulator, FIC controllers, driver, bags, and plotter in order — without the torque-ramp step, so use E-STOP when a real robot is moving.
