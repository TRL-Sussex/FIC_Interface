Web Remote

The Studio's controls in any browser on the network, laid out for a phone — served by the Studio itself, for as long as it runs. New in v4.3.0.

Overview

FIC Control Studio runs a small web server alongside its window. Open its address on a phone, tablet or laptop on the same network and you get the control bar, the Dashboard readout and the session controls, arranged for the screen you are holding. Nothing is installed on the phone and nothing extra runs on the robot PC: the Studio is the server, so the page works exactly as long as the Studio does.

Every button on the page runs the same handler as the matching button in the Studio, and joint or pose targets are written into the Studio's own fields before they are published. The phone and the desktop therefore never disagree about what a button does, and each shows what the other commanded.

Opening it

  1. Start FIC Control Studio as usual. The web remote starts with it (it can be turned off in Settings ▸ Web Remote).
  2. Find the address. The Studio shows it in three places: the log ("Web remote at http://…"), the tooltip of the WEB indicator in the status bar, and the Web Remote settings card, which also labels each address as LAN or Tailscale.
  3. Open https://<address>:8088/ on the phone. It must be on the same network, or on the same Tailscale network as the robot PC. The browser warns once about the certificate (the Studio signs its own — see Signing in); accept it.
  4. Sign in. The first Studio in a lab makes an admin account and says its password once: in the Studio's log, and on its standard output. A robot PC with no monitor therefore still has it — journalctl --user -u fic-studio | grep "first sign-in" on that machine. Change it on the Users page.
  5. Tap Take control to command the robot. Until then the page only watches.
Add it to the home screen

In the phone browser's share menu choose Add to Home Screen. The page opens full-screen like an app. The URL hash remembers the tab (#control, #dashboard, #session, #log) and, on a desktop, the open panel (#joint, #cart…), so a bookmark returns to the same place.

Taking control

Any number of browsers can watch. Only one at a time can command:

  • Take control claims it if nobody holds it. While someone does, the button reads In use and the banner names them.
  • The page keeps control by sending a heartbeat every second; a command also counts. Control is lost after 3 s without either.
  • The page gives control up at once when it is hidden: the phone locks, the browser goes to the background, or the tab closes.
  • Nobody can take control from a live holder. The Studio can: Take control back in Settings ▸ Web Remote.
  • STOP never needs control. Any connected browser can press it. It does not take control away: whoever holds it keeps it, and the E-STOP refuses motion until it is reset.
  • A remote holder can hand control back with In control · Release in the status bar. When someone else takes control, the page says who.

Still a shared machine

Signing in decides who may open the page and what they see, not who is in the room. Anyone signed in can take control when it is free, and STOP once signed in. The certificate is the Studio's own, so a browser trusts it only after you accept it. The software STOP is no substitute for the hardware emergency stop.

Audit log

Every E-STOP and reset, session and process started or stopped, target change, teleoperation request, Pause / Resume all and control hand-over is written to ~/.fic_studio/audit.log: one JSON object per line with the time, the event and who did it (the signed-in account and its address, not the name the browser gives). It cannot be cleared from the UI; it is rotated at 1 MB and five old files are kept (FIC_STUDIO_AUDIT moves it). User changes on the Users page are recorded too (never a password).

The Audit tab of the Log page shows it, newest at the bottom, filtered by event and text, and saves it as JSON lines. Anyone whose account has the log page can read it without taking control.

Extensions in the browser

The Studio's extensions — and the Studio pages the web app has no version of its own for (Multi-Robot, Tuning, Safety, Locomotion) — are Qt pages. Rather than write each one again for the browser, the Studio describes the page it already has — buttons, tick boxes, drop-downs, numbers, sliders, text, logs — and the web app draws the same controls and sends back what was used. An extension written next month appears on its own, with nothing added here.

  • Choosing one — the drop-down lists the Studio pages first, then every extension this Studio has loaded (Settings ▸ Extensions decides which those are). The page follows the Studio's own, refreshing about every two seconds while it is open.
  • Using one needs control, exactly as the control bar does: until Take control the controls are shown but dimmed, and the Studio refuses them.
  • What is not mirrored — a plot, a 3D view or a custom widget has no browser equivalent, so it is listed as only in the Studio rather than quietly left out.
  • Values follow the Studio: change something in the Studio and the browser shows it, and the other way round. A half-typed number is left alone while it is being typed.
It is the real panel

A button in the browser runs the same handler as the button in the Studio — including the ones that move the arm. Give the extensions page only to people you would hand the Studio to, and remember the control lease is what decides who may press anything.

Signing in

The page asks for a name and password, and shows only the pages that person is allowed. It is served over HTTPS, so the password does not cross the lab in the clear.

  • Anyone can make their own account — Make one on the sign-in screen asks for a name and a password (eight characters or more) and signs them straight in. What they get is the page and the simulation only: they can drive a simulated robot, but they cannot move the target off simulation, and nothing they press reaches an arm while the Studio is on hardware or VR. E-STOP still works. An admin lifts that with the Simulation only switch on the Users page. Self sign-up is off unless web_remote.signup is true (off by default since 5.11.0).
  • The first admin — a Studio with no user list makes one: user admin with a random password, said once in the log and on standard output (the journal keeps it: journalctl --user -u fic-studio | grep "first sign-in"). Nothing else can be done until someone signs in with it.
  • Access — on the Users page an admin gives each person one of four: Observer (3D view, dashboard and log: watches, never commands a robot), Simulation operator (commands robots in simulation only), Operator (real arms too) or Admin (everything, and users). The page ticks below fine-tune it. From a browser, only an admin may change the safety limits, save tuning or clear the log, and an admin may Take over control from whoever holds it (they are told; it is in the audit log).
  • Pages — control, view3d, dashboard, session, log, extensions. An admin ticks them per person on the Users page (in the sidebar, for admins only). A tab or card that is not ticked is not shown, and the Studio refuses the matching requests as well: hiding is not the lock.
  • Commanding the robot needs the control page. Without it the page watches: no control bar, no Take control.
  • STOP works for anyone signed in, whatever their pages.
  • Admins see every page and may add, remove and change users, including setting a new password for someone who forgot theirs.
  • A lab that is locked out — Settings ▸ Web Remote has Reset admin password…. Whoever is at the Studio is at the machine, so the old password is not needed: type a new one, or leave it empty and the Studio makes one up and shows it (and says it on standard output, for a robot PC with no monitor). Every browser is signed out, and the new password reaches the lab's other Studios like any other change.
  • Sessions live in the Studio's memory: restarting a Studio signs everyone out, and a session left alone for 12 hours ends. Eight wrong passwords in a row make that name wait a minute.

Passwords are never stored — only a scrypt hash with a per-user salt, in ~/.fic_studio/accounts.json (mode 0600), beside this machine's certificate.

One user list for the lab

Every Studio shares the same list over ROS (/fic_studio/accounts, republished every 5 s), newest version winning. An admin therefore edits users once — on the Master — and within seconds the others have taken it and saved it, including Studios started later. Hashes travel between Studios on the lab's own ROS domain; nothing of the kind reaches a browser.

Turning it off

A lab that does not want accounts sets web_remote.accounts to false: the page then behaves as it did before, open to anyone who can reach the port. web_remote.https does the same for the certificate. Both are on by default.

Several Studios

Every Studio serves its own page, titled with its host and station (for example robot2 · Station 1). If the port is taken — a second Studio on the same machine — the next free port is used (8089, 8090…) and the log says so.

Studios find each other over ROS: each publishes a small card for its page on /fic_studio/web_remotes every 2 s and drops any Studio not heard from for 7 s. Every page lists the others in its switcher, choosing the address on the same network as the browser. Studios must share a ROS domain to see each other, as they already do to share robots.

The WEB indicator in the status bar is grey when no browser is connected, green with a count when some are, blue while a browser holds control, and red if the server could not start. Its tooltip lists the addresses.

How it works

  • Server — fic_studio/web_remote/server.py, the Python standard library only. It serves a fixed set of files and nothing else, accepts commands only as JSON (so a web page on another site cannot send them), and pushes state as Server-Sent Events.
  • Threading — requests arrive on server threads; every command and every snapshot runs on the Studio's Qt thread through MainThreadInvoker, the thread its own buttons use. A command that waited too long is dropped rather than run late; STOP is never dropped.
  • Commands and state — web_remote/actions.py maps each command onto the Studio handler and builds the snapshot from the same fields the desktop shows.
  • Control lease — web_remote/lease.py.
  • Extensions — web_remote/qtmirror.py describes a Qt page as data and applies what the browser sends back, on the Qt thread. Widgets are addressed by their place in the tree, and a page that changed under a phone is refused rather than clicked blindly.
  • Accounts — web_remote/accounts.py (the store and the permissions), web_remote/auth.py (sessions), web_remote/tls.py (the certificate), web_remote/sync.py (one list for the lab, over ROS).
  • 3D view — web_remote/scene.py reads the robot's MuJoCo model and sends its shape once; static/view3d.js draws it and poses it from the same joint feedback the Dashboard shows, so on hardware it is the arm's measured position.
  • Discovery — web_remote/discovery.py.
  • Studio wiring — mixins/web_remote_mixin.py: start and stop, the 10 Hz state push, the status-bar indicator and the settings card. It is a mixin like the gamepad rather than an extension, because it needs the E-STOP and process control that extensions deliberately do not get.
  • Page — web_remote/static/: index.html, app.js, app.css. No build step.

HTTP API

For scripts. The page itself uses only these endpoints. With accounts on, every request but GET /api/session and POST /api/login needs the session cookie (fic_session) from a login, and a script must accept the Studio's certificate (curl --cacert ~/.fic_studio/web-cert.pem, or -k).

POST /api/register{user, password}{ok, auth} and the cookie; 400 if the name is taken or the password is short, 403 if sign-up is off
POST /api/logout—{ok}
GET /api/users—{ok, users, pages}, admins only (no hashes)
