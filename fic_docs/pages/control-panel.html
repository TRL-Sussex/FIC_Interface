Control Bar

The robot-driving surface, docked to the bottom of every page.

Overview

As of v4.2.0 Robot Control is no longer a page. Driving the robot happens on a bar docked along the bottom of the window, present on the Dashboard, Tuning, Settings and every extension page alike. It follows the KINOVA Kortex Web App's robot control panel: a persistent strip of buttons that slide a panel up from beneath, where clicking the same button again clears the panel.

The eight control modes collapse into two menus. Multi-station work moved to the Multi-Robot page.

│ ▲ Joint │ ▲ Cart │ ▲ Gripper │ ⌂ Home │ ◈ Contact │ ◉ Snapshot │ ▲ Quick Actions │ ──── │ ● Joint Impedance · SIM · 998 Hz │ -- │

The viewer launch toggle that used to sit here as ◈ Contact Twin moved to the top toolbar (renamed ▶ VIEW, beside ▶ PLT) and is now hardware-only — see Process Management and Contact Localization. The Contact readout to its right is likewise hardware-only now (below).

Each menu owns its own modifiers

The joint menu permanently carries the Admittance planner; the Cartesian menu permanently carries Postural, Elbow and H-PMP. Previously one shared row was shown or hidden per mode. Because a menu now owns only the modifiers that apply to its kind, a modifier can no longer be visible for a mode it does not apply to — that class of bug is structurally impossible rather than prevented by a visibility pass.

Pressing a menu commits to its base mode

Opening Cart while a joint mode is running selects Cartesian Impedance, so the controls beneath are live immediately rather than commanding the other space. A menu already holding the active mode is left alone — re-opening Joint during Joint Admittance does not drop you back to Impedance.

One shared control surface

The joint rows and the Cartesian pose fields are a single surface shown under both menus, not a copy per menu. _rc_joint_fields and _rc_pose_fields are singular state that _rc_publish_joints reads; two surfaces would mean two sets of fields and ambiguous publishing.

Cartesian layout

Position runs down the left column and orientation down the right, so the two halves of a pose read as two things rather than one seven-item list:

LeftRight
X, Y, Z (metres)axis X, axis Y, axis Z, angle (degrees)

Orientation is entered as axis-angle. Configuration stores it as a quaternion, so values are converted and pushed into the canonical hemisphere (angle ≤ 180°) on the way in.

Home

Home is mode-aware, and never changes which mode you are in:

Active modeWhat Home commands
Any joint mode (1–4)q_home_deg from the robot config, written into the joint targets and published.
Any Cartesian mode (5–8)default_ee_target from the robot config — position and orientation — published as a pose. Stays in Cartesian.
Why it matters

Before v4.2.0 a Cartesian Home fell through to publishing joint angles at a robot running Cartesian control — commanding it in a different space from the one it was running in. If a robot's config has no default_ee_target, Cartesian Home logs a warning and does nothing rather than commanding a fabricated pose.

If a sequence is playing, Home asks before firing rather than contending with the playback loop for the same publisher.

Quick Actions and Snapshot

Both are backed by the sequences extension through a small public API — list_sequences(), waypoint_count(name), play(name, loop), stop(), capture(kind, into). The bar does not reimplement playback: that is a state machine (play index, hold timers, arrival checks) and there must be exactly one of it.

With the extension disabled or missing, both buttons disable themselves with a tooltip explaining why, rather than half-working off ~/robot_sequences.yaml as a second source of truth. E-STOP already fans out to every extension's on_emergency_stop, so the panic button stops playback with no extra wiring.

Live indicator

The right-hand readout reports the active mode, the target, and the health of the joint-state stream:

ReadoutMeaning
● Joint Impedance · SIM · 998 Hz (green)Telemetry arriving within the last 500 ms.
● … · stale 780 ms (amber)Last message older than 500 ms.
● … · offline (grey)No joint telemetry has arrived at all.
▶ … (teal)A sequence is playing.

It ticks at 5 Hz on its own timer. Both this and the Dashboard header read one helper, JointStateMixin.telemetry_health(), so the two cannot report different things about the same stream.

A second readout beside it shows the active robot's {rid}_contact_estimate, on the same 5 Hz tick, visible only while the control target is Hardware (the same gate the toolbar's ▶ VIEW button follows — see Process Management). It has four states — -- (no message has arrived), UNCAL (gated off, no statement possible), no contact (a genuine zero reading) and a link name with confidence, e.g. ForeArm 87% — which must never collapse into one another. Full detail, including the v2 fit's force/point marker in the twin, on Contact Localization.

Panel mechanics

  • At most one panel open at a time; clicking the active button closes it; Esc closes.
  • The panel is sized by its own layout — no scroll area and no pinned height, so nothing is ever clipped or hidden behind a scrollbar.
  • Opening a panel grows the bar and shortens the page rather than covering it. This is a deliberate divergence from Kinova, whose panel overlays the page: on a dense telemetry Dashboard an overlay hides the readings you are commanding against.
  • Ctrl+Shift+B hides or shows the bar (Ctrl+B is Compile).
