Tuning Panel

Full-width interactive force-profile canvas with scrubbable inputs, a live operating-point overlay (v3.9.4), a live-feedback strip, and direct save to config.xml.

Overview

The Tuning Panel places the interactive FIC force-profile canvas as the full-width centerpiece. Below it a live-feedback strip shows tracking error, joint effort, and Cartesian wrench in real time so you see the effect of a gain change immediately. Scrubbable MetricField inputs replace plain text boxes — units, ranges, and clamping are embedded. Planner, Admittance, and Advanced parameters live in collapsible sections that are shown only when relevant to the selected mode and axis.

Clicking SAVE TO XML writes to fic_library/config/config.xml. The save also publishes robot<N>_param_update, and both C++ controller nodes then read the file again in the background and switch to the new values on the next control tick once they are read (see How Changes Reach the Controller below) — no process restart or mode change is needed on simulation or hardware.

The FIC Force Profile

Every tunable channel (each joint, each Cartesian axis, elbow, postural) has the same nonlinear force–displacement profile, built from a linear region followed by N_S/2 smooth (tanh) saturation stages. The canvas draws the intended profile below; the controller computes it in getEffort() in FIC.cpp, which since v4.4.0 places the outer bands differently from the canvas (see How the controller computes it after the figure):

How the controller computes it

getEffort() stores the breakpoints as one ordered vector x_b (negative breakpoints first, mirrored for a symmetric profile) with the forces E_s and ratios S beside it, and picks a band by the error:

  • Linear range: between S·x_b of the innermost negative and positive breakpoints, F = K₀·x (separate K₀ for each sign).
  • First band on each side: starts at S·x_b from the linear force there, K₀·S·x_b (so the first negative band starts at −K₀·S·|x_b|), and rises along the tanh to the first saturation force. With a single negative band (n_saturations = 2) that band is bounded by x_b(0).
  • Outer bands: start at the previous breakpoint and run from its force to their own. Each band's condition uses the bounds S(i)·(x_b(i) − x_b(i±1)) + x_b(i±1).
  • Beyond the outermost breakpoint: the outermost force, F_max.

The tanh step itself is getEffortValue(), the same function the canvas uses.

Known limitation: gaps in the band conditions

With the current band conditions some errors match no band and getEffort() returns 0:

  • Just inside the outermost breakpoint. On both sides, errors in the last (1 − S) of the outermost band — from S·(x_b,last − x_b,prev) + x_b,prev to x_b,last — return 0, and beyond x_b,last the effort is F_max. For the KinovaGen3_7DOF Cartesian profile (x_b = 0.05 / 0.1 / 0.2 m, S = 0.9) that is |error| from 0.19 to 0.2 m. Below that the outer band holds the previous band's force: the tanh rise to the outermost force is never reached.
  • The first positive band's condition never matches. Positive errors past S·x_b are taken by the next band instead, so the effort steps from K₀·S·x_b to the first saturation force rather than rising along the tanh (on the Kinova Cartesian profile, from 9 N to 13 N at 0.045 m). With n_saturations = 2 there is no next band, and positive errors from S·x_b to x_b return 0.

Errors exactly on a band boundary also return 0. These come from evaluating getEffort() directly; the controller's convergence branch scales from the effort at the peak error, so a zero there also gives a zero convergence stiffness. The canvas does not show these gaps.

Workflow

  1. Select a Control Mode (1–8) from the Mode dropdown. A label beside it shows the control space and damping situation: (NO damping — use lower stiffness!), (HAS damping_ratio), or (HAS Kv damping). See Control Modes.
  2. Select a Joint ID (0 to N−1 for the selected robot) in joint modes, or an Axis (x / y / z / q / elbow / postural) in Cartesian modes 5–8.
  3. Select a Config (tuning profile) — default, or a named profile you created.
  4. Drag handles on the FIC canvas or edit the MetricField inputs below it. The canvas, stats bar, and fields stay in sync in both directions.
  5. Watch the live-feedback strip and the operating-point marker — both refresh at ~10 Hz while the controller is running and the Tuning page is visible.
  6. Click SAVE TO XML → validates the values, writes fic_library/config/config.xml, and shows a Saved to config.xml at HH:MM:SS stamp. It also publishes robot<N>_param_update; the controller reads the file in the background and switches to the new values when they are read.

Interactive FIC Canvas

The canvas draws the FIC force–displacement curve in real time and spans the full width of the panel. Each positive-side breakpoint i gets two draggable handles (mirrored on the negative side):

Handle / ControlParameterEffect
xbi·Fierror_max[i] + force_max[i]2-D drag: horizontal moves the saturation boundary, vertical sets the saturation force. Constrained to stay strictly between neighbouring breakpoints.
S·xbisaturation_ratiosHorizontal drag sets the ratio S = handle position / xb,i, clamped to 0.4–0.95. The GUI stores a single shared S for all stages.
Scroll wheelstiffness (K₀)±10 per notch (±50 with Shift), clamped to 1–5000
live marker ●—Read-only dot showing where the robot sits on the curve right now (v3.9.4)

Overlays show the linear stiffness reference (teal dashed), the convergence-phase pullback line (red dashed), the x_b boundaries (orange dashed) and the S·x_b lines (red dashed). The canvas re-themes automatically when you switch between the Warmth dark and light themes.

Stiffness auto-clamp

The panel enforces K₀ ≤ force_max[0] / error_max[0] live: if you raise K₀ (or shrink the first breakpoint) past that bound, K₀ snaps back to the maximum. The same rule is re-checked when you save.

The FICStatsBar cards below the canvas display the current computed values: Stiffness K₀, N_S, x_b (all), F (all), Ratio S, and Conv. K (the convergence stiffness).

Live Operating Point (v3.9.4)

The canvas does not just draw the designed force profile — it shows where the robot is operating on that curve right now. A marker dot is painted in the canvas’s own (displacement, force) coordinate space at the live operating point and refreshes at ~10 Hz while the controller runs.

  • Joint modes — the marker sits at (commanded − measured position, measured effort) for the joint selected in the dropdown.
  • Cartesian modes — the marker sits at (Cartesian error component, wrench component) for the selected x/y/z/q axis; q maps to the orientation error against the torque channel. Null-space axes (elbow / postural) show no marker.
  • Fading trail — the last 24 samples (~2.4 seconds) fade from old to new, so oscillation, overshoot, and settling are visible at a glance.
  • Deviation connector — a thin dotted connector links the marker to the designed curve at the same displacement and reddens as the gap grows. When the dot sits on the curve the controller is tracking the profile; when it drifts off (and the connector reddens) the controller has saturated or is lagging.
  • Off-scale clamp — if the operating point leaves the plotted range, a small red dot is pinned at the canvas edge instead of the normal marker.
  • Numeric readout — a Δx · F · dev line below the canvas reports the live displacement, force, and signed deviation from the curve. The marker and trail clear when telemetry is absent (controller idle) and whenever you change joint, axis, or mode.

Live-Feedback Strip

A three-bar strip below the canvas updates from a 100 ms timer while the Tuning page is visible (a page-visible guard prevents background load). Each bar is centre-zero: positive values fill right in green, negative values fill left in red. Bars show -- when their channel has no data:

ChannelActive inSourceRange reference
Tracking errorJoint modesjoint_commanded_for() − joint_positions_for() for the selected jointerror_max[0] (first breakpoint)
EffortJoint modesjoint_effort_for() for the selected jointforce_max[-1] (the top of the curve)
WrenchCartesian modes, axes x/y/z/qwrench_for() component for the selected axisforce_max[-1] (peak saturation force)
Reading the strip

The bar fills proportionally to the configured range. A tracking-error bar at half-fill means the robot is sitting at error_max[0] / 2 away from its target — right in the linear region. An effort bar near full means the effort is near the top of the curve, force_max[-1]; consider widening the saturation range or increasing the force breakpoints before raising stiffness further.

MetricField Inputs

MetricField replaces plain text boxes throughout the panel. Each field embeds its unit label and a painted fill bar, and can be scrubbed: drag horizontally to change the value (hold Shift for fine 0.2× steps), use Up/Down keys for fixed increments, or click in to type an exact number. Values are clamped to the field’s min/max on commit. Units switch automatically with the control space — Nm/rad, Nm, rad in joint modes; N/m, N, m in Cartesian modes.

Save-time validation

SAVE TO XML refuses to write (with an error dialog) if the error_max or force_max breakpoints are not strictly ascending, or if K₀ exceeds force_max[0] / error_max[0]. Canvas drags cannot produce these states, but manual field edits can.

BreakpointStrip

The error_max and force_max lists are multi-value fields: one MetricField per positive-side breakpoint, i.e. N_S/2 fields. Changing the N_S spinner adds or removes fields from both strips (new fields are seeded at double the last value), and while Asymmetric is off it also keeps n_neg_sat in sync at N_S/2. The strips emit on every commit so the canvas redraws in real time.

Tuning Profiles (Configs)

A profile is a named tuning set for one robot. Profiles let you store variants like Stiff or Gentle alongside the default tuning and switch between them at runtime without re-tuning each mode.

ControlWhat it does
Config dropdownLists every profile defined anywhere for the selected robot. Selecting one publishes its name on robot<N>_active_profile (String, transient-local, so late-started controllers still receive it) and reloads the fields from XML.
+ ConfigPrompts for a name, then clones the current (mode, profile) block into a new block with that name. Other modes fall back to default until you edit them too.
− ConfigAfter confirmation, removes the selected profile from every mode it appears in. The default profile cannot be deleted.
Fallback indicator

Items in the Config dropdown show (fallback → default) when the selected profile has no concrete override for the currently-selected mode. Picking that profile loads default values; saving creates the override. The same fallback happens inside the controller: fic_param_loader.hpp falls back to the default profile block whenever the requested one does not exist for a mode.

The sim profile. When a robot has a profile named sim, the Config dropdown selects it on the Simulation target and default on Hardware, until you pick a config yourself. The Kinova Gen3's sim profile gives the joint admittance (mode 3) the lower damping of mode 4 on joints 2–4, so the arm is easy to move, and slows the Cartesian planner of modes 6–8 to 0.25 m/s so the arm keeps up with it on large moves; modes it does not list use default.

Example: creating a "Stiff" config for modes 1 and 5

  1. Set mode to Joint Impedance, click + Config, name it Stiff. Edit the joint fields and click SAVE TO XML.
  2. Switch mode to Cartesian Impedance. The Config dropdown still shows Stiff — decorated with (fallback → default) because no Cartesian override exists yet.
  3. Select Stiff (fields load from mode 5 default), edit Cartesian values, click SAVE TO XML. The indicator disappears — Stiff now has a concrete block for mode 5.
  4. Modes 2, 3, 4, 6, 7, 8 continue to fall back to default at runtime until you tune them.

Live trial (web interface)

The web Tuning Panel can try changes on the robot without touching the saved config. Live trial copies the selected config to <config>~trial (every mode block it has) and makes the copy the active config, so the robot carries on with the same values. From then on each change is written to the copy and the controller reloads it: a typed value a moment after the last keystroke, a dragged handle when you let go, the wheel a moment after the last step. A value the Studio refuses (for example a stiffness above force_max[0] / error_max[0]) is not applied, and the robot keeps the last values that were.

  • Keep writes the trial over the saved config, for every mode the trial changed, makes that config active and deletes the copy.
  • Discard puts the robot back on the config it ran before the trial and deletes the copy. Nothing from the trial is saved.

While a trial runs the Config selector is locked to the copy; mode, joint and axis change as usual, and a change still waiting to be applied is applied before the page moves on. Elbow and postural are robot-wide rather than per config, so they are not part of a trial: Save to XML writes them directly, as before. The copy is an ordinary config in config.xml, so a trial left behind by a crash shows up again in the panel and can still be kept or discarded. Starting a trial and applying to it follow the same rules as commanding the robot (not just after an E-stop, not while VR drives it); Keep and Discard always work.

H-PMP’s Own Tuning

H-PMP is switched on in modes 5–8, and while it is on it does not use the tuning of the mode it runs in. It has a tuning block of its own in config.xml, <mode id="100" name="H-PMP">, with two layers:

LayerWhat it isParameters
Joint layerA joint admittance around the torques the Cartesian layer asks for, one per jointController, planner and admittance (Kv damping, inverse mass, flow limits) per joint
Cartesian layerA Cartesian planner and FIC controller that turns the pose error into those torquesController and planner per axis (x, y, z, q)

On the Tuning Panel, pick H-PMP at the end of the Mode list, then the Layer. The web panel opens on it when H-PMP is on. Tuning it changes nothing in modes 4 or 6, and tuning those modes no longer changes H-PMP. Profiles work as for any mode: a profile without a H-PMP block of its own uses the default profile’s, and a live trial copies it along with the rest.

Before H-PMP had a block it ran on mode 4’s joints and mode 6’s Cartesian block, and a robot whose config.xml has no H-PMP block still does (the node logs H-PMP tuning: config.xml has no H-PMP block). The panel then shows those values and the first change gives H-PMP its own block, copied from them. fic_ws/src/fic_studio/tools/migrate_hpmp_tuning.py adds the blocks to an older file without changing what any robot runs. Simulation and hardware choose the blocks in the same function, fic::tuningKeyFor in fic_param_loader.hpp.

H-PMP moves on its own

A ~1 Hz swing of a few centimetres is the joint layer’s damping being too low: with Kv 9.0 / 13.7 the loop closes a limit cycle. Raise Admittance → Damping on the joint layer (joint 4 on the Kinova is held by its InvM and needs nothing). The hw_x2–hw_x6 profiles hold damping ×2 to ×6 for comparison; sim is ×4 and default ×6 (Kv 54, 82.2 on joint 1), from a simulation sweep where ×3 still oscillated and ×6 held to 1.5 mm. More damping makes the arm heavier to push: the joint layer yields at torque / Kv. The admittance Pose limits are not used: the offset is bounded by the joint’s outer error breakpoint.

Null-Space Axes: elbow and postural

The Axis dropdown also offers elbow and postural. These edit the robot-scoped <elbow> and <postural> blocks — they are not per-mode and not per-profile. Saving one applies to every Cartesian mode that runs that null-space helper, and the Planner/Admittance sections are hidden while they are selected (postural planner fields are persisted for round-tripping but not consumed at runtime). See Control Modes for when the helpers engage and H-PMP for the hybrid helper that reuses the joint parameter blocks.

Tuning Guidelines

GoalWhat to Change
Reduce oscillationLower K₀, increase Damping Ratio (planner modes), or increase Damping Kv (admittance modes); watch the effort bar in the feedback strip
Faster convergenceIncrease K₀ (watch the tracking-error bar; stop before effort saturates), increase Vel Desired
Softer feel (compliant)Increase Inv-M, lower K₀
Limit peak forceLower the last value in the Force Max strip; the force profile saturates at that value beyond the last breakpoint
Wider workspace before saturationIncrease the Error Max breakpoints (keep them ascending)
Add a saturation stageRaise N_S by 2 — one more field appears in each breakpoint strip and a new handle pair on the canvas
Start low, go slow

When tuning a real robot, start with low stiffness (K₀ < 200) and small force limits (last Force Max < 20 Nm). Increase gradually while watching the live-feedback strip. Always test in simulation first — the same config.xml drives both (see Simulation vs Hardware). For automated gain search, see Autotuning.

config.xml Structure

Parameters are stored per robot, per mode, per profile, per joint/axis in fic_library/config/config.xml. Excerpt (values from the shipped Kinova defaults):

<robots>
  <robot name="KinovaGen3_7DOF">
    <mode id="1" name="Joint Impedance" profile="default">
      <joint id="0">
        <controller>
          <stiffness>200.000</stiffness>
          <diff_effort_max>100.0</diff_effort_max>
          <error_max>0.05,0.1,0.2</error_max>
          <force_max>10,20,39</force_max>
          <saturation_ratios>0.9</saturation_ratios>
          <n_saturations>6</n_saturations>     <!-- 3 breakpoints per side -->
          <asymmetric>false</asymmetric>
          <n_neg_sat>3</n_neg_sat>
        </controller>
        <!-- <planner> and <admittance> blocks for modes that use them -->
      </joint>
      <!-- joints 1-6 ... -->
    </mode>

    <!-- User profile override (only modes that need custom tuning) -->
    <mode id="1" name="Joint Impedance" profile="Stiff">
      <joint id="0">...</joint>
    </mode>

    <mode id="5" name="Cartesian Impedance" profile="default">
      <cartesian>
        <x>...</x> <y>...</y> <z>...</z> <q>...</q>
      </cartesian>
    </mode>

    <!-- Robot-scoped null-space blocks (no mode, no profile) -->
    <postural>...</postural>
    <elbow>...</elbow>
  </robot>
</robots>

Read by fic_param_loader.hpp (C++ controller) and xml_manager.py (Python GUI). See config.xml Reference for the full schema and the fallback rules.

How Changes Reach the Controller

The GUI writes the repository file fic_library/config/config.xml, but the controller reads the installed copy at <install>/fic_simulation/share/fic_simulation/config/config.xml (both the simulation node and the hardware node use the fic_simulation share path). With colcon build --symlink-install the installed copy is a symlink back to the repository file, so a GUI save is immediately visible to the controller.

Since v4.4.0 each node holds the whole tuning for the current robot and mode in memory (every joint, the Cartesian axes and, where needed, the postural block) and reads the file only:

  • when it needs a set it does not have — a new control mode, robot or joint count, or a H-PMP toggle that changes the mode the parameters come from; until the set is read the loop sends no new command;
  • when the tuning on disk changes — a robot<N>_param_update message (sent by SAVE TO XML) or a different robot<N>_active_profile, on both nodes. The controllers keep running on the old values until the new set is read, then switch on the next tick.

The read runs on a background thread, so the 1 kHz loop never waits for it. A new joint or Cartesian target does not read the file: where it re-seeds the planners, they re-seed from the values already in memory. See config.xml for the full rules.

No file watcher

The controller does not watch config.xml for changes. An edit made outside the Tuning Panel (a text editor, a script that writes the file) reaches it only with the next robot<N>_param_update, profile change, or mode or robot change. If your workspace was built without --symlink-install, rebuild so the installed copy picks up the new file.

Manual Tuning from Terminal

If you prefer editing parameters directly without the GUI:

# Edit the config file (repo path)
nano ~/Ros2WS/FIC_Interface/fic_library/config/config.xml

# Make the running controller read it again (sim and hardware; payload only logged)
ros2 topic pub --once /robot1_param_update std_msgs/String "data: robot1:manual:0"

# ...or restart the controller
ros2 launch fic_simulation fic_launch.py robot_name:=Franka_FR3 num_joints:=7    # simulation
ros2 launch fic_hardware robot_control_launch.py robot_name:=Franka_FR3 station_id:=1  # hardware

You can also open the raw XML in-app with the VIEW XML button, which shows an editable view of config.xml for the selected robot.
