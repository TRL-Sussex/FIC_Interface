Emergency Stop

Graceful torque ramp-down, position lock, then full process teardown.

Escape does not E-STOP

Escape is bound to Stop sequence (shortcuts.stop_sequence), not to E-STOP. It halts sequence playback but leaves controllers and processes running. Use Space for the full emergency stop.

What E-STOP Does (Full Studio)

Since the June 2026 safety remediation, E-STOP stops gracefully first, kills second. The old behaviour killed the controller process outright, which could leave the last commanded torque frozen on the robot. The current sequence (_emergency_stop in main_window_pro.py) is:

  1. Extension fan-out — every loaded extension's on_emergency_stop() hook is called, so sequences, scripts, teach mode, and teleop halt their own activity (see table below).
  2. Graceful stop command — broadcast_stop() publishes "Stop Controller" on every active robot's robot{N}_mode_select topic. The hardware controller (fic_hardware) switches to mode 0 and ramps its output torques down exponentially inside the 1 kHz loop (decay factor 0.995 per cycle, ≈200 ms time constant) toward the idle baseline — gravity compensation for robots whose driver does not compensate gravity internally, zero for those that do. When every joint's residual drops below 0.05 Nm, the controller signals the vendor driver via shared memory (stop_torque_mode) to exit torque mode.
  3. Position lock — each robot's last-known joint angles are published to its robot{N}_desired_joint_angles topic, a redundant hold while nodes are still alive. On a multi-robot station every active robot is locked at its own last pose.
  4. Ramp window — the GUI waits 250 ms (_ESTOP_RAMP_MS) so the ramp can actually run before teardown.
  5. Process teardown — every Studio-launched process is stopped (SIGTERM to the whole process group, SIGKILL after a short timeout):
    • FIC hardware controller (ros2 launch fic_hardware robot_control_launch.py)
    • Robot driver (per-robot driver_command, e.g. the libfranka cartesian_impedance_control binary)
    • FIC simulation controller (ros2 launch fic_simulation fic_launch.py)
    • MuJoCo / Newton simulation
    • ROS bag recording (stopped with SIGINT so the bag is finalized)
    • Plotter
  6. OS-level backstop — pkill -9 -f "ros2 launch" and pkill -9 -f cartesian_impedance_control catch anything that survived the per-process teardown.
  7. UI feedback — the status bar shows "E-STOP ACTIVE - ALL PROCESSES KILLED" in red.

Extensions implement on_emergency_stop() from ExtensionBase (see Extensions). The core ones:

Dev Console Difference

The Dev Console has a simpler E-STOP handler: it stops the hardware controller, driver, FIC controller, bag recording and plotter, publishes the hold pose for the station robot only, and runs the cartesian_impedance_control pkill backstop. It does not load extensions, so there is no fan-out step, and it does not issue the mode-0 ramp command before killing — prefer the Full Studio when running hardware experiments.

Automatic Trigger: Safety Zone Violations

The safety system can also command a stop without you pressing anything: when a safety zone violation is detected with enforcement enabled, the GUI issues a debounced broadcast_stop() (one stop per 3-second episode) — the same graceful mode-0 ramp, but without the process teardown. The C++ controller additionally clamps targets and applies virtual walls, so this GUI-side stop is a backstop, not the primary enforcement.

Recovery After E-STOP

  1. Assess the situation — check the robot's physical state and surroundings.
  2. Review logs — check the Logs for what triggered the stop.
  3. Restart processes — E-STOP kills all processes. You need to restart them manually:
    • In FIC Control Studio, set Target to Simulation or Hardware and press ▶ Start to relaunch the session (simulator/driver, then the FIC controller ~2 s later)
    • In the FIC Dev Console, use the discrete ▶ API (driver) and ▶ FIC (controller) buttons instead
    See Processes for the full start order.
  4. Verify robot state — check joint positions in the live readout before sending new commands.
  5. Resume work — the status bar returns to normal once processes are restarted.

Terminal Equivalent

To stop everything manually from a terminal, mirror the GUI's own sequence — graceful stop first, then kill:

# 1. Graceful controller stop (torque ramp-down, robot1)
ros2 topic pub --once /robot1_mode_select std_msgs/msg/String "{data: 'Stop Controller'}"

# 2. Kill the launch trees and controllers
pkill -9 -f "ros2 launch"
pkill -9 -f cartesian_impedance_control

# 3. Simulation leftovers (patterns the GUI itself uses)
pkill -9 -f simulation_launch.py
pkill -9 -f mujoco
pkill -9 -f mujoco_newton
pkill -9 -f gripper_bridge.py

Repeat step 1 with /robot2_mode_select etc. on a multi-robot station. See Topics for the full topic map.

Skipping the ramp

Killing the controller process without first sending Stop Controller loses the graceful ramp. Since v4.3.0 a controller that is stopped normally (SIGTERM or Ctrl+C) clears the shared-memory alive flag, and the driver leaves torque mode and holds position. A controller that is SIGKILLed or crashes cannot clear it, so the driver keeps the last commanded torque until it is stopped too. Always send the mode-0 stop first when the robot is under torque control.

Hardware E-STOP

The software E-STOP is not a substitute for a physical emergency stop button. When working with real hardware, always have a hardware E-STOP within arm's reach. The software E-STOP requires a working computer and network — a physical button does not.
