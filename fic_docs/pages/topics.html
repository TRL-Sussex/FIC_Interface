ROS 2 Topics

Consolidated reference for all topics used by FIC Control Studio.

Naming conventions

Everything is scoped so that up to four independent robot stations can share one ROS 2 network:

ConventionMeaning
robot{N}_*Per-robot controller topics. N is the numeric robot / station id (1–4). The GUI creates a full publisher family per active robot; each fic_simulation / fic_hardware process reads its own family based on its station_id ROS parameter.
robot{N}_simulation/*Physics-backend topics. The MuJoCo launch file builds this prefix as robot{sid}_simulation from its station_id argument and passes it to the sim node's topic_prefix parameter.
vr/*, vr{i}/*Same physics-backend topics when the FIC controller is launched with source_prefix:=vr for VR headset mode — see VR / ZED Teleop.
fic_studio_{host}The GUI node name. It embeds the machine's hostname so two Studios on one ROS domain don't collide.

Topic flow

GUI → Controller (published by fic_studio_{host})

Every robot the Studio talks to gets its own family of topics, prefixed by robot{N} where N is 1–4. Since v3.3.0 these are created on demand: when the operator clicks ＋ Add Robot in Multi-Robot, node.add_robot(N) creates the full set; the ✕ button on a card destroys them. TL marks TRANSIENT_LOCAL durability, so late-joining controllers still receive the last value.

robot{N}_param_updateStringParameter hot-reload trigger: "robotN:param_type:param", sent on every SAVE TO XML. Any message makes both FIC nodes read config.xml again in the background; the controllers keep the old tuning until the new set is ready (the payload is only logged). See Tuning.
robot{N}_safety/cartesian_limitsFloat64MultiArray[x_min, x_max, enabled, y_min, y_max, enabled, z_min, z_max, enabled] (metres).
robot{N}_safety/joint_limitsFloat64MultiArray[j0_min, j0_max, j1_min, j1_max, …, enabled] (radians).
robot{N}_safety/velocity_limitsFloat64MultiArray[max_joint_vel, max_cart_vel, enabled], optionally a 4th value: the joint target speed of joint impedance (rad/s, 0: off).

Safety limits are broadcast: the Safety panel publishes the same workspace, joint, and velocity bounds to every active robot. The matching fic_hardware / fic_simulation process subscribes to its own robot{N}_* family based on its station_id ROS parameter, so two robots on one network never collide.

Simulation topics (robot{N}_simulation/ prefix)

Published by the physics backend — the CPU MuJoCo simulator (mujoco_native) or the optional Newton GPU node, selected in Settings → Simulation. The prefix comes from the node's topic_prefix parameter (default simulation; the launch file sets robot{sid}_simulation).

TopicTypeRate (MuJoCo, CPU)Description
…/actuators_cmdscommunication/ActuatorCmdssubTorque commands from the FIC controller (and the gripper bridge); actuator names torq_j1…torq_jn, merged per name across publishers. A torque not refreshed for 200 ms is zeroed; a position actuator (the gripper) keeps its setpoint.
…/joint_statesJointState1 kHzSimulated positions, velocities, efforts.
…/gravity_torquesFloat64MultiArray1 kHzg(q) inside the sim, from qfrc_bias at zero velocity. The FIC controller adds this raw to its own output in the joint modes, so a wrong vector here is injected feedforward on every joint. Sanity check: a vertical-axis joint must read ~0 Nm in every pose.
…/contact_torquesFloat64MultiArray1 kHzJoint torques the environment applies to each hinge (qfrc_constraint + qfrc_applied: contacts, joint limits, applied wrenches), without the controller's own command. fic_simulation estimates H-PMP's external wrench in Modes 7/8 from it (since v5.3.0). MuJoCo backend only.
…/force_torqueWrench200 HzThe arm's wrench estimate at the EE sensor site. Includes gravity — measured at 46.7 N with a Kinova standing still and untouched — so it is not a contact detector on its own.
…/imu_dataImu500 HzFrom the MJCF's accelerometer / gyro / framequat sensors (defaults when the model has none).
…/odomOdometry50 HzFloating-base odometry (zeros for a fixed base).
…/actuator_torquesFloat64MultiArray1 kHzFinal per-joint torques the controller sent (after velocity damping and clamping) — published by fic_simulation, not the sim.

One service: robot{N}_simulation/sim_reset (communication/srv/SimulationReset) resets the model to a requested base pose (floating base) and joint state; header.frame_id must be the model name.

Newton backend differences

The Newton GPU backend uses the same topic names but publishes at 200 Hz (500 Hz physics step). Its gravity_torques are computed via mj_inverse on the solver's internal CPU MuJoCo mirror — the same recipe that was found wrong in the (since retired) C++ backend in Oct 2026 (mj_forward recomputes qacc from ctrl, so qfrc_inverse returns the actuator command rather than g(q)). Newton has not been re-measured since; treat its gravity as suspect and check a vertical-axis joint reads ~0 Nm before relying on it. imu_data and force_torque are published as empty messages. Incoming torques are applied through an actuator-name→DoF map into control.joint_f. See Simulation.

Sensor-data QoS

All robot{N}_simulation/* topics and robot{N}_force_torque use best-effort sensor-data QoS. If ros2 topic echo shows nothing, force a compatible profile: ros2 topic echo /robot1_simulation/joint_states --qos-profile sensor_data.

Teleoperation topics

Created only while a teleop session is active; destroyed on disconnect. See Teleoperation.

TopicTypeRateDescription
/teleop/negotiationString (JSON)1 Hz while waitingRole handshake: ANNOUNCE (with desired role), ACK, DISCONNECT, SESSION_BUSY. Machines pair only when roles are complementary.
/teleop/master_jointsFloat64MultiArray100 HzMaster joint state stream (joint mode).
/teleop/master_ee_posePose100 HzMaster EE pose stream (Cartesian mode).
/teleop/slave_wrenchWrench100 HzSlave contact forces for bilateral force reflection (bounded since the June 2026 safety update).
/teleop/configString (JSON)On-demandMode/scaling synchronisation between master and slave.
/teleop/ping / /teleop/pongFloat641 HzMaster sends a timestamp; slave echoes it; master computes RTT.
/teleop/latencyFloat641 HzOne-way latency estimate (RTT/2), published by the master.

There is no dedicated heartbeat topic: liveness is inferred from data flow. A monitor checks every 2 s that some partner message arrived within the configurable timeout (default set in the Teleop panel); on timeout the session ends and the robot holds position.

Debugging topics from the terminal

# List all active topics
ros2 topic list

# View a topic's type and endpoint count
ros2 topic info /robot1_trajectory_data

# Echo live data (add --qos-profile sensor_data for sim/wrench topics)
ros2 topic echo /robot1_trajectory_data

# Check publish rate (expect ~1000 Hz from mujoco_native, ~200 Hz from Newton)
ros2 topic hz /robot1_simulation/joint_states

# Command a mode from the CLI (String for hardware, Int32 for simulation)
ros2 topic pub --once /robot1_mode_select std_msgs/msg/String "data: 'Joint Impedance'"
ros2 topic pub --once /robot1_control_mode std_msgs/msg/Int32 "data: 1"

For a live GUI-based topic browser, use the Topic Monitor. The message definitions for ActuatorCmds, Jacobian, and SimulationReset live in fic_ws/src/communication/.
