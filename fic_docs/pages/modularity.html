Modularity & Extensibility

Pluggable kinematics solvers (incl. closed-loop parallel mechanisms), robots with more joints than actuators, and an uncapped dashboard — the system adapts to the robot instead of the robot adapting to the system.

Why this matters

These changes let FIC Studio drive robots it was never hard-coded for: a parallel/closed-loop mechanism (via a new solver), a robot whose controlled joints ≠ displayed joints (N actuated of M total), and any joint count in the dashboard. Everything is driven by robots_config.yaml + a small pluggable C++ seam — no per-robot code branches.

1 · Pluggable kinematics solvers

The FIC controller talks only to an abstract fic::KinematicsSolver interface (fic_library/include/fic/kinematics_solver.hpp). The concrete solver is chosen per robot by the kinematics_solver: key in robots_config.yaml and built by solver_factory.hpp:

kinematics_solverSolverUse
pinocchio (default)Built-in serial solverOrdinary open-chain arms (Kinova, Franka, IIWA…)
nonenone (degraded)Joint-space control only; Cartesian/IK/FK disabled. Deliberate, no error.
pinocchio_closed_loopClosed-loop solver (below)Parallel / closed-loop mechanisms (e.g. CSPM)
your nameCustomRegister in solver_factory.hpp — see docs/custom-kinematics-solver.md

Adding a solver is: implement fic::KinematicsSolver in a header, add one #include + one if (name == "…") branch in solver_factory.hpp, rebuild, and set the name in config. The interface is Eigen-only (no ROS, no pinocchio pulled in for the caller), so solvers are unit-testable outside a ROS workspace.

2 · Closed-loop / parallel mechanisms

A URDF is a kinematic tree; a parallel mechanism has closed loops a tree can't express. The new ClosedLoopPinocchioSolver (fic_library/include/fic/solvers/closed_loop_pinocchio_solver.hpp) handles this generically:

  • It holds the full open tree (from the URDF) plus N loop closures given as frame pairs in config — no mechanism-specific math.
  • It presents an actuated-joint interface to the controller (nq()=nv()= the number of actuated joints), whose end-effector is the moving platform.
  • Per control cycle it does a warm-started Newton constrained-FK (solve the passive joints so all loops close) and returns the reduced Jacobian (EE twist per actuated joint) via a constraint null-space projection. IK uses that reduced Jacobian.
  • With zero loops it degrades to the ordinary serial solver — a strict superset usable for any robot.

Config keys (per robot in robots_config.yaml):

kinematics_solver: pinocchio_closed_loop
ee_frame_name: platform          # the controlled (moving) frame
ee_orientation_only: true        # control rotation only (fixed-CoR spherical mechanism)
loop_closures:                   # each pair of points the mechanism holds coincident
- bodyA: leg1_tip
  posA: [0.028961, 0.050163, -0.048264]
  bodyB: platform
  posB: [0.028961, 0.050163, -0.048264]
- { bodyA: leg2_tip, posA: [...], bodyB: platform, posB: [...] }
- { bodyA: leg3_tip, posA: [...], bodyB: platform, posB: [...] }
Validated

For the CSPM spherical parallel manipulator the solver's platform orientation matches MuJoCo ground truth to < 0.03° and the reduced Jacobian is full rank (the platform's 3-DOF orientation is fully controllable by the 3 motors). The controller loads it as "Loaded robot model: CSPM (nq: 3, nv: 3, solver: pinocchio_closed_loop)".

Real-time note

The constrained FK is iterative (Newton). It stays real-time because it is warm-started from the previous cycle's configuration, converging in a few iterations. Cold starts (first cycle) take more.

3 · Robots with more joints than actuators (N of M)

A parallel robot has passive joints you want to see but not command. Two independent config lists express this:

KeyMeaning
joint_names + num_jointsThe actuated joints — what the controller drives (e.g. 3).
view_joint_names (optional)The full display set — every joint to show (e.g. 9 hinges + 3 platform-orientation pseudo-joints). Omit for conventional robots.

The GUI reacts automatically (all in fic_studio):

  • The control bar's joint surface lists every view_joint_names joint; only the actuated ones are interactive, the rest are greyed/disabled but show live data. Commands publish only the actuated joints, by name.
  • Dashboard joint rows are now built dynamically, one per joint (uncapped) — previously hard-limited to 7. A robot with 3, 12 or 20 joints all render correctly, rebuilt on robot change.
  • View-only joints get their live data by name from the simulator's joint_states (which the MuJoCo simulator publishes for every joint, plus <ball>_roll/pitch/yaw pseudo-joints for a platform's orientation).
Backward compatible

Robots without view_joint_names behave exactly as before (num_joints controllable rows, index-based telemetry). All of this is platform-independent and applies on Linux too.
