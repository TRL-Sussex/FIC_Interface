Troubleshooting

Common issues and their fixes. If you're brand new, pair this page with the First Motion Checklist.

"My robot doesn't move" — decision tree

Work down this list in order. Each step tells you how to prove or disprove one possible cause before moving on.

  1. Is the GUI actually publishing a command?
    Open Topic Monitor (Windows → Topic Monitor) and subscribe to robot{N}_desired_joint_angles. Drag a joint slider.
    • Values update as you drag → GUI layer is fine. Go to step 2.
    • Nothing updates → station_id mismatch between the GUI and your FIC node (GUI publishes robot1_*, node subscribes to robot2_*). Check Settings → General → Station ID.
  2. Is the control-mode message the right flavour?
    Simulation uses robot{N}_control_mode (Int32, 1–8). Hardware uses {rid}_mode_select (String, "Joint Impedance" etc.). The GUI publishes both so this normally just works — but if you're sending mode changes from a custom script, subscribe to the right one for your target. See Simulation vs. Hardware.
  3. Is the FIC node subscribing at all?
    Run ros2 topic info robot1_desired_joint_angles --verbose. You should see at least one subscriber.
    • Zero subscribers → FIC node never started, crashed silently, or started with a different station_id. Check the terminal where FIC was launched; restart with matching station ID.
  4. (Simulation only) Is MuJoCo running?
    The FIC simulation node needs MuJoCo's feedback topics before it can publish torques. If the SIM LED is red or the viewer never appeared, start SIM first, then FIC.
  5. (Hardware only) Is the vendor driver running?
    ros2 topic list | grep -i joint_state on the hardware machine should show the driver's state topic. Also check the shared-memory heartbeat: with the driver up, ls -la /dev/shm/ | grep robot should list robot_feedback_memory and desired_joint_angles_memory.
    • No shared-memory entries → the driver crashed. Start API alone (no FIC) and confirm it stays up.
    • Entries present, heartbeat stale → old shared-memory segment from a previous session. Stop everything, remove with rm /dev/shm/robot_feedback_memory /dev/shm/desired_joint_angles_memory, restart.
  6. Is the FIC control loop publishing torques?
    Subscribe to /fic_torque_commands (simulation) or watch the driver-side log (hardware). If torques are exactly zero, the current control mode is probably 0 (passive) or K₀ is zero. The C++ controller initialises to Mode 1 (Joint Impedance), but stays effectively passive until a mode message lands and a non-zero stiffness is set — re-select and send Mode 1 in the Control Panel to re-engage.
  7. Are torques being saturated to zero by a safety limit?
    Robot Config → Safety. A Cartesian-zone violation or out-of-range joint target clamps the output. The log viewer (Ctrl+L) logs "Safety limit hit" when this happens.
  8. Is the target just… where the robot already is?
    FIC holds pose when target == current. If nothing moves and the log shows zero tracking error, command a 5° joint offset to confirm the full pipeline works before assuming anything is broken.
Bisect with ros2 topic echo

The fastest way to find which layer is wrong is to watch the data at each hop: GUI → desired_joint_angles, FIC node → fic_torque_commands, driver → joint state. Wherever the values stop updating is the broken layer.

IK solver didn't converge (Modes 5–8)

  • Cartesian target is outside the robot's reach → shrink the commanded offset.
  • Target too close to a kinematic singularity (fully-extended arm, wrist flip) → add a small rotation to break the singularity.
  • Tolerance too tight → relax ik_tolerance in the robot config.
  • Symptom: "IK: no solution" in the log, the Cartesian target turns red in the Control Panel, and no new desired_joint_angles is published until the target becomes feasible again.

Shared memory: "permission denied"

  • The first process that creates /dev/shm/robot_feedback_memory sets its permissions. If an earlier run was launched as root, subsequent user-mode runs can't write to it.
  • Fix: sudo rm /dev/shm/robot_feedback_memory /dev/shm/desired_joint_angles_memory, then restart the driver + FIC as your normal user.

Simulation

ProblemFix
Robot not moving in simulationBoth SIM + FIC LEDs must be green. Verify correct robot is selected. Check MuJoCo window for errors.
MuJoCo window doesn't appearCheck for OpenGL errors: glxinfo | grep "direct rendering". Install libglfw3 libglew-dev.
FIC node crashes on startStart SIM before FIC. The FIC node needs MuJoCo's topics to be available.
Jacobian size mismatch crashStop FIC/CTRL → change robot → restart. Never change robot while controller is running.
Arm holds a rock-steady pose and ignores every targetA latched hard fault. A joint that left its joint_limits_deg range sets hard_fault_ and the controller outputs gravity compensation only — which looks exactly like a healthy arm that refuses to move. It is cleared only by loadRobotModel(), i.e. by republishing the robot name on robot{N}_selected_robot. Look for HARD FAULT in the FIC log.
Several simulators fighting over one topicKilling the ros2 launch parent can leave the simulator process (install/mujoco_native/lib/mujoco_native/simulation) or the controller running, and one accumulates per restart. Kill on lib/mujoco_native/simulation and install/fic_simulation/lib, SIGKILL, then verify exactly one of each before trusting anything you measure.
Freshly started station falls over before you can use itThe arm starts at the model keyframe with nothing holding it and falls during the ~10 s the controller spends initialising; on the Kinova joint 3 reaches its −150° limit and hard-faults on the way down. Park it with the robot{N}_simulation/sim_reset service while you wait, and command the pose before teleporting onto it, so the controller is never closing a large error against an arm that was just moved.
The FIC loop rate drops while a target streams (the arm slows, lags or stops following)Before v4.4.0, in every mode except Joint Impedance (mode 1) each streamed joint target, and every robot{N}_hapfic_enable message even with an unchanged value, made the next 1 ms tick re-read config.xml (about 29 ms per read on the lab PC, more on slower PCs). In MuJoCo with targets at 100 Hz the loop fell from 1000 Hz to 74 Hz (mode 2) and 65 Hz (mode 3); hapfic_enable re-sent at 20 Hz brought it to 405 Hz. This is what stopped the arms after 5 Oct. Fixed in v4.4.0: the nodes read the tuning once per robot and mode, in the background, and a target only re-seeds the controllers from memory (see config.xml). Rebuild fic_simulation and fic_hardware. fic_simulation logs the rate it reaches every 10 s (Control loop: … Hz); it should read about 1000 Hz.
Commands you publish have no effect at allYou published before the controller subscribed. Discovery here takes up to about 12 s, and publishing into an undiscovered topic succeeds silently and delivers nothing. Wait on get_subscription_count() before sending anything that matters.

Recording from another PC

Two traps that do not look like faults — they look like bad control.

ProblemFix
A topic reads a steady, plausible nothingQoS mismatch. gravity_torques, actuator_torques, force_torque and joint_states are published best-effort; a default (reliable) subscription matches none of them and simply receives nothing. ROS warns once on the console — read it. Subscribe with qos_profile_sensor_data.
The arm looks like it is divergingCheck your own sample rate before believing it. Draining callbacks once per loop iteration against a ~1 kHz publisher drops most messages and leaves the value you read stale, so the arm appears to freeze and then jump. Spin on a dedicated thread, and refuse to record below a feedback rate you have chosen in advance.
force_torque suggests contact that never happenedIt is the arm's own wrench estimate and includes gravity — measured at 46.7 N with a Kinova standing still and untouched, swinging 10–47 N in free motion. It is not a contact sensor. To detect contact, run the same commanded motion with and without the obstacle and compare; that cancels gravity and the arm's own dynamics because both runs follow the same trajectory.
Is the published gravity actually gravity?

Pick a joint whose axis is vertical (on the Kinova Gen3, joint 0). Gravity exerts no moment about a vertical axis in any pose, so that entry in gravity_torques must be ~0 Nm whatever the arm is doing. If it is not, the vector is not gravity — and fic_simulation adds it raw to the control law's output in every joint mode, so a wrong one is injected feedforward on every joint, every cycle. See Simulation vs. Hardware.

Known issue: one simulated joint does not move

On the Kinova in simulation, joint 0 receives its target correctly, computes the right error and the control law asks for up to 20 Nm, yet the arm does not move; every other joint tracks to about a degree. Not explained by continuity detection (the controller logs it correctly as CONTINUOUS), the gains, the model or gravity. Under investigation — if you are driving joint 0 in simulation and seeing nothing, this is why.

Hardware

ProblemFix
Robot not respondingCheck: (1) driver connected (API LED green), (2) can ping robot IP, (3) torque control enabled on robot, (4) start API before FIC.
Driver won't connectCheck network cable, robot IP, firewall. Try manual launch: ~/FIC_Interface/robot_library/franka/build/franka_joint_controller 192.168.1.100
Kinova faults when stopping FIC or APIFixed in v3.8.1. If you see this on an older build, rebuild both fic_hardware and the Kinova driver against the latest shared_params.h. The driver now catches SIGTERM and transitions back to position mode before exiting. fic_hardware ramps torques down to gravity compensation over ~200 ms instead of zeroing instantly.
Kinova faults during normal operationCheck torque tuning — the per-joint rate limit is ±2 Nm/ms (joints 0–3) and ±1 Nm/ms (joints 4–6). If the controller output changes faster than this, the rate limiter clamps it. Lower K0 stiffness or increase planner damping_ratio to reduce torque transients.
Jerky motion on hardwareLower K0 stiffness, increase planner damping_ratio, check network latency between machines.
Robot goes limp after E-STOPExpected behaviour. Restart API + FIC to re-enable control. The hold command only lasts while the controller runs.
Shared memory version mismatch after updateAuto-handled — open_or_create() detects the size change and recreates the segment. If you see persistent errors, manually remove: rm /dev/shm/robot_feedback_memory /dev/shm/desired_joint_angles_memory and restart.

Tuning & Auto-Tuning

ProblemFix
Parameters don't take effectClick SAVE after editing; the save publishes robot{N}_param_update and the FIC node logs Parameter update (…); reloading tuning from config.xml, then Controllers Initialized … (tuning read from config.xml) when it has switched. After editing the file by hand, publish robot{N}_param_update (any string) or restart the FIC node. Without --symlink-install, rebuild fic_simulation first.

New robot missing from dropdownAdd it in Robot Config (+ ADD), click DEPLOY TO CONTROLLER, rebuild (colcon build --symlink-install), source, restart.

Scripts & Sequences

ProblemFix
Script can't find Robot APIFunctions are injected automatically. Don't import them. Check the Target dropdown (Simulation/Hardware).
Joint sequence waypoint timeoutIncrease timeout_seconds in Settings, or increase joint_tolerance_deg (default 3°).
Cartesian sequence waits for the timeout before advancingThe Cartesian planner often steady-states 5–10 mm off in gravity-loaded poses. Default Pos Tol is 15 mm and there is also a settle-pass fallback (position_error ≤ 3× tolerance stable for 1.0 s). If it still times out, the EE never got within 45 mm — check the trajectory plot for an unreachable target / wrong frame / singularity rather than tolerance.
Cartesian sequence advances too aggressively (settles far from target)If the settle-pass log line fires consistently more than the strict-pass line, the planner can't reach within tolerance. Either tighten the Cartesian-mode tuning (Tuning panel, Mode 6 stiffness) or accept the wider tolerance and lower the Pos Tol spinbox to a value the planner reliably hits.
TEACH MODE button puts the robot in the wrong spaceSet the Capture Mode dropdown above the position fields first — the TEACH / PLAYBACK buttons read it. Joint / Gripper → joint admittance / planner; Cartesian → Cartesian admittance / planner.
Sequence doesn't loopCheck the Loop checkbox is enabled.
pip error on Install APIThe button uses python3 -m pip. If it fails with PEP 668, the --break-system-packages flag is already added.

Teach Mode

ProblemFix
Click Start Teaching but the robot is still stiffThe teach panel publishes "Joint Admittance" or "Cartesian Admittance" on {rid}_mode_select — the FIC controller has to be running for the publish to land. Confirm with ros2 topic echo {rid}_mode_select; if the message goes out but mode never changes, the FIC node isn't subscribed (matching station_id).
Teach started in the wrong control spacePick the Mode selector in the teach panel's title row before clicking Start Teaching. The selector locks while a session is live; click Stop Teaching first if you need to switch.
Cartesian Go-To moves the wrong directionThe teach panel saves the EE pose in the base frame (matching {rid}_ee_current_pose). If pushing the EE during teaching produced a recorded pose that's offset from where you actually were, check that the ee_link frame in the URDF matches what libfranka / the simulator publishes.
Gripper buttons don't actuate the real gripperThe libfranka bridge runs the gripper on a separate thread at ~20 Hz and ignores width changes < 2 mm. Confirm {rid}_gripper_width is reaching the bridge (ros2 topic echo); if the bridge isn't running, the publishes go to the void silently.

Manual Process Debugging

If GUI processes fail to start, try launching them manually in separate terminals:

# Terminal 1: Source workspace
source /opt/ros/jazzy/setup.bash
source ~/FIC_Interface/fic_ws/install/setup.bash

# Terminal 2: MuJoCo simulation
ros2 launch mujoco_native simulation_launch.py robot_name:=Franka_FR3

# Terminal 3: FIC controller (simulation)
ros2 launch fic_simulation fic_launch.py robot_name:=Franka_FR3 num_joints:=7

# Terminal 4: FIC controller (hardware)
ros2 launch fic_hardware robot_control_launch.py robot_name:=Franka_FR3

# Terminal 5: Plotter
ros2 run fic_simulation plotter_node.py

# Terminal 6: Bag recording
ros2 bag record -a -o ~/bags/debug_session

# Terminal 7: GUI
ros2 run fic_studio fic_studio_pro    # or fic_dev for Dev Console
