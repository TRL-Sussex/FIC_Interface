Topic Monitor

Namespace-grouped topic tree with per-field live inspection — directly in FIC Control Studio.

Overview

The Topic Monitor panel discovers all active ROS 2 topics, groups them by robot namespace, and lets you subscribe to them to view live message data broken down field-by-field — without opening a separate terminal. The raw string dump is complemented by a structured inspector card that shows each field value alongside a micro-bar for numeric scalars, plus a small sparkline of recent message arrivals. It is implemented in fic_studio/mixins/topic_monitor_mixin.py.

Interface Layout

The panel is a horizontal splitter below a filter row, with a stats bar at the bottom:

  • Left: Topic Tree — topics grouped by robot namespace, with an Hz chip and a Monitor toggle per topic
  • Right: Inspector Card — field-by-field live breakdown for the selected topic, plus arrival-rate sparkline and raw stream

Topic Tree

Topics are organised into a namespace tree (one collapsible parent per namespace, labelled with its topic count). Grouping handles both naming styles used by the framework:

  • Path-style — the first path segment becomes the group, e.g. /robot1_simulation/joint_states groups under /robot1_simulation
  • Flat FIC naming — an embedded robotN token is detected, so robot1_target_joint_angles groups under robot1
  • Everything else (e.g. /rosout) falls into the (global) group

Expansion state is preserved across list refreshes, and a lone namespace is auto-expanded. The tree has three columns:

Column / ElementDescription
Namespace groupParent row: namespace with total topic count in parentheses, e.g. robot1  (12); not selectable
Topic / NamespaceChild row: leaf name only (last path segment); full topic path shown as a tooltip on hover
HzFractional messages per second to 1 d.p. over a rolling 5-second window (e.g. 19.8 Hz); shows - for topics that are not monitored, since rates are measured from received messages, not from the graph
Monitor / StopToggle button to start/stop subscribing to this topic
Hz readings saturate at 20.0 Hz

Rates are computed from a per-topic timestamp buffer capped at 100 entries, counted over a 5-second window (count / 5.0). A topic faster than 20 Hz fills the buffer in under 5 seconds, so the reading tops out at 20.0 Hz. The 1 kHz joint_states stream from the simulator and other fast telemetry will therefore read 20.0 Hz here — use ros2 topic hz in a terminal for an exact figure.

Message Flow

Inspector Card

Selecting a topic in the tree activates the inspector. If the topic is not yet monitored, selection auto-subscribes it (and persists it as a favourite), and the raw stream is cleared for the new topic. The card shows a live field-by-field breakdown of the latest cached message using rosidl_runtime_py.convert.message_to_ordereddict() (with fallbacks to msg.get_fields_and_field_types() and then __slots__ when that library is unavailable):

  • Scalar fields — label + current value + a LimitBar micro-bar for numeric scalars, filled with |value| clamped to the 0–1 range
  • Nested messages — collapsed to a compact summary, e.g. {...(3 keys)}
  • Arrays / sequences — up to 4 elements shown in full; longer arrays are truncated to the first 3 plus a total count, e.g. [0.1, 0.2, 0.3, ... (7)]
  • Formatting — floats to 4 decimal places; strings longer than 60 characters truncated
  • Arrival-rate sparkline — a small TrajectoryPlot of message recency over the last 5 seconds (1 = just arrived, 0 = 5 s old)
  • Raw stream — one timestamped block per message of the selected topic, format [HH:MM:SS.mmm] <str(msg)>; individual messages are truncated at 2000 characters

Field rows are rebuilt only when the field set changes; otherwise the ~15 Hz refresh patches value labels and bars in place, so the inspector stays responsive on fast topics.

Favourites

Monitored topics are persisted across restarts as a {topic_name: msg_type} map under topic_monitor.monitored in the studio settings file ~/.robot_selector_gui_settings.yaml (written by the settings auto-save, see Settings). When the page is built, previously monitored topics are automatically re-subscribed; if the ROS node is not yet available the restore is silently skipped.

Monitoring is subscription-based

Clicking Monitor dynamically imports the message class from the advertised type string (e.g. sensor_msgs/msg/JointState) and creates a real rclpy subscription with queue depth 10. Types the studio cannot import (unsourced workspaces, custom interfaces) log an error to the Logs under the Monitor source instead of crashing the panel.

Stats Bar

The bottom of the panel shows summary statistics:

  • Topics — total topics discovered in the last scan
  • Monitoring — how many topics are actively subscribed
  • Total Messages — messages received across all monitored topics

Bug Fixes (v3.9.3)

  • Alphabetical sort — topics are sorted alphabetically within each namespace group
  • Working Publishers / Subscribers filter — previously dead; implemented via node.count_publishers() / node.count_subscribers()
  • Fractional Hz — rolling 5 s window replaces the old 1-second integer-only count
  • No per-tick full rebuild — rate ticks patch only the Hz cell instead of recreating every row
  • Stop-monitoring cleanup — _stop_monitoring removes all per-topic dict entries (topic_rates, topic_msg_count, topic_last_msg, topic_cached_msg) to prevent memory leaks
  • Persisted favourites — monitored topics survive restart

Terminal Equivalents

The Topic Monitor provides a GUI alternative to these terminal commands (topic names follow the flat robot{N}_ convention for controller topics and the robot{N}_simulation/ prefix for simulator topics — see Topics for the full reference):

# List all topics (equivalent to Refresh)
ros2 topic list -t

# Monitor a topic's rate (equivalent to Hz column, without the 20 Hz cap)
ros2 topic hz /robot1_q_current

# Echo messages (equivalent to Raw Stream)
ros2 topic echo /robot1_simulation/joint_states

# Get publisher / subscriber counts (equivalent to role filter)
ros2 topic info /robot1_q_current --verbose
