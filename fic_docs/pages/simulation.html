Simulation (MuJoCo + fic_control)

Physics-accurate simulation with the fic_control ROS 2 control node.

How It Works

fic_control and the MuJoCo node are separate processes communicating over ROS 2 topics. MuJoCo handles physics stepping and 3D rendering; fic_control handles FIC control. All simulation topics are scoped by station id: the simulator node publishes under robot{N}_simulation/ (its topic_prefix parameter, set by the launch file from station_id, 1–4), and the controller subscribes to the same prefix via its source_prefix parameter. This keeps multiple side-by-side stations from cross-talking — see Topics. For behavioural differences from the hardware node, see Sim vs Hardware.

Starting Simulation

  1. Select the robot from the toolbar dropdown.
  2. Set Target to Simulation and press ▶ Start. This launches the simulator (MuJoCo on the CPU, package mujoco_native, by default; see Settings → Simulation for the Newton backend below), with a gripper bridge helper alongside it to drive the scene's gripper actuator, if present, from robot{N}_gripper_width.
  3. About 2 s later the fic_control control node auto-starts with source_prefix:=robot{N}_simulation.
  4. The SIM and FIC status LEDs turn green. (There is a single Start/Stop button, not one per process — see Processes.)

Both processes are managed by the GUI — see Processes for logs and manual start/stop.

Torque Output

Every torque passes an output guard before publishing: non-finite values are replaced with 0 and each joint is clamped to its physical limit from fic_library/config/robots_config.yaml (joint_torque_max; fallback ceiling 150 N·m when a robot has no per-joint entry). If the Safety panel's velocity limits are enabled, a velocity damping term is added on top, scaled so the damping torque saturates exactly at the joint's torque limit when the joint reaches max_joint_velocity:

kd[i]   = torque_limit[i] / max_joint_velocity
tau[i]  = clamp(fic_torque[i] − kd[i] × joint_velocity[i], ±torque_limit[i])

A robot driven in simulation uses its config's sim_max_joint_vel when it has one (see Safety). The Kinova Gen3 model's joints have a viscous damping of 5 N·m·s/rad (its wall scenes keep 45).

With velocity limits disabled, torques are published undamped (guarded and clamped only). This replaced the old fixed −10·q̇ damping term during the June 2026 safety remediation — see Safety.

Control Loop (1 kHz)

  1. Guard — skip until a robot and joint count have been received and the Pinocchio model is loaded
  2. Snapshot state (under mutex) → release mutex before computing
  3. Detect mode change → reset init flag (also reset by the hpmp toggle, robot selection, and new joint targets)
  4. Compute EE velocity = Jacobian × q̇
  5. Initialise controllers when the init flag is down — loads (robot, mode, profile) parameters from the installed config.xml (<fic_control share>/config/config.xml, installed from fic_library/config/config.xml). With hpmp active on modes 6/7/8, its joint and Cartesian parameters load from the H-PMP block (<mode id="100">; modes 4 and 6 on a robot without one)
  6. Compute FIC torques per joint/axis; modes 1–4 and hpmp add MuJoCo's gravity torque g(q) on top (the FIC law has no gravity term), and in modes 3/4 it is also the commanded effort the interaction torque is measured against
  7. Apply null-space helpers (postural / elbow) on Cartesian modes if enabled
  8. Hard-fault check — if any joint exceeds the config's physical position limits, latch a fault and output gravity compensation only until a new robot is loaded
  9. Output guard, optional velocity damping, then publish trajectory_data, torque commands, actuator commands

Inverse Kinematics

Iterative damped Jacobian pseudo-inverse using Pinocchio. It runs asynchronously in a detached thread on each incoming Cartesian target, so the 1 kHz loop never waits for it. Its result, q_target_ik, is hpmp's joint set-point and the target of the postural/elbow null-space helpers:

ParameterValue
Convergence1e-6 (SE3 log-map error norm)
Max iterations5000
Step size (DT)0.01
Damping1e-6 on J·Jᵀ diagonal
Per-step velocity clamp0.5 (norm of the update)

Higher precision than the hardware node (1e-6 vs 1e-4, 5000 vs 1000 iterations) since it is off the real-time path.

Important Notes

  • Start-up mode is 1 (Joint Impedance) until the GUI publishes a mode on robot{N}_control_mode — see Control Modes
  • Gravity torques prefer MuJoCo's (they include gripper/attachment mass from the scene). Pinocchio's computeGeneralizedGravity (arm-only URDF) is used only as a fallback until the first MuJoCo gravity message arrives
  • Trajectory data is N×8 (hardware is N×5 — extra channels for the autotuner)
  • Robot selection reloads the controller's Pinocchio model and config — avoid during active control. The MuJoCo scene itself does not follow: switching robots restarts the simulator process (the GUI does this when you toggle SIM)
  • Every mode switch snaps targets to the current state (joint targets in modes 1–4, EE pose in modes 5–8) so the robot holds position instead of jumping to a stale target

Scenes, Models and Reset

The simulator node loads its MJCF scene from the simulation/model_file ROS parameter, which the launch file resolves from robot_name:= against the menagerie package:

robot_nameScene file (menagerie share)
Franka_FR3model/Franka_FR3/xml/scene.xml
KinovaGen3_7DOFmodel/KinovaGen3_7DOF/xml/scene.xml
IIWA_14model/IIWA_14/XML/scene.xml
Pendulummodel/Pendulum/xml/pendulum.xml

Any other robot runs from its config's mujoco_xml_path: the Studio passes it as model_file:=, so the launch map needs no entry. .xml/.urdf scenes and compiled .mjb models load; the mujoco wheel's bundled plugins (e.g. the cable model) are available without setup.

Start pose. A fixed-base arm starts with every joint at 0 unless its robot config sets sim_start_at_home: true (the Kinova Gen3 does): it then spawns at its q_home_rad and is held there until the first actuator command, so the controller starts at home instead of swinging the arm to it. The Studio passes the pose as the launch argument initial_joint_positions:=q1,q2,... (radians, the first joints in model order), which both backends accept.

The parameter is read once at startup on both backends — there is no runtime model hot-reload, so switching robots means stopping and relaunching SIM (which the toolbar button does for you). In multi-robot scenes, MuJoCo element names carry an r1_/r2_ prefix; the controller's joint_name_prefix parameter matches its joints against those names, and the F/T publisher falls back to scanning for any sensor whose name ends in force_sensor/torque_sensor.

Reset service: robot{N}_simulation/sim_reset (communication/srv/SimulationReset) resets the MuJoCo state, applies the requested base pose (floating-base models only) and named joint positions, and clears the actuator commands. The request's header.frame_id must equal the loaded model's name (e.g. KinovaGen3_7DOF scene) or the reset is refused.

ros2 service call /robot1_simulation/sim_reset communication/srv/SimulationReset \
  "{header: {frame_id: 'KinovaGen3_7DOF scene'}, joint_state: {name: [Actuator2, Actuator4], position: [0.5, 1.0]}}"

Simulator rates and timing

TopicRate
joint_states, gravity_torques1 kHz (publish_rate_hz)
imu_data500 Hz
force_torque, body_poses200 Hz
odom50 Hz

Physics steps at the MJCF's own timestep (1 ms for the arms; override with the sim_dt launch argument), paced to the wall clock. Rates are capped by the physics rate. In the viewer, Space pauses and resumes and Backspace resets to the spawn state.

A dead controller leaves the arm limp

A torque command the controller stops refreshing for 0.2 s is zeroed, so if the FIC controller dies the simulated arm falls under gravity instead of pushing on with its last torque. Position-type actuators (the Robotiq gripper) keep their last setpoint, because the gripper bridge publishes only when the width changes. Several publishers can share actuators_cmds (the controller and the gripper bridge, or one controller per robot of a multi-robot scene); commands are merged per actuator name.

Safety Enforcement in Simulation

Since the June 2026 safety remediation, fic_control enforces the Safety panel limits itself, not just in the GUI:

  • Target clamping — Cartesian targets are clamped to the enabled zone; joint targets are clamped to joint limits and rejected if forward kinematics would place the EE outside the Cartesian zone.
  • Virtual wall — in joint modes, an EE past an enabled Cartesian boundary gets a restoring force (2000 N/m) mapped through Jᵀ, bounding the robot at the limit.
  • Velocity limits — enable the per-joint damping term in the torque pipeline above.
  • Hard-fault latch — a joint beyond its physical config limits switches output to gravity compensation only until a robot reload.
  • Output torque guard — NaN/Inf → 0, per-joint clamp on everything published.

Simulator Backends: MuJoCo (CPU) vs MuJoCo Newton (GPU)

The SIM button can launch one of two backends. The choice lives in Settings → Simulation and is persisted to ~/.robot_selector_gui_settings.yaml as simulation.backend:

Backendbackend valueLaunch packageEngine versionHardware
MuJoCo (default)mujoco_nativemujoco_native (Python)the installed mujoco wheel (the Docker image pins 3.10.0)CPU: Linux x86-64 and arm64, macOS
MuJoCo Newton (optional)newtonmujoco_newton (Python)newton 1.3.0 + mujoco-warp 3.8.1 (pip mujoco 3.8.1)NVIDIA GPU (CUDA via Warp)
The C++ mujoco package was retired in v4.5.0

Until v4.5.0 the default on Linux x86-64 was a C++ simulator (fic_ws/src/mujoco, DeepMind's simulate linked against a vendored x86-64 libmujoco), and mujoco_native served macOS, arm64 and floating-base robots. Its features (1 kHz state, IMU, F/T with prefixed sensors, the sim_reset service, multi-publisher commands, pause/reset in the viewer) were ported into mujoco_native, which is now the only CPU simulator. A saved backend: mujoco loads as mujoco_native.

How dispatch works

process_mixin._start_simulation() reads the backend setting and runs one of:

ros2 launch mujoco_native simulation_launch.py robot_name:=<robot> station_id:=<N> model_file:=<scene>
ros2 launch mujoco_newton simulation_launch.py robot_name:=<robot> station_id:=<N> model_file:=<scene>

A robot whose config sets sim_backend (mujoco_native or newton) uses that backend whatever the setting says.

Both launch files accept the same robot_name:= argument and end up publishing the same five topics (joint_states, odom, imu_data, gravity_torques, force_torque) and subscribing to actuators_cmds — so the FIC controller node sees the same interface either way. If Newton is selected but the mujoco_newton package isn't built (e.g. you toggled the setting before running colcon build), the dispatcher logs a WARN and falls back to the CPU simulator.

The Newton backend (mujoco_newton)

NVIDIA Newton (currently 1.3.0, with mujoco-warp 3.8.1 and warp-lang 1.14) is a Python-first physics engine built on NVIDIA Warp (JIT-compiled CUDA kernels). The SolverMuJoCo Newton ships is MuJoCo's solver running on Warp — physics behaviour matches MuJoCo, but stepping happens on the GPU. The mujoco_newton ROS 2 package wraps that solver in a node with the same topic contract as the CPU simulator:

Newton publishes empty IMU / F-T messages

Newton's SolverMuJoCo doesn't expose mjData->sensordata, so IMU and force-torque stay zeroed on the Newton backend. Subscribers that gate on magnitude are unaffected; subscribers that need real IMU or F-T data should run the CPU simulator. Gravity torques are real on both backends.

Known limitations of the Newton backend

  • First launch JIT-compiles 30–60 s of CUDA kernels for mesh-heavy MJCFs (Kinova, Franka), then caches them in ~/.cache/warp/. The SIM button shows "running" during this window but no viewer appears yet. Subsequent launches load from cache and the viewer comes up within ~3 s. Tail /tmp/fic_sim_mujoco_newton_*.log if you want to watch progress.
  • MJCF compatibility is per-file. Newton's importer uses Python's strict xml.etree.ElementTree, while libmujoco's C parser is forgiving. Expect to occasionally fix XML quirks on new robots — e.g. class="X"pos="0 0 0" (no space between attributes) loads fine in MuJoCo but trips Newton with not well-formed (invalid token).
  • IMU and F-T topics carry empty payloads (see the parity table above — gravity torques are real). Switch to the CPU simulator if you need IMU or force-torque data.
  • pyglet ≥ 2.0 is required for Newton's OpenGL viewer. Without it, Newton runs successfully but headless and you'll see "Falling back to headless mode: OpenGLRenderer requires pyglet (version >= 2.0) to be installed" in /tmp/fic_sim_mujoco_newton_*.log. The installer pulls pyglet automatically; for manual setups: pip install --break-system-packages 'pyglet>=2.0'.
  • Headless when $DISPLAY is unavailable. Over SSH without X-forwarding, ViewerGL falls back to headless with a WARN.

Diagnosing failed launches

If the SIM button toggles to "running" but no window opens, the dispatcher writes the subprocess's combined stdout/stderr to /tmp/fic_sim_<backend>_<timestamp>.log (path is logged to the Logs at launch time). A QTimer-based health check fires after a warmup window — 2 s for the CPU simulator, 8 s for Newton (JIT compilation) — and if the subprocess has already died, the Log Viewer gets the last lines of the log and a modal dialog summarises the failure. While the subprocess is JIT-compiling kernels (alive but quiet), the health check passes and the dialog stays hidden.

When to use which

SituationBackend
Default workstation use, single robot, sequence playback, teleopMuJoCo (CPU)
You hit any of Newton's MJCF compatibility issuesMuJoCo (CPU)
You need real IMU or F-T sensor data in simulationMuJoCo (CPU)
You're running parallel-environment RL training (future)Newton (GPU)
You're benchmarking GPU sim throughput on simple MJCFsNewton (GPU)
Newton is groundwork, not a perf upgrade for teleop

For a single arm, Newton's GPU step is not faster end-to-end than the CPU MuJoCo loop on a modern CPU — the win shows up at hundreds of parallel envs. The Settings switch and matching topic contract are mostly about avoiding a rewrite later, when RL data generation becomes a real workflow.
