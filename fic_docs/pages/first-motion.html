Your First Motion — Validation Checklist

Run through this page the first time you use FIC Control Studio on a new machine, a new robot, or after a rebuild. It tells you, in order, how to know each layer of the stack is actually working before the next one goes live.

Do the simulation pass first

Never skip straight to hardware on a new setup. If simulation Modes 1, 2, and 5 don't behave correctly, hardware will misbehave in the same way — just with a real arm attached. See Simulation vs Hardware for what does and doesn't transfer.

Phase 0 — Environment sanity (once per machine)

  1. ROS 2 sourced. In a fresh terminal, ros2 --help should succeed without activation. If not, your ~/.bashrc isn't sourcing /opt/ros/$ROS_DISTRO/setup.bash. (The launcher script auto-detects and sources the newest distro under /opt/ros/ itself, but your own terminals still need it for debugging.)
  2. Workspace built. cd ~/FIC_Interface/fic_ws && colcon build --symlink-install finishes without errors. --symlink-install matters: the controller reads its tuning from the installed share/fic_simulation/config/config.xml, which is a symlink back to fic_library/config/config.xml only when you build this way — otherwise Tuning-panel saves need a rebuild to reach the controller.
  3. GUI launches. Run bash ~/FIC_Interface/fic_install/fic-control-studio.sh and confirm the main window appears. On the very first launch the setup wizard opens automatically (Welcome → Verify Workspace → Test Your Setup → Setup Complete); accept the defaults for now. See Installation.
  4. Status LEDs. The bottom status bar shows LEDs labelled ROS2, FIC, SIM, BAGS and TELEOP. ROS2 goes green as soon as the GUI's node is up; FIC and SIM stay idle until you launch those processes in Phase 1.

Phase 1 — Simulation baseline

  1. Pick the correct robot. Toolbar robot dropdown → the robot you intend to validate (Franka_FR3, KinovaGen3_7DOF, IIWA_14 or Pendulum). The robot name selects the URDF, the MJCF scene and the config.xml section; everything downstream breaks silently if this is wrong. The dropdown locks while a session is running.
  2. Launch the simulation session. In the toolbar set Target to Simulation and click ▶ Start. This launches the MuJoCo simulation node (a 3D viewer window opens with the robot in its home pose) and auto-starts the FIC controller about 2 s later. The SIM and FIC status LEDs turn green. Equivalent menu items: Simulation → Launch Sim + FIC (F7), or individually Toggle Simulation (F5) and Toggle FIC Controller (F6).
  3. Select a test mode. Open the Control Panel and click the Joint Planner mode tab (Mode 2, Joint Impedance With Planner). Clicking a mode tab publishes immediately — there is no separate "send mode" step. On engage the controller snaps its targets to the robot's current state, so the arm holds position instead of jumping.
  4. Verify the robot holds against perturbation. In the MuJoCo viewer, double-click a link to select it, then hold Ctrl and right-drag to pull it (Ctrl + left-drag applies a rotation), and release. The arm should recover to its target under FIC control. If it collapses or drifts, the controller isn't actually running — see the debugging tip below.
  5. Test a commanded motion. In the joint target fields, increase J4 by +10° and click ▶ Send command (or tick Live publish to stream edits as you type). The arm should ramp smoothly to the new pose. No overshoot, no oscillation.
  6. Watch the planner output. Click ▶ PLT in the toolbar to launch the live plotter (ros2 run fic_simulation plotter_node.py). It plots per-joint current vs dashed target curves from robot1_trajectory_data; they should converge within about a second. For raw values you can also watch the topic in the Topic Monitor. If current never reaches target, check the planner's Vel Desired field in the Tuning panel.
Sanity check for Mode 1

Mode 1 (Joint Impedance) has no velocity damping — commanding it as your first test can mask other problems because oscillation looks like a controller bug. Use Mode 2 for the first motion; drop to Mode 1 only once Mode 2 is clean. See Control Modes.

If nothing moves: where the logs are

The simulation subprocess writes to /tmp/fic_sim_<package>_<timestamp>.log (the exact path is printed in the Logs when the sim starts). If the sim dies during startup, Studio flips the Start button back and prints the last log lines automatically. On the Newton backend (Settings → Simulation) the first launch JIT-compiles GPU kernels for several seconds — Studio waits 8 s before declaring it dead, so give it time. See Simulation.

Phase 2 — Tuning sanity

  1. Open the Tuning panel. Confirm the parameters for the mode you just tested load without warnings in the log. Joint modes show per-joint stiffness K₀, Error Max breakpoints, Force Max ceilings and the planner group (Vel Desired, Damping Ratio).
  2. Nudge stiffness. Halve K₀ for one joint, and click SAVE TO XML — the save tells the controller to read config.xml again, and it switches to the new values a few tens of milliseconds later without leaving the mode. The arm should feel visibly softer on the next commanded motion. Restore the value when done.
  3. Break it on purpose. Set an obviously-too-high K₀; the joint should oscillate on the next motion. This confirms the Tuning panel actually reaches the running controller — if it doesn't, you built without --symlink-install (see Phase 0).

Phase 3 — Cartesian baseline

  1. Switch to Mode 5. Click the Cart Imp tab (Cartesian Impedance). The control area rebuilds from joint fields to EE pose fields automatically.
  2. Hold the EE pose. Don't command anything — the controller snapped the Cartesian target to the current EE pose on engage, so just confirm the arm holds it. Perturb a mid-chain link in the viewer; the EE should recover but the elbow may "swim" in the null space.
  3. Enable postural. In the Control Panel's Null-space row, tick Postural. Perturb the elbow again — it should return to the IK-preferred configuration without the EE moving noticeably. (The row also has Elbow, H-PMP and Admittance Planner toggles; Postural and Elbow both work in every Cartesian mode, the admittance Modes 7/8 included. See H-PMP.)
  4. Commanded EE step. Offset the Cartesian target by 5 cm in one axis and click ▶ Send command. The EE should move smoothly, not jump.

Phase 4 — Pre-hardware checklist

Do every item on this list before powering a real robot.

  • ☐ Phases 1–3 above all pass on this machine for this robot.
  • ☐ E-Stop works. In simulation, press Space (or the toolbar ■ E-STOP button). Studio commands a graceful Stop Controller ramp to every active robot, waits ~250 ms for the torque ramp-down, then kills all Studio-launched processes (with an OS-level pkill backstop for the hardware controllers). The status label reads E-STOP ACTIVE - ALL PROCESSES KILLED. See Emergency Stop.
  • ☐ Safety limits set and ENABLED. Open the sidebar Safety page (or Robot Config → Safety Zones tab) and set joint, velocity and Cartesian-zone limits that match your physical cell. Per-robot zones ship disabled in fic_studio_robots.yaml — tick their enable boxes. Limits are published on robot{N}_safety/cartesian_limits, …/joint_limits and …/velocity_limits; the C++ control loop enforces them (virtual-wall force at Cartesian bounds, joint-target clamping, out-of-zone target rejection), and the GUI runs a 10 Hz check that commands a graceful stop if the robot is actually past a limit. See Safety.
  • ☐ You know where the physical E-Stop is. Within arm's reach of wherever you'll be standing.
  • ☐ Low stiffness for first motion. Halve the K₀ values that Phase 2 validated. You can ramp back up once the arm tracks cleanly.
  • ☐ Nobody in the workspace. Clear the robot's full reach envelope, not just the current target.
  • ☐ Vendor driver tested. Start the driver alone (menu Simulation → Toggle Robot Driver, F9 — do not use the combined ▶ Start yet) and confirm gravity compensation holds the arm without drift. The driver command per robot lives in Robot Config → File Paths (e.g. the libfranka cartesian_impedance_control example for Franka_FR3, the Kortex torque-control example for KinovaGen3_7DOF).

Phase 5 — First hardware motion

  1. Start the vendor driver. F9 (as validated in Phase 4). Wait until joint positions appear on robot1_q_current in the Topic Monitor.
  2. Start the FIC hardware controller. F8 (Simulation → Toggle Controller). It starts passive — no mode is engaged, the arm is held only by the driver's gravity compensation and should sag slightly. (Once you trust the pair, toolbar Target = Hardware + ▶ Start launches driver-then-controller in one click.)
  3. Engage Mode 2 with zero delta. Click the Joint Planner tab without commanding a new target. The controller snaps its target to the current pose on engage, so the arm should hold; joint errors in the plotter should be near zero.
  4. Command a small motion. One joint, 5° change, then ▶ Send command. Watch the physical arm and the robot1_trajectory_data plot — they should track within the bandwidth your stiffness allows.
  5. Scale up gradually. Larger angles, then multi-joint, then Cartesian. Never skip directly to haptic / admittance modes (3, 4, 7, 8) on a new setup.
Red flag behaviours
  • Arm oscillates on mode engage. Stiffness too high for the damping available. Drop K₀; use Mode 2 over Mode 1.
  • Arm drifts slowly in one direction. Gravity model mismatch — check the URDF payload / tool mass in Robot Config.
  • Arm jumps right after entering a mode. The controller snaps targets to the current state on engage, so a jump means a stale or streaming target arrived immediately afterwards — untick Live publish, and check nothing else (script, gamepad, teleop) is publishing targets.
  • Joint torques saturate at rest. K₀ much too high, or your error is larger than the last error_max breakpoint (FIC is in its final saturation stage even near zero commanded delta). See Glossary → Saturation stage.
