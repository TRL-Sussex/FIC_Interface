Simulation vs. Hardware

One control node and one joint inner loop drive both the simulator and the real arm; what differs is the plant behind the inner loop. When to reach for each target, and what still differs between them.

One node, two targets

Every setup runs the same two layers. The task-space layer is the fic_control node: it runs the fic_library control law, the kinematics and the safety checks, and sends the inner loop one CMD per tick over FIC-link (UDP). The joint layer is fic_inner_loop, a separate process: it runs the joint modes, H-PMP's split drive, the target slew, the hold-and-ramp when the task layer goes quiet, and the E-STOP latch. The node's target parameter picks the plant behind the inner loop; both targets read the same config.xml (from the fic_control package share).

The simulation-only topics

robot{N}_control_mode (Int32) and robot{N}_target_joint_angles (JointState) are the simulator's older topics; the experiment suite and several extensions publish them. Only the simulation target listens to them, so a simulation tool pointed at the wrong station cannot move a real arm. FIC Studio publishes every mode change on both mode topics. In a new script, use robot{N}_mode_select and robot{N}_desired_joint_angles: they work on both targets. The string names are listed on the Control Modes page.

Which simulator backend?

The SIM button launches either the CPU MuJoCo simulator (mujoco_native, with its viewer) or the optional Newton GPU backend, depending on Settings → Simulation → backend. The node and the inner loop are identical in both cases. On Newton the force_torque and IMU messages are empty, and physics runs at 500 Hz with a 200 Hz publish rate instead of ~1 kHz. Details on the Simulation page.

The simulator's gravity vector goes straight into the control law

Note the preference in the table above: the simulation target uses the simulator's published gravity_torques ahead of its own solver's, and adds it raw to the control law's output in the joint modes. A wrong vector there is not a cosmetic reporting problem — it is injected feedforward on every joint, every cycle.

That is exactly what happened until Oct 2026: the C++ node computed gravity with mj_forward → mj_inverse → qfrc_inverse after zeroing qvel/qacc, but mj_forward recomputes qacc from d->ctrl, so the published “gravity” was the actuator command itself and the loop had unity gain. It now reads qfrc_bias at zero velocity, which is g(q) exactly.

The Newton backend still uses the old recipe (mujoco_newton/simulation_node.py), and has not been re-measured since. Treat Newton gravity as suspect until it has been.

A one-minute check for any backend: pick a joint whose axis is vertical (on the Kinova Gen3, joint 0). Gravity exerts no moment about a vertical axis in any pose, so its entry in gravity_torques must be ~0 Nm whatever the arm is doing. If it is not, the vector is not gravity.

Simulating like the real robot

An ideal simulator makes tunes that do not hold on the arm. On the Kinova (October 2026) H-PMP on modes 7 and 8 held still in simulation and oscillated on the robot, and Cartesian Admittance (mode 7) yielded much less on the robot than in simulation. Simulation and hardware ran the same controller; what differed was what the controller measured:

  • The push the admittance sees. Both targets estimate the end-effector wrench from the measured joint torque less gravity. On the robot that torque also carries the joints' friction: moving at 10–20 mm/s with nothing touching it, the Kinova's estimate showed about 2 N along the motion, and 0.2–0.4 N of noise at rest. The ideal simulator's measured torque is its own command, with a little viscous damping and no noise, and H-PMP's task-space admittance (modes 7/8) was given MuJoCo's exact contact force instead of an estimate.
  • The filter. The simulator filtered the measured torque at 10 Hz, the robot at 200 Hz.
  • The deadbands and the velocity damper. H-PMP's task deadband was the library's 1 N in simulation and the robot's 4 N on the arm; the simulator ran the weaker sim_max_joint_vel damper.

A robot's hardware_model block in robots_config.yaml closes these gaps. With it on, the simulator gives the arm's joints the measured friction, damping and rotor inertia and adds the torque-sensor noise and command delay (mujoco_native/hardware_model.py), and the simulation target measures torque as the hardware target does: the robot's filter, H-PMP's push estimated from the joint torques, the robot's H-PMP task deadband (the arm's own Cartesian force deadband, cart_force_hardware, when the robot has one) and its velocity damper. The Studio's simulation then also runs the tuning the arm runs (the default config) instead of the robot's simulation-only sim config, so what you try in simulation is what goes on the robot. A robot without the block, or with enabled: false, is simulated as before.

Measuring a robot

With the controller running on the real robot (Hardware target) and room for each joint to swing 10° either way, run on its PC:

python3 -m fic_studio.hardware_model --env hardware --robot KinovaGen3_7DOF --write

The arm holds still for 4 s (the noise), then swings one joint at a time through a slow sine about where it started, in Joint Impedance (about 4½ min for 7 joints, a warm-up swing first for each). The measured joint torque less the URDF's inverse dynamics gives each joint's friction, damping and rotor inertia; --write puts the block into robots_config.yaml and the Studio's robot list (only that block: the rest of each file is kept), and the run folder keeps the recording and the fit. --joints 2,4 measures some joints only, --amplitude-deg sets the swing; from another computer, run it over SSH on the robot's PC. On the simulator (--env sim) it returned the model's damping within 9 % and its friction within 27 %. Its rotor-inertia fit also takes up any difference between the URDF's link inertias and the MuJoCo model's (0.06–0.34 kg·m² for 0.01 on the Kinova), so it is written only with --fit-armature.

Switching it off

enabled: false (or the switch on the Hardware tab) for the robot, or FIC_HARDWARE_MODEL=off in the environment of one simulator run: both mujoco_native and the node read it. Results made with the ideal simulator are reproduced that way.

What it does not model yet

  • Joint elasticity (the harmonic drive and the torque sensor are springs on the real arm) and the robot's own loop latency; command_delay_ms is there for the latter once it is measured.
  • The gravity model's error: the real Kinova's push estimate reads about 2 N down at rest with nothing touching it (the gripper's modelled mass), the simulator's none.

The Kinova's block (October 2026) has the torque noise measured at rest on Robot1 and friction estimated from that day's wall runs; replace it with a measurement. With the Kinova's block on, the October default H-PMP tuning showed a small residual oscillation on mode 7 in simulation, and the default was changed to remove it (see Changelog, 5.7.0); the robot's own instability on modes 7/8 has not yet been reproduced in simulation, so check a new tuning on the arm.

When to use which

  • Developing a new behaviour, new script, or new tuning? Start in simulation. Free to crash without physical damage, full topic visibility, fast iteration.
  • Validating contact / admittance / dynamics? Simulation is approximate — MuJoCo models friction and contact, but real rigidity and backlash are not captured; simulate the robot like the real one (its hardware_model) so tunes carry over. Once a behaviour is stable in sim, re-validate on hardware starting from a lower stiffness (K0) than you used in sim — see Tuning.
  • Teaching / recording waypoints? Hardware, via Teach Mode. Simulation teach mode works but you lose the kinesthetic signal that makes teach mode useful.
  • Teleoperation? Both peers should run hardware nodes when possible; sim on one side is a useful dry-run but the force feedback then comes from the simulated arm (its wrench estimated from the simulated joint torques, or the simulated F/T sensor with wrench_from_api), not from physical sensing. See Teleoperation.

Why shared memory on hardware?

Two reasons:

  1. Latency. ROS 2 DDS serialises every message; at 1 kHz with 7-axis torque traffic, that overhead shows up as jitter in the control loop. Atomic reads/writes against a mapped page skip the serialiser entirely.
  2. Process isolation. Vendor drivers (libfranka, Kortex) run in their own real-time processes and bring their own threading and timing constraints. A shared-memory bridge lets FIC co-exist without inheriting the driver's threading model.

Two segments are defined in fic_library/include/fic/shared_params.h: /dev/shm/robot_feedback_memory (measured torques and positions, commanded torques, tool_wrench[6], gripper width, the stop_torque_mode flag) and /dev/shm/desired_joint_angles_memory. Each reserves 16 joint slots (kMaxJoints) — the runtime n_joints field says how many are active, so 7-DOF arms and future dual-arm setups share one layout. The header carries a magic ("FICS") and layout version; a segment whose size doesn't match is unlinked and recreated on open, so a stale segment from an older build can't silently alias the new struct. On the hardware target only fic_inner_loop maps the feedback segment; the node talks to the inner loop over FIC-link. Simulation uses the same FIC-link messages to the simulator instead (SimStep and SimTorque).

Stale shared-memory segments

If you see [shared_params] … magic/version mismatch or feedback that never updates, stop the FIC node, fic_inner_loop and the driver, delete the segments (rm /dev/shm/robot_feedback_memory /dev/shm/desired_joint_angles_memory), and restart. Bumping kMaxJoints or changing the struct layout requires rebuilding every process that maps the segments — fic_inner_loop and all vendor driver bridges.

Switching targets safely

  1. Stop FIC. On hardware, sending "Stop Controller" first is gentler: the inner loop ramps torques toward the gravity baseline and then sets stop_torque_mode in shared memory so the driver exits torque mode cleanly.
  2. Stop whichever backend is running (SIM or API).
  3. Change the robot dropdown if needed. The node reloads the URDF live on robot{N}_selected_robot, but the simulator scene and vendor driver do not follow — a controller model that doesn't match the running backend produces wrong Jacobians and torques, so always stop the backend first.
  4. Start the new backend.
  5. Start FIC for the new target.

Note that the hardware target refuses robots whose config lacks is_supported: true in robots_config.yaml — KUKA IIWA 14 and Pendulum are simulation-only. See Robot Configuration for the flag and the per-robot driver_command, and Safety / E-STOP for what happens on an emergency stop.

A simulation and a real robot on one computer

They run side by side on different stations: each simulated station has its own inner loop (127.0.0.1:7200+N), and the real robot's is 127.0.0.1:7360. The node refuses an inner loop that another node already drives. Two nodes on the same station still conflict: both publish robot{N}_trajectory_data and both react to that station's modes and targets.
