Simulation vs. Hardware

Why the same stack has two different control nodes, and when to reach for each — plus why one talks over ROS topics while the other talks over POSIX shared memory.

Two nodes, one algorithm

The GUI publishes to both mode topics

Because the GUI doesn't know in advance whether you'll run sim or hardware, ros_node.py publishes every mode change to both robot{N}_control_mode (Int32) and robot{N}_mode_select (the matching String name). That's why switching modes "just works" regardless of which FIC node is listening — but if you're writing a custom script, pick the topic that matches your target. The string names are listed on the Control Modes page.

Which simulator backend?

The SIM button launches either the CPU MuJoCo simulator (mujoco_native, with its viewer) or the optional Newton GPU backend, depending on Settings → Simulation → backend. The FIC node is identical in both cases. On Newton the force_torque and IMU messages are empty, and physics runs at 500 Hz with a 200 Hz publish rate instead of ~1 kHz. Details on the Simulation page.

The simulator's gravity vector goes straight into the control law

Note the preference in the table above: fic_simulation uses the simulator's published gravity_torques ahead of its own solver's, and adds it raw to the control law's output in the joint modes. A wrong vector there is not a cosmetic reporting problem — it is injected feedforward on every joint, every cycle.

That is exactly what happened until Oct 2026: the C++ node computed gravity with mj_forward → mj_inverse → qfrc_inverse after zeroing qvel/qacc, but mj_forward recomputes qacc from d->ctrl, so the published “gravity” was the actuator command itself and the loop had unity gain. It now reads qfrc_bias at zero velocity, which is g(q) exactly.

The Newton backend still uses the old recipe (mujoco_newton/simulation_node.py), and has not been re-measured since. Treat Newton gravity as suspect until it has been.

A one-minute check for any backend: pick a joint whose axis is vertical (on the Kinova Gen3, joint 0). Gravity exerts no moment about a vertical axis in any pose, so its entry in gravity_torques must be ~0 Nm whatever the arm is doing. If it is not, the vector is not gravity.

When to use which

  • Developing a new behaviour, new script, or new tuning? Start in simulation. Free to crash without physical damage, full topic visibility, fast iteration.
  • Validating contact / admittance / dynamics? Simulation is approximate — MuJoCo models friction and contact, but real rigidity and backlash are not captured. Once a behaviour is stable in sim, re-validate on hardware starting from a lower stiffness (K0) than you used in sim — see Tuning.
  • Teaching / recording waypoints? Hardware, via Teach Mode. Simulation teach mode works but you lose the kinesthetic signal that makes teach mode useful.
  • Teleoperation? Both peers should run hardware nodes when possible; sim on one side is a useful dry-run but the force feedback then comes from the simulated arm (its wrench estimated from the simulated joint torques, or the simulated F/T sensor with wrench_from_api), not from physical sensing. See Teleoperation.

Why shared memory on hardware?

Two reasons:

  1. Latency. ROS 2 DDS serialises every message; at 1 kHz with 7-axis torque traffic, that overhead shows up as jitter in the control loop. Atomic reads/writes against a mapped page skip the serialiser entirely.
  2. Process isolation. Vendor drivers (libfranka, Kortex) run in their own real-time processes and bring their own threading and timing constraints. A shared-memory bridge lets FIC co-exist without inheriting the driver's threading model.

Two segments are defined in fic_library/include/fic/shared_params.h: /dev/shm/robot_feedback_memory (measured torques and positions, commanded torques, tool_wrench[6], gripper width, the stop_torque_mode flag) and /dev/shm/desired_joint_angles_memory. Each reserves 16 joint slots (kMaxJoints) — the runtime n_joints field says how many are active, so 7-DOF arms and future dual-arm setups share one layout. The header carries a magic ("FICS") and layout version; a segment whose size doesn't match is unlinked and recreated on open, so a stale segment from an older build can't silently alias the new struct. Simulation, which isn't latency-sensitive in the same way, uses ROS topics and scales with the joint count from the URDF.

Stale shared-memory segments

If you see [shared_params] … magic/version mismatch or feedback that never updates, stop the FIC node and the driver, delete the segments (rm /dev/shm/robot_feedback_memory /dev/shm/desired_joint_angles_memory), and restart. Bumping kMaxJoints or changing the struct layout requires rebuilding every process that maps the segments — fic_hardware and all vendor driver bridges.

Switching targets safely

  1. Stop FIC (both sim and hardware variants). On hardware, sending "Stop Controller" first is gentler: the node ramps torques toward the gravity baseline (~200 ms time constant) and then sets stop_torque_mode in shared memory so the driver exits torque mode cleanly.
  2. Stop whichever backend is running (SIM or API).
  3. Change the robot dropdown if needed. Both FIC nodes reload the URDF live on robot{N}_selected_robot, but the simulator scene and vendor driver do not follow — a controller model that doesn't match the running backend produces wrong Jacobians and torques, so always stop the backend first.
  4. Start the new backend.
  5. Start FIC for the new target.

Note that fic_hardware refuses robots whose config lacks is_supported: true in robots_config.yaml — KUKA IIWA 14 and Pendulum are simulation-only. See Robot Configuration for the flag and the per-robot driver_command, and Safety / E-STOP for what happens on an emergency stop.

Don't run both FIC nodes at once

If fic_simulation and fic_hardware run simultaneously with the same station ID, both will publish to robot{N}_trajectory_data and both will react to commanded modes and targets. The control loop won't be deterministic. Stop one before starting the other.
