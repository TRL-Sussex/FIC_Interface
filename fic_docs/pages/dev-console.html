FIC Dev Console

Lightweight hardware-focused GUI for direct robot control and teleoperation.

What is Dev Console?

The FIC Dev Console is a stripped-down version of FIC Control Studio designed to run on a second PC sitting next to a real robot. It removes simulation, scripting, experiments, and dashboard panels, keeping only what you need for hands-on hardware work. It is a separate entry point (fic_studio.entry_dev) that reuses the same mixins as the full studio — tuning, process management, publishers, settings, safety, and teleoperation.

When to use Dev Console

Use Dev Console when you have a dedicated robot workstation that only needs hardware control and teleoperation — no simulation, no scripting, no experiment logging. It starts faster and has a simpler UI that keeps the focus on the real robot.

Installation

Dev Console is part of the same FIC Studio package. During installation, the installer asks which mode to register:

  1. FIC Control Studio (Full) — the complete interface
  2. FIC Dev Console (Teleop) — the lightweight hardware GUI
  3. Both — registers both in your app launcher

To re-run the installer and change your choice (see Installation):

cd ~/FIC_Interface
bash install-fic-studio.sh

If you chose "Both", you will see two entries when you search for "FIC" in your app launcher.

Running from terminal

# Via launcher script
bash ~/FIC_Interface/fic_install/fic-dev-console.sh

# Direct ROS 2 command (workspace must be sourced)
ros2 run fic_studio fic_dev

On startup a splash screen loads settings from ~/.robot_selector_gui_settings.yaml (shared with the full studio). If ROS_DOMAIN_ID is not already set in the environment, the value from the settings key network.ros_domain_id is applied before ROS initialises. The ROS node is named fic_studio_<hostname>, so two instances on different machines in the same domain never collide.

Interface Overview

The Dev Console window has a toolbar at the top, four tabs in the centre (Control, Tuning, Teleoperation, Settings), and a collapsible log viewer at the bottom.

Running processes turn red and show a ■ icon. Idle processes show teal (orange for BAG/PLT, blue for VR) with a ▶ icon.

Status Bar

The bottom status bar shows LED indicators for ROS2, FIC, API, and BAGS processes, plus the currently selected robot name and DOF.

Tabs

1. Control Tab

The main tab for sending commands to the robot.

Joint Targets

One input field per joint (up to seven; fields beyond the selected robot's DOF are hidden), in degrees. Visible when the active control mode is joint-space (modes 1–4).

  • SEND JOINTS — converts values to radians and publishes to robot{N}_desired_joint_angles.
  • RESET TO HOME — fills the fields with the robot's q_home_deg values from fic_studio_robots.yaml.

Cartesian Targets

Six input fields: X, Y, Z (metres) and Rx, Ry, Rz (radians). Visible when the active control mode is Cartesian (modes 5–8).

  • SEND POSE — publishes the pose to command_ee_position_change_robot{N}. The Rx/Ry/Rz values are copied raw into the Pose orientation fields (no quaternion conversion in the Dev Console).
  • RESET TO HOME — fills the fields with the robot's default_ee_target from fic_studio_robots.yaml (position + orientation).
Automatic visibility

The joint and Cartesian groups toggle automatically when you change the control mode in the toolbar. Joint modes (1–4) show the joint fields; Cartesian modes (5–8) show the Cartesian fields.

Gripper

A width spinner (0–0.08 m, 0.005 m steps, default 0.04 m) with three buttons. All publish to robot{N}_gripper_width:

  • Send — publish the current spinner value
  • Open — set width to 0.08 m (fully open)
  • Close — set width to 0.0 m (fully closed)

Live Readout

Updated at 20 Hz from two station-prefixed ROS 2 topics:

TopicTypeData
robot{N}_trajectory_dataFloat64MultiArrayFull trajectory state (joints + EE position)
robot{N}_q_currentFloat32MultiArrayFallback joint positions only

Displays each joint angle in degrees and the end-effector XYZ position in metres. See Topics for the full topic reference.

2. Tuning Tab

Identical to the Manual Tuning panel in the full studio. Allows real-time adjustment of FIC parameters (stiffness, damping, etc.) per joint and per mode. Changes are sent immediately via ROS 2 topics.

3. Teleoperation Tab

Identical to the Teleoperation panel in the full studio. Supports bilateral master/slave teleoperation over DDS on the shared /teleop/ topics (/teleop/master_joints, /teleop/master_ee_pose, /teleop/slave_wrench, /teleop/latency), with joint mapping, bilateral force feedback, motion scaling, velocity limiting, EMA smoothing, and a data-flow connection monitor.

This is the primary use case for the Dev Console — place it on the robot's workstation as the slave, and control from the full studio on a separate master machine. The role is chosen explicitly with the Role dropdown (Master / Slave) before starting a session.

Typical teleop setup

Machine A (office/lab) runs FIC Control Studio as master.
Machine B (robot cell) runs FIC Dev Console as slave.
Both machines share the same ROS_DOMAIN_ID on the same network.

4. Settings Tab

Identical to the Settings panel in the full studio. Theme selection (Warm Dark / Warm Light), log viewer height, default robot, network settings, keyboard shortcuts, and the workspace build tools (Rebuild Workspace, Rebuild Package…, Clean Rebuild).

Typical Workflow

Direct Hardware Control

  1. Launch FIC Dev Console on the robot workstation.
  2. Select the robot from the toolbar dropdown.
  3. Click ▶ API to start the vendor driver — wait for the API LED to turn green. If a "No Driver Command" dialog appears, set the driver_command for the robot in the full studio's Robot Configuration editor (File Paths tab).
  4. Click ▶ FIC to start the hardware controller.
  5. Choose a control mode (e.g. 1: Joint Impedance) and click Send.
  6. On the Control tab, click RESET TO HOME to load the robot's home position, then click SEND JOINTS.
  7. Adjust FIC parameters on the Tuning tab as needed.
  8. Use ▶ BAG to record data and ▶ PLT to visualise it.

Teleoperation (Slave Side)

  1. Ensure the master machine (running full FIC Control Studio) is on the same network with the same ROS_DOMAIN_ID.
  2. Launch FIC Dev Console and start the driver + controller as above.
  3. Switch to the Teleoperation tab.
  4. Set the Role dropdown to Slave, then click START TELEOP. The console announces itself and the connection monitor shows the partner's machine ID, latency, and heartbeat once data flows.
  5. The master's joint commands are now forwarded to the real robot through the Dev Console.
  6. Enable Bilateral Force Feedback on the master to receive force feedback from the slave.
  7. Click STOP TELEOP to end the session.

Safety

The Dev Console runs the same safety system as the full studio (see Safety):

  • Zone limits per robot — when you select a robot, its safety_zones section from the robot configuration is loaded and broadcast to the controller on robot{N}_safety/cartesian_limits, robot{N}_safety/joint_limits, and robot{N}_safety/velocity_limits. The C++ control loop enforces Cartesian boundaries as a virtual wall (restoring force) and clamps joint targets at the limits.
  • GUI-side monitoring — a 10 Hz check compares the live joint positions and EE position against the loaded limits, warns when within 90% of a limit, and logs violations. As a backstop, an actual violation triggers a debounced graceful controller stop.
  • E-STOP — the red button in the toolbar (default keyboard shortcut Space, configurable under shortcuts in the settings file) stops the controller, driver, bag recorder, and plotter, publishes the current joint positions as a hold command, then force-kills any lingering controller processes.
  • Teleop safety — data-flow connection monitor (the slave freezes when the partner's data stops), max joint velocity limiting, EMA smoothing, motion scaling, and latency monitoring with a warning above 100 ms (see Teleoperation for details).
  • Process cleanup — every spawned process (driver, controller, bags, plotter, VR relay) is killed with its whole process group when the window closes, and children carry PR_SET_PDEATHSIG so they also die if the GUI crashes.
Always keep E-STOP accessible

When working with a real robot, keep the E-STOP button visible and your hand near its keyboard shortcut. Start with low stiffness and test movements incrementally.

Configuration

Dev Console reads the same configuration files as the full studio:

FilePurpose
fic_ws/src/fic_studio/fic_studio/fic_studio_robots.yaml GUI robot definitions: num_joints, q_home_deg, default_ee_target, driver_command, safety_zones
fic_library/config/config.xml FIC tuning parameters per robot per mode (see config.xml). On startup the Dev Console ensures an entry exists for every robot.
~/.robot_selector_gui_settings.yaml Shared GUI settings: theme, default robot, log viewer, station_id, ros_domain_id, keyboard shortcuts

Changes saved in the full studio's Robot Config editor are picked up by the Dev Console the next time it starts (robot configs are loaded once at startup).

Network Architecture

Bilateral teleoperation over DDS: the master publishes joint targets, the slave returns measured wrenches for force feedback.

ProblemFix
Dev Console not in launcherRe-run the installer and choose "FIC Dev Console" or "Both"

Joint fields show for Cartesian modeEnsure mode was sent (click Send after selecting)
Live readout stuck at 0Verify the FIC controller is running and publishing to robot{N}_trajectory_data (or robot{N}_q_current). Check the station id in settings matches the controller's.
Teleop not connectingCheck both machines have the same ROS_DOMAIN_ID and can ros2 topic list each other
E-STOP doesn't stop everythingCheck process names. E-STOP also runs pkill -9 -f cartesian_impedance_control as a fallback.
