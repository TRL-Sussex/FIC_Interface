Adding a Robot from its URDF

Drop a robot's URDF on the Robot Configuration page and it is ready to simulate a minute later: MuJoCo model, config entry and tuning built for you, no rebuild. Parallel (closed-loop) robots too.

The short version

  1. Open Robot Configuration in the Studio's sidebar.
  2. Drag the robot's .urdf (or .xacro, its description-package folder, or a .zip of that folder) onto the Robot Configuration page (anywhere on it; Add a robot under the robot list lights up). Or use its buttons to browse. Up to 200 MB in all per drop. The URDF is required: the controllers read it. If you also have the robot's MuJoCo model (.xml and its meshes), drop it together with the URDF or keep it in the same folder — it is then used for simulation (see Your own MuJoCo model below).
  3. Check the one review screen. Everything on it was read from the robot's own files; fix the name if you like, and the end effector if the guess is wrong.
  4. Click Create robot, then Try in simulation. The Studio starts the MuJoCo simulator and the FIC controller for it, and the arm moves to its home pose.

The new robot joins the list, the toolbar's robot selector and the Robot → Select Robot menu straight away. Everything it needs is written in the same layout as the robots that ship with FIC (see What gets written below).

What your URDF needs

Most vendor URDFs work as they are. The importer tells you on the review screen when something is missing, and whether it could work around it (! a note) or not (✕ an error that stops the import).

RequirementWhyIf it is missing
One tree with one base linkURDF's own rule; the base is fixed to the world in simulation.✕ Not importable. Fix the URDF.
The arm's joints are revolute or continuousThe simulator and the controllers drive rotating joints.✕ A sliding (prismatic) joint on the arm stops the import. Sliding gripper fingers are fine.
At most 12 arm jointsThe Studio's joint editor handles 1–12.✕ Pick an end effector nearer the base, or split the robot.
<limit lower upper effort velocity> on each arm jointLimits become the robot's joint limits, effort its torque limits, velocity caps its speed limit.! A missing effort becomes 50 N·m, flagged (default); set the real value before using hardware. A missing velocity is written as 2 rad/s in the controllers' copy, which needs one.
<inertial> with mass > 0 on every moving linkGravity compensation and the simulation's dynamics come from the masses.! MuJoCo estimates the mass from the mesh; the arm then droops or pushes in simulation. Real values fix it.
Meshes the importer can find, as .stl, .obj or .daeMuJoCo draws and collides with them.! .dae is converted to .obj. Other formats, and files not found, are left out — except a missing display mesh when the link has a collision mesh, which is simply drawn instead.
Loops written somewhere, for a closed-loop robotA URDF is a tree, so a parallel mechanism's URDF has its loops cut (the CSPM's platform floats free).✕ “Looks like a closed-loop mechanism, but no loops were found”: add its MuJoCo model, or add the loops on the review screen (Closed-loop robots below).

Where the meshes may be

The importer looks for every mesh the URDF names, in this order:

  1. a package://pkg/… path in a ROS package inside what you dropped (a folder with a package.xml), then in an installed package;
  2. a path relative to the URDF;
  3. an absolute path; one written on another machine (/root/ws/install/pkg/share/pkg/meshes/…, common in exported URDFs) is found again in the same package here;
  4. failing all of those, a file of the same name anywhere in what you dropped (case-insensitive, since CAD exporters write LINK1.STL).

So dropping the whole description package (or the folder above it) almost always finds everything. The review screen says how many meshes were found.

xacro files

A .xacro is expanded with ROS's xacro tool. Its $(find pkg) finds packages inside the folder you dropped as well as installed ones, so an unbuilt description package works. Many xacro files need arguments (a robot variant, a prefix); the importer cannot guess those and says which one is missing. Expand it yourself then, and drop the result:

xacro gen3.xacro dof:=7 > gen3.urdf

When a folder holds several robot descriptions (Kinova's ros2_kortex has 28), the review screen lists them at the top: pick the one you mean.

Your own MuJoCo model

Without one, the Studio builds the simulation model from the URDF. With one, it uses yours: someone tuned its contacts, damping and solver, and it can hold what a URDF cannot, above all the constraints that close a parallel robot's loops. It is found when

  • you drop it together with the URDF (select both, or drop the folder that holds both);
  • it is in the folder you dropped, or beside a dropped URDF (its folder or the one above, as menagerie/model/<robot>/URDF and xml/ sit), and shares at least half the URDF's moving joints;
  • or you pick it on the review screen (Add yours…). Don't use it goes back to a model built from the URDF.

It is copied into the robot's xml/ folder with its meshes, and changed only where FIC needs it to be:

ChangeWhy
The actuator on driven joint k becomes the motor torq_jk; a position or velocity servo there is replaced by a torque motor with the same force limit.The FIC controller commands torque, joint by joint, through actuators of those names.
A force_torque_site with force_sensor and torque_sensor on the end effector, if the model has none.The simulated wrench readout.
A home keyframe at the home pose, loops closed.The viewer opens there.

Everything else — damping, solver settings, contacts, a gripper actuator named gripper — is kept. Before anything is written the importer checks that the model and the URDF describe the same robot: every shared joint must have the same axis through the same point at the zero pose. If not, the review screen names the joints (the controllers use the URDF and the simulator the MuJoCo model, so they would fight).

Closed-loop robots

A parallel mechanism — the CSPM, a five-bar, a delta — is a tree with some links joined again. Each join is a loop closure: a point on one link held to a point on another. FIC stores them as loop_closures (bodyA, posA, bodyB, posB, each point in its link's frame); the controllers' pinocchio_closed_loop solver closes them itself, and the simulator closes them with MuJoCo connect constraints. The importer takes the loops from, in order:

  1. the robot's MuJoCo model: its <equality><connect> constraints (by sites or by bodies), turned into the URDF's link frames — each point is taken to world coordinates at the reference pose and brought back into the matching link, so it does not matter where either file puts its frames;
  2. markup in the URDF: Drake's ball constraint, or onshape-to-robot's closing frames — 
    <robot name="five_bar" xmlns:drake="http://drake.mit.edu">
  …
  <drake:ball_constraint name="tip">
    <drake:ball_constraint_body_A name="l_dist"/>
    <drake:ball_constraint_p_AP value="0.1 0.15 0"/>
    <drake:ball_constraint_body_B name="r_dist"/>
    <drake:ball_constraint_p_BQ value="-0.1 0.15 0"/>
  </drake:ball_constraint>
</robot>
    or two frames (fixed links) named closing_<name>_1 and closing_<name>_2 at the two ends of the cut;
  3. you, on the review screen: Add a loop…, pick link A, the point on it (in its frame) and link B. The point on B is where the point on A is in the URDF's zero pose, since a URDF is cut with its loops still assembled.

With the loops known, the importer works out the rest on a MuJoCo model of the mechanism (yours, or a quick one built from the URDF):

SettingHow
End effectorA free body the loops hold (the CSPM's platform); else a link sitting where a loop closes, preferably one named like an end effector (a five-bar's tip).
Driven jointsYour MuJoCo model's actuators; else the joints nearest the base, taken one by one until the end effector cannot move — parallel robots mount their motors on the base, and a redundant arm keeps all its joints. Untick or tick them in the Driven column. They become joint_names, in that order.
Degrees of freedomHow the end effector can move with the loops closed, checked at a pose that is not special (reference poses are often singular). The review screen refuses a set of driven joints that leaves it free to move.
Orientation onlySet when no motion the loops allow moves the end effector's origin — a spherical mechanism — so Cartesian control steers orientation only (ee_orientation_only).
Shown jointsEvery joint of the mechanism in view_joint_names, passive ones greyed; a ball joint as its roll / pitch / yaw.
HomeDriven joints at home, the rest moved to close the loops (the keyframe and the default target use that assembled pose).

Joints that are not part of the mechanism (a gripper, say) are held fixed as for any robot. The controllers' URDF keeps every mechanism joint, including a floating platform's; in a MuJoCo model built from the URDF a free body below the base gets three slides and a ball, since MuJoCo frees only top-level bodies, and passive joints are damped like the driven ones.

Imported from its folder, the CSPM comes out with the joint_names, end effector, solver, ee_orientation_only, view_joint_names and loop_closures of its hand-written config, and the Kinova + CSPM wrist picks exactly Actuator1…7, phi1_1…3 as its driven joints.

The review screen shows each of these with the file it came from. All of them can be changed afterwards on the robot's tabs.

Finding the SRDF

A robot's ROS packages often come with a *_moveit_config package beside the description. The importer uses its SRDF when the SRDF names the joints of the URDF you are importing:

  • dropping a folder or zip: any .srdf / .srdf.xacro inside it;
  • dropping one file from a description package: the SRDFs in the sibling packages named like it (franka_description → franka_moveit_config).

What gets written

Everything goes into fic_ws/src/menagerie/model/<Robot ID>/, the layout every FIC robot uses:

menagerie/model/<Robot ID>/
  URDF/
    <Robot ID>.urdf           the controllers' copy (Pinocchio: FK, IK, gravity)
    <Robot ID>.original.urdf  the URDF exactly as imported (xacro expanded)
    meshes/                   the original mesh files
  xml/
    <Robot ID>.xml            the MuJoCo robot
    scene.xml                 floor, light and sky around it — what the simulator loads
    assets/                   meshes MuJoCo reads (.dae converted to .obj)
  import_report.md            what was found and done (Overview → Import report)

It is built in a hidden staging folder and moved into place only once the model has loaded and passed its checks, so a failed import never leaves half a robot behind. The robot is then added to both robot lists (fic_studio_robots.yaml and fic_library/config/robots_config.yaml) and to config.xml.

The MuJoCo model

MuJoCo imports the URDF itself (bodies, joints, limits, inertias, meshes); the importer then adds what FIC's simulator expects, as the hand-made models have it:

  • a <motor> per arm joint named torq_j1…torq_jN in joint order, limited to the joint's torque;
  • force_torque_site on the end effector with force_sensor and torque_sensor, for the simulated wrench;
  • a 1 kHz implicitfast integrator and a little joint armature;
  • joint damping scaled to each joint's torque (1.15 × effort, at most 45 N·m·s/rad, as the Kinova and Franka models use), so full torque still moves a joint at about 0.9 rad/s and the arm settles instead of falling in the seconds before the controller starts;
  • self-collision off (exported meshes overlap at every joint and would make the arm shake) — the robot still collides with the floor and with objects;
  • a home keyframe, and for a sliding-finger gripper an actuator named gripper.

Before it is saved, the model is loaded and held at its home pose for half a second under gravity compensation. An arm with sensible masses and joint axes does not move; if it drifts, the review screen says so.

The controllers' URDF

URDF/<Robot ID>.urdf differs from the original in three ways, all so the controllers load exactly the configured joints:

  • joints off the arm (fingers, wheels, a pan-tilt head) are fixed;
  • continuous joints are written as revolute without bounds, FIC's way of marking a continuous joint (see Joint Continuity). Pinocchio then gives each one position coordinate rather than a cos/sin pair, which the controllers need;
  • a missing effort or velocity is filled in — urdfdom, which Pinocchio uses, refuses a joint without them.

When Pinocchio is installed for Python, the importer also loads this URDF the way the controllers will and warns if it cannot.

No rebuild needed

A new robot runs as soon as it is created because nothing it needs is compiled in or installed:

  • the controllers read robots_config.yaml and the URDF from the source tree every time a robot is loaded;
  • the Studio starts the simulator with model_file:= the robot's scene, so the simulators' launch files need no entry for it (any simulation_launch.py takes it: mujoco_native and mujoco_newton);
  • config.xml is installed as a link to fic_library/config/config.xml by colcon build --symlink-install, which this workspace uses. (A copy install would need colcon build --packages-select fic_control to see a new robot's tuning.)

Real robot: the driver library

A real robot runs through a driver: a program built from the vendor's SDK that talks to the robot on one side and to FIC on the other, through the shared-memory segment /robot_feedback_memory (fic_library/include/fic/shared_params.h). The FIC hardware node writes the commanded torques there; the driver sends them to the robot and writes back the measured joint positions, torques and tool wrench. The shipped robots keep their libraries in FIC_Interface/robot_library/ — {robot_lib} in the commands:

LibraryDriver sourceBuilt by
Kinova (Kortex api_cpp)api_cpp/examples/01-torque-control/00-Torque_Controller.cpp./scripts/build-gcc.sh in api_cpp/examples
libfrankaexamples/cartesian_impedance_control.cppCMake, in libfranka/build

Adding one

  1. Select the robot, open its Hardware tab.
  2. Drop the library's folder, or a .zip of it, on Add the driver library (or click it to browse).
  3. Check the one review screen: the folder name it gets in robot_library, how it builds, the driver program and, if the driver needs them, its arguments (the robot's IP address, say). The robot will run shows the exact driver command.
  4. Click Set up. The library is copied into robot_library/<name> (nothing is copied when it is already in robot_library), the build and driver commands are saved, and the build runs with its output on screen. Afterwards the Studio finds the program the build made and points the driver command at it.
  5. Check the torque sign and limits, tick This robot has a hardware driver and Save. Until then the hardware node refuses to control the robot — setting up a driver does not tick it for you. The API button in the toolbar then starts the driver.

Only the driver fields are saved by Set up; other edits on the page stay unsaved, as you left them. A library another robot uses is named on the review screen before you can replace it. The copy goes into a hidden folder first and is renamed into place when complete, so a cancelled copy leaves nothing behind.

What the Studio looks for

WhatHow it is found
The driverSource files that mention shared_params.h, /robot_feedback_memory or SharedFeedback and have a main() (or a Python __main__). Names with stub, mock, test, sim, example or demo are offered last.
The buildA build*.sh script (one in scripts/ runs from the folder above it, as Kinova's does); the top CMake project (cmake .. -DCMAKE_BUILD_TYPE=Release && make in <project>/build); a Makefile; a Python package (pip install --user -e ., not run for you). The one containing the driver's source comes first, a script before the CMake project it wraps.
The programAlready built (in a build* folder): used as it is. Otherwise the build names it, so the review screen shows a guess from the source's name, and after the first build the program named after the driver's source is used — Kinova's build turns 00-Torque_Controller.cpp into 01-torque-control_00-Torque_Controller. A build that made a single program is trusted too.

A library in robot_library/<name> finds FIC's header at ../../fic_library/include, as the CSPM build does, and the driver is started with FIC_ROOT set to the FIC_Interface folder.

A vendor SDK alone is not a driver

If nothing in the library uses FIC's shared memory, the review screen says so: the SDK talks to the robot, but nothing passes FIC's torques to it. Write the bridge — a program that maps /robot_feedback_memory, sends commanded_torque[] to the robot each cycle and writes back joint_positions[], torque[] and tool_wrench[] — into the library and drop it again. CSPM's src/cspm_fic_bridge.cpp shows the whole loop, and its src/fic_shm_stub.cpp stands in for the hardware node so a bridge can be tested alone.

The build did not finishThe commands are saved; fix what the build output shows (often a missing dependency) and press Compile driver.
Not covered by the importer
  • Sliding drives (a linear actuator on the arm or in a mechanism): the controllers drive rotating joints.
  • Loops other than point loops: weld constraints and joint couplings in a MuJoCo model are simulated, but the controllers model only point loops.
  • Legged and mobile robots: a floating base is fixed so the robot stays mounted; legged robots use the locomotion setup instead.
  • Rotating-knuckle grippers are held fixed in simulation.
  • Writing the driver: an imported robot is set up for simulation. The Hardware tab copies, builds and runs a driver library, but the FIC bridge inside it is written for each robot (see Real robot).
