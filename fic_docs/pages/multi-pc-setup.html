Multi-PC Lab Setup

Running FIC Control Studio on several robot PCs at once — one Studio per robot, all on the same version, told apart by station, reachable from other devices, and started automatically.

Overview

A lab usually has one PC per robot, each running its own FIC Control Studio. For those Studios to work together — and not trip over each other — a handful of things have to be the same on every PC, and one thing has to be different:

Must be the same on every PCMust be different on every PC
FIC branch and commit, builtStation ID — one per robot, matching the PC (PC 1 → station 1, …)
ROS 2 domain ID
Default robot model and first-launch choices

This page covers those settings, reaching each Studio's Web Remote from other devices, starting the Studio at boot, and keeping every PC on the latest version. It does not prescribe a network layout: whether the PCs share a switch, a Wi‑Fi network, or something else is up to your lab. The only requirement is that each device can reach the PC it wants to talk to, and that the robot PCs can reach each other if their Studios should discover one another.

Edit settings with the Studio closed

Everything below lives in ~/.robot_selector_gui_settings.yaml on each PC. The Studio auto-saves that file on a timer and on exit, so an edit made while it runs is silently overwritten. Close the Studio, edit, then start it again. See Settings for every key.

1. The same version on every PC

Pick one branch for the whole lab and put every PC on the same commit of it:

cd ~/FIC_Interface
git fetch origin
git checkout -B <branch> origin/<branch>
./build.sh

Check with git log -1 --oneline on each PC: the commit must match. Local edits on a robot PC (tuning files, config tweaks) make PCs silently differ — commit what should be shared, and keep genuinely per-robot changes out of the checkout, or record them before resetting.

Workspaces copied from another machine

A fic_ws copied from another PC (or another user's home) carries CMake caches that point at the old path. colcon then fails within a second with “The current CMakeCache.txt directory … is different than the directory … where CMakeCache.txt was created”. Delete the generated folders and build clean — they are not in git:

cd ~/FIC_Interface/fic_ws && rm -rf build install log && cd .. && ./build.sh

The Settings page's Clean Rebuild does the same.

One PC builds, another does not

Compare installed packages. A common case is the MuJoCo simulation failing with GLFW/glfw3.h: No such file or directory: that PC has libglfw3 but not libglfw3-dev. See the dependency lists on Installation (Linux).

2. A unique station ID per PC

The station ID decides which robotN topics a Studio drives and names its nodes, so two Studios with the same ID on the same ROS domain fight over the same robot. Give each PC the ID of its robot. In the Studio use the toolbar Robot selector (it confirms and restarts the app), or with the Studio closed set it in the settings file:

general:
  station_id: 2

A PC that has never run the Studio has no settings file and starts as station 1 — easy to miss when several PCs were set up the same day.

A PC with no arm of its own (a lab's control PC) takes the Master station (station_id: 0; any number of PCs can be Master, each on topics of its own): it sees and commands the whole fleet from the Multi-Robot page, and its simulations can never reach a real arm. The Multi-Robot page warns when two Studios claim the same station.

3. One shared ROS domain

Studios find each other (the Web Remote lists the other Studios, and multi-robot work spans PCs) only when they share a ROS 2 domain. Choose one domain ID for the lab and set it on every PC:

network:
  ros_domain_id: 10
The shell wins over the settings file

The Studio only applies network.ros_domain_id if ROS_DOMAIN_ID is not already set, and both launch scripts re-apply export ROS_DOMAIN_ID=… lines from ~/.bashrc. An old export there silently overrides the file. Keep the two in agreement:

grep -n ROS_DOMAIN_ID ~/.bashrc

If there is an export, make it the lab's value (or remove it). Terminal-launched ROS tools use it too.

When Studios do not see each other

ROS 2 finds other machines by multicast (group 239.255.0.1). Check the path with two terminals, ros2 topic pub /t std_msgs/msg/String on one PC and ros2 topic echo /t on another. If PCs on wifi stop seeing each other a few minutes after they start, while wired ones still work, the wifi router is filtering multicast by IGMP snooping and nothing on the network sends IGMP queries, so it forgets who listens. Either turn IGMP snooping off on the router, or run an IGMP querier on one wired machine (one query a minute is enough).

ROS_STATIC_PEERS (a list of addresses to contact directly) also works around missing multicast, but over wifi it makes every new publisher or subscription slow — a Studio can take a minute to start — so prefer fixing multicast.

Avoid domain 0 on a network that other ROS machines share: it is every machine's default, so a visitor's laptop would join your graph.

4. Reaching each Studio's Web Remote

Each Studio serves its Web Remote on all of the PC's network interfaces, on web_remote.port (default 8088; the next free port is used if it is taken). So any device that can reach the PC on any of its addresses can open it:

http://<an address of the robot PC>:<port>/
  • Use the address on the network the device is on — a PC with two network connections has two addresses, and a device on either side uses the one on its side. The Web Remote settings card lists the PC's addresses.
  • If one PC is set to a different port, note it: the port is per PC, in web_remote.port.
  • A firewall on the robot PC must allow that port from the networks that should use it.
No login, by design

Anyone who can reach the port can take control of the robot from the page. Only expose it on networks you trust.

5. Starting the Studio at boot

FIC Control Studio is a desktop application: it needs a logged-in desktop session. A robot PC that reboots to the login screen has no Studio — and so no Web Remote — until someone logs in.

Start it at login

Create ~/.config/autostart/fic-control-studio.desktop for the robot PC's user (adjust the path):

[Desktop Entry]
Type=Application
Name=FIC Control Studio
Exec=/home/<user>/FIC_Interface/fic_install/fic-control-studio.sh
Terminal=false
X-GNOME-Autostart-enabled=true
X-GNOME-Autostart-Delay=10

The short delay lets the network come up before the Studio starts.

Log in automatically (optional)

For a PC nobody sits at, enable automatic login so the desktop — and the Studio — come up after every reboot. On Ubuntu with GDM, in /etc/gdm3/custom.conf under [daemon]:

AutomaticLoginEnable=true
AutomaticLogin=<user>

Trade-off: whoever is at the PC's screen has its desktop without a password (sudo still asks). Also stop the PC suspending when idle, or it will look switched off.

Answer the first-launch wizard in advance

The first time a user starts the Studio it opens the first-launch wizard and waits. Until it is answered the main window is not built — and the Web Remote does not start. On an unattended PC that is a Studio that appears to run but cannot be reached. Answer it once by hand, or set it in the settings file (Studio closed):

general:
  wizard_completed: true
  default_robot: KinovaGen3_7DOF
Set default_robot explicitly

A Studio that has started once writes the built-in default default_robot: Franka_FR3 even though nobody chose it. When pre-answering the wizard, set the robot the PC actually drives.

6. Keeping every PC up to date

Update each PC with the commands in step 1 whenever the branch moves. If you automate it (a timer, or a script run from one machine), follow the same rules the Studio's own safety relies on:

  • Never update while a hardware or simulation node is running (fic_hardware, fic_simulation, …): the code would change under a moving arm. Skip that PC and try again later.
  • Close the Studio first, update and rebuild, then start it again. An open Studio holds the old build, and it rewrites its settings file on exit.
  • Save anything a reset would discard (git diff, untracked files) before resetting a PC.
  • After updating, confirm each PC still has its own station ID and the shared domain.
