Architecture

How the system components fit together.

System Diagram

Three layers, one controller. The Studio (PyQt5) publishes commands on robot{N}_* topics. A C++ controller node — fic_simulation_node or fic_hardware_node, both wrapping the same FIC library (fic_library/include/fic/) at 1 kHz — turns them into torques. In simulation the torques go over ROS 2 topics (prefix robot{sid}_simulation/, e.g. /robot1_simulation/actuators_cmds) to a physics backend: the CPU MuJoCo simulator mujoco_native (Python on the mujoco wheel, with its viewer) or the optional GPU mujoco_newton node. On hardware they go through POSIX shared memory to the vendor driver. See Simulation vs Hardware and Topics.

GUI Mixin Architecture

The GUI is a single ProfessionalRobotGUI(QMainWindow) composed of 12 mixins via multiple inheritance (main_window_pro.py). Page-owning mixins each contribute a page to the central QStackedWidget; the rest provide shared services.

Everything optional lives outside the mixins as a discoverable extension: a folder under Extensions/<name>/ at the repo root with a manifest.json and an extension.py. Auto-tuning, sequences, teach mode, the script editor, teleoperation, tracker, experiments, trajectory tests, and the VR features all ship this way; folders without a manifest are skipped at discovery. Cross-extension imports are forbidden — shared code goes in Extensions/_shared/. See Extensions API.

Process Management

The toolbar has a target selector (Simulation / Hardware / VR) and a single ▶ Start toggle that brings up the whole stack for that target, plus independent EXP / BAG / PLT buttons. Each spawned child runs in its own process group and is killed with the GUI (crash-cleanup hooks + parent-death signal). Details on Processes.

Simulator won't come up?

Simulator stdout/stderr is captured to /tmp/fic_sim_<pkg>_<timestamp>.log (e.g. /tmp/fic_sim_mujoco_newton_...). Check it when the button toggles to running but no window appears — Newton crashes on some mesh-heavy MJCFs land there, not in the GUI log.

Event Loop

PyQt5 and ROS 2 share one process. entry_pro.py creates a SingleThreadedExecutor and drains its callbacks from a QTimer, so ROS callbacks always run on the Qt thread and can touch widgets directly:

executor = SingleThreadedExecutor()
executor.add_node(node)

def _spin_ros():
    deadline = time.monotonic() + 0.008
    while time.monotonic() < deadline:
        executor.spin_once(timeout_sec=0)

timer = QTimer()
timer.timeout.connect(_spin_ros)
timer.start(10)  # tick every 10 ms, spin ROS for up to 8 ms per tick

Hardware IPC: POSIX Shared Memory

On hardware, the 1 kHz torque path deliberately bypasses DDS. fic_hardware_node and the vendor driver map two POSIX shared-memory segments defined in fic_library/include/fic/shared_params.h. The structs reserve kMaxJoints = 16 slots (a runtime n_joints field says how many are active) and carry a magic/version header (kShmMagic = "FICS", kShmLayoutVersion = 3); a mismatched version or byte-size triggers unlink-and-recreate so upgraded processes never silently alias an old layout.

All fields are std::atomic<float> / std::atomic<uint32_t> with acquire/release ordering — no locks in the servo path. stop_torque_mode is set by fic_hardware after the graceful torque ramp-down so the driver exits torque mode cleanly (see E-STOP). Why shared memory instead of topics is covered on Simulation vs Hardware.

Stale segments

If fic_hardware reports a magic/version mismatch after an upgrade, stop both processes and remove /dev/shm/robot_feedback_memory (and /dev/shm/desired_joint_angles_memory) before restarting.

Multi-robot topology (v3.3.0+)

One FicStudioNode can drive several robots concurrently. Internally it owns a pubs[rid][key] table — one publisher set per active robot, e.g. pubs['robot1']['mode_select'], pubs['robot2']['gripper_width'], etc. Robots come and go at runtime via node.add_robot(N) / node.remove_robot(N), called from the Multi-Robot page (e.g. its Drive button on another station's card). The legacy single-robot attributes (mode_publisher_, position_publisher_, the real_joint_publishers dict, the robot_N_*_publisher aliases) all alias to the first active robot, so unmigrated code keeps working unchanged.

Each robot still needs its own backend process — fic_hardware or fic_simulation, launched with a unique station_id ROS parameter (1–4, or 100–999 for a Master) — so the robot{N}_* topic prefix routes to the right physical or simulated arm. The Studio doesn't manage these processes; they're owned externally.

Per-extension targeting is layered on top: every extension's ExtensionHost carries its own target_robot_id independent of the Multi-Robot page's selection, with a make_target_robot_combo() UI factory and target_robot_changed Qt signal for retargeting. See Extensions API.

Important Notes

  • Do not publish to robot{N}_selected_robot during active control — the controller reloads the Pinocchio model and resets its planner state (robotSelectionCallback), causing a Jacobian size mismatch mid-motion
  • config.xml is shared — changes from the Tuning Panel or auto-tuner affect both simulation and hardware nodes; the controller reads the file into memory once per robot and mode, and again on a control-mode change, a H-PMP toggle that changes the parameter mode, a robot selection, a profile change or a robot{N}_param_update (sent by the Tuning Panel's SAVE TO XML) — not on a new target, and not on a file write alone. The read runs off the control thread (v4.4.0; see config.xml)
  • Scripts directory: ~/.fic_studio_scripts/ (Script Editor extension; examples under examples/)
