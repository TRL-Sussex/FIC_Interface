Working with Lab Robots from Your Own Machine

Run your own Studio as a Master, start a lab robot, and drive it with your own code — without changing FIC itself.

Overview

In a lab set up as in Multi-PC Lab Setup, every robot PC runs the lab's FIC Studio, which is kept on the lab branch. You do not change that. Instead:

  1. you run your own Studio as a Master on your own machine;
  2. from its Multi-Robot page you start a robot and watch it;
  3. your code (an FIC API script, an extension, your own ROS node) commands that robot over the network.

Changes to FIC itself go through a pull request into the lab branch, not onto the robots.

1. Set up your machine

  • Install FIC as usual (Installation (Linux)).
  • Connect to the lab network the robots are on.
  • Use the lab's ROS domain, in the environment your Studio and scripts start in (for example ~/.bashrc): 
    export ROS_DOMAIN_ID=<the lab's domain>
  • In the Studio toolbar, set Robot to Master. Every Master gets topics of its own, so any number of people can do this at once, and your own simulations never reach a lab robot.
Before the first run

A Studio that has never been configured starts as Robot 1. On the lab's domain that is a real robot's station. Choose Master, or run with a different ROS_DOMAIN_ID until you have.

For work that does not need the lab robots, use a ROS domain of your own (any number the lab does not use): your simulations and tests are then invisible to the lab and the lab to you.

2. Start a robot and watch it

Open Multi-Robot. Every Studio on the network has a card.

  • Start ▾ → Simulation or Hardware… starts that robot's session. The robot's own Studio does it, with the same checks as its web remote. The card shows the answer.
  • Drive points your control bar and extensions at that robot. Its state then comes to you from the robot's light feed (below).
  • Web opens the robot's web remote.
  • Commanded by on each robot card lists every Studio, script and ROS node that can move it — so everyone can see who is driving what.
  • E-STOP ALL stops every robot on the network.

3. Drive it with your own code

Everything FIC does to a robot goes through its robotN_* topics (Topics). From your machine, the FIC API is the simplest way:

from fic_api import Robot

r = Robot(target='simulation', robot_id=2, state='lite', node_name='alice_grasp')
print(r.get_current_joints())
r.move_joints([0, -30, 0, -90, 0, 60, 0])
r.close()
ArgumentMeaning
robot_idThe robot's station number.
state='lite'Read the robot's light feed: its state at 50 Hz, republished by its Studio on /robotN_lite/joint_states and /robotN_lite/ee_pose. Use it on any machine other than the robot's own PC; the full state is 1 kHz on several topics, too much over wifi.
node_nameGive it a recognisable name: with your script's name and host it appears in the robot's Commanded by.

Your own ROS nodes can publish to the same topics and read the light feed the same way. Extensions in your Master Studio work on a driven robot like on a local one.

Rules

  • Your code talks to robots only through their topics. Do not edit FIC on a robot PC: the lab keeps it on the lab branch, and local edits are discarded at the next update.
  • One robot, one driver at a time: check Commanded by before you start, and stop your script when you are done.
  • Start on simulation. Before hardware, make sure the area around the arm is clear — and remember each robot's own E-stop is the primary stop; stops over the network are a convenience.

Troubleshooting

SymptomCheck
No robots on the Multi-Robot pageSame network and ROS_DOMAIN_ID as the lab? See When Studios do not see each other in Multi-PC Lab Setup.
Your script reads zerosIs the robot's session running (its card says running or live)? With state='lite', the robot's Studio must be up.
